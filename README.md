# Home Hub

Home Hub is my server, to do what I want with, and to have futuristic things built on it that can help me do what I want: a cool program that knows stuff and can help me out.

## Why I built it
I built it to learn, to help me do more coding stuff, and because it was cool as shit.

## How I built it
I built it using my own ideas, with AI helping me plan and learn what I needed to do to make it. I made all the decisions and made each commit myself.

## How the parts fit
- Everything runs on one Ubuntu server, from one compose file: `docker-compose.yaml`.
- Caddy is the front door. Each service has a `.home` name, and AdGuard Home answers DNS on the home network, which is how those names reach Caddy.
- `hub.home` and `api.home` also answer over HTTPS, using Caddy's own certificate authority. Only devices that have installed Caddy's root certificate trust it, so plain HTTP still works everywhere.
- Nothing is open to the internet. Away from home, everything goes through Tailscale.
- The API (`api/`) is the centre: one module per capability, and every route except logging in needs a token. It reads from qBittorrent and Jellyfin, watches the server's Wi-Fi reconnect log, and can count and add notes in the brain's inbox.
- Every 5 minutes the API checks for problems (low disk or memory, Wi-Fi reconnects, a failed backup) and sends any change to my phone through ntfy. It also pings Healthchecks.io, which tells me if the server goes quiet, and sends a daily summary at 08:00.
- The phone page (`hub/`, at `hub.home`) is plain JavaScript served by Caddy, which passes `/api/*` on to the API.
- Claude Code reaches the API through an MCP server (`mcp/`), a throwaway container started for each session. Its tools read from the API; the three that change things (start a library scan, stop or start a download) always ask first.
- The brain is a separate private repo of notes, `hub-memory`. Its `inbox/` folder is mounted into the API.
- Anything that runs outside Docker lives in `host/`. The main ones are the Wi-Fi watchdog, a systemd timer that reconnects the Wi-Fi when the router stops answering, and the backup.
- Backups use restic. `host/backup.sh` backs up this folder, the brain and Claude Code's settings, stopping the apps that keep databases while it copies them. A systemd timer runs it every night at 03:30, but it stays off until there's a backup drive. Each run's result shows on the phone page, in the daily summary and at `GET /system/backup`, and can ping its own Healthchecks.io check. `docs/restore.md` explains how to get files back.

## Switches
New features are built switched off. Each switch is a line in `api/.env` set to exactly `on` or `off`. Anything else, or a missing switch, stops the API starting, so a typo can't quietly change what's on. `GET /system/features`, the phone page and the daily summary all show what's off. The MCP server has one switch of its own, `MCP_ACTIONS`, which `bash host/hub-mcp.sh read-only` turns off. Jobs that run on the server itself, like the nightly backup, are switched on and off by enabling or disabling their systemd timer.

### The deal watcher's settings
`DEALS` switches it on. While it's on, `api/.env` also needs `DEALS_SEEN` (`memory` or `disk`), `EBAY_ENVIRONMENT` (`production` or `sandbox`), `EBAY_CLIENT_ID`, `EBAY_CLIENT_SECRET` and `DEALS_AI` (`on` or `off`: whether Claude's tools may read the listings). Each search has its own `switch` in `deals/searches.json`. `docs/deals.md` has the rest.

### Finding your phone
`FIND_PHONE` switches on `POST /phone/find`, which sends your phone ntfy's top priority, "Here's your phone", to `NTFY_TOPIC`, so `api/.env` needs that topic while it's on. ntfy's docs describe that priority as really long vibration bursts and the default sound, with a pop-over; whether it sounds through Do Not Disturb or silent mode is down to the phone and its ntfy settings (not checked). It's sent at most once every 10 seconds. Jarvis asks it when you say "find my phone" (record 0046).

### Train times
`TRAINS` switches on `GET /trains`, the next five trains from one station to another, from National Rail's live departure boards (Darwin) through the Rail Data Marketplace (record 0047). While it's on, `api/.env` also needs:
- `RAIL_DATA_KEY`: the consumer key from your free Rail Data Marketplace account, on the "Live Departure Board" product's Specification tab. It's a secret, like the other keys in `api/.env`.
- `TRAINS_FROM` and `TRAINS_TO`: the two stations' three-letter codes, in capitals (National Rail's station pages show them).
- `TRAINS_BOARD_URL`: the departure board's address on that Specification tab, up to but not including the station code. In community copies of that tab it looks like `https://api1.raildata.org.uk/1010-live-departure-board-dep1_2/LDBWS/api/20220120/GetDepartureBoard`, but copy yours. It must be https on `raildata.org.uk`, with no `?`, `#` or `{` part.

The hub asks `TRAINS_BOARD_URL/TRAINS_FROM?numRows=5&filterCrs=TRAINS_TO&filterType=to`, sending the key in an `x-apikey` header. That's how community examples of the board's JSON version ask it; the official specification is behind the marketplace's login and wasn't checked, so `bash host/hub-get.sh /trains` is the first test. One copy of the specification describes `filterType=to` as trains starting or ending at `TRAINS_TO`; it's believed to mean trains that call there, which that first test should show with a train known to run on past it. It gives each train's booked and expected time, platform, whether it's cancelled (or cancelled at `TRAINS_TO`) and why, how many buses the board lists, and up to three of the board's own messages, which on a day with no trains may be all there is. The board covers about the next two hours, as far as community clients show (not checked), so "no trains" means none in that time. It says why when the board can't be reached, refuses the key, can't find the address (a 404 usually means `TRAINS_BOARD_URL` includes the station code), redirects or sends something that isn't a board, never with the key, and gives up after 8 seconds. Jarvis says the next three when you say "train times" (record 0046).

### Morning train alerts
`TRAIN_ALERTS` switches on a morning check of the trains between the same two stations, sent to your phone through `NTFY_TOPIC` (record 0048). It needs `TRAINS=on` too, and while it's on, `api/.env` also needs:
- `TRAIN_ALERT_DAYS`: the days to check, from `mon`, `tue`, `wed`, `thu`, `fri`, `sat` and `sun`, with commas between, like `mon,wed`.
- `TRAIN_ALERT_WINDOW`: the trains to watch, by the time they're due to leave, as two 24-hour times with a dash between, like `07:00-08:30`. Both ends count, and it must end by 22:59, so the hour after it is still the same day.
- `TRAIN_ALERT_REMINDER`: when to send the reminder, a 24-hour time like `06:45`. It must be before the window ends, and no more than 2 hours before it ends, since the board only looks about that far ahead.

London time throughout. On those days, at the reminder's time, the hub sends "Morning trains": each train in the window with whether it's on time, how late or cancelled and why, and its platform once the board has one, then any buses the board lists and its own messages. If the board's furthest train is due before the window ends, it says how far the board reaches, since it asks for only 10 trains. From then on it asks the board every 2 minutes and sends "Train change" when a train in the window:
- is cancelled, at high priority;
- becomes 5 minutes late or more, and again whenever that moves by 5 minutes or more;
- is shown as delayed with no expected time, when it wasn't already 5 minutes late;
- after one of those, is back to 2 minutes late or less, or is 5 minutes or more less late than last sent;
- runs again after being cancelled;
- moves from one platform to another (a platform appearing for the first time isn't sent);
- leaves the board more than a minute before it's due, while the board lists later trains and has fewer than 10 on it, which may mean it was cancelled or replaced by a bus.

So a train hovering around 5 minutes late, or flipping between a time and no time, doesn't send each flip. A train is known by the time it's due, so a change of destination (a train ending its journey early, say) doesn't make it a new train; only two trains due at the same time are told apart by destination. A train first seen after the reminder, as the board reaches further, is only sent if something's already wrong with it. It stops once the window has ended and none of its trains is still on the board, or an hour after the window ends, whichever comes first, and starts again the next set day.

If the board fails for 5 minutes or more, whether it can't be reached, refuses the key or sends something that isn't a board, it says so with when it started failing (about 6 minutes after the first failure, since it asks every 2 minutes), and keeps trying every 2 minutes. When the board answers again it says so, unless the reminder follows straight away, and if it's still failing an hour after the window ends, it says it has stopped checking for the day. Each outage is sent once. The API's log says when it couldn't reach the board and when it can again, never with the key. A notification ntfy didn't take is sent with the next check, 2 minutes later. It keeps nothing on disk: if the API restarts before the window ends, the reminder comes again with the trains as they are then, and if it restarts after the window ends, it only sends what's wrong with the window's trains still on the board. The notifications pass through ntfy.sh like the other alerts. The hub adds no station or destination names to them, but the board's own reasons and messages go as they are, and those can name stations.

### Jarvis's settings
Lines in `jarvis/.env`. Jarvis prints the `JARVIS_` ones in one line when he starts.
- `ANTHROPIC_API_KEY`: required.
- `JARVIS_LOG`: `on` or `off`, required, like the API's switches. Logs each answer's numbers, never its words, for `npm run compare`.
- `JARVIS_ENGINE`: `sdk` (default) or `api`.
- `JARVIS_THINKING_HISTORY`: `keep` (default) or `drop`. Only the plain API engine uses it.
- `JARVIS_LENGTH_HINTS`: `note` (default) prints the chat-length note below; `jarvis` gives Jarvis the chat's size with each question once it's long, and leaves the suggestion to him. The log records which, so `npm run compare` can show how big chats got before you typed `new`. The size lines stay in a saved chat, so type `new` before switching this setting on a saved chat, or its answers mix the two.
- `JARVIS_LENGTH_WARN`: the chat size, in tokens, where the length warning starts. Default `80000`, 80% of Haiku 5.5's long-prompt line. Set it lower to hear sooner, or to suit another model.
- `JARVIS_LENGTH_CAP`: `off` (default), or a number of tokens above the warning. Once a chat's last request passes it, Jarvis says so, won't send more questions in that chat, and says to type `new`. A guard against long chats quietly costing more. A saved chat's size is kept with it, so the cap still holds after a restart: in the chat file on the plain API engine, and on the Agent SDK in `jarvis/data/chats/agent-sdk-size.json`, which only counts while the transcript it names is still the newest.
- `JARVIS_HUB_TOOLS`: `off` (default) or `on`. On gives Jarvis the hub's read-only tools (status, alerts, switches, downloads, library, Wi-Fi reconnects and backup), through the MCP server in `mcp/`, which he starts inside his own container in read-only mode (unless `JARVIS_HUB_ACTIONS` is on), as one more Node process (about 60 MB) while he runs. Both engines use them. The log records whether he was given them, so `npm run compare` keeps answers with and without the tools apart; on the Agent SDK, a chat whose MCP server didn't start still counts as with. If the MCP server doesn't start or list its tools, Jarvis says so (the plain API engine as he starts, the Agent SDK with his first answer) and carries on with the brain only; the note doesn't say why, and running `npm test` for `mcp/` is the first thing to try. On needs two things, and he won't start without either:
  - Start Jarvis with `bash host/jarvis.sh`, which passes in only `API_TOKEN` from `api/.env`.
  - The MCP server built in `mcp/`, which Jarvis runs from `mcp/dist`: `npm ci`, then `npm test`, as under Tests below. After `mcp/` changes, run `npm ci` and `npm test` for it again, or Jarvis keeps using the old build. `host/hub-update.sh` does both when a pull changes `mcp/`. If the tests fail, `mcp/dist` already holds the new build, because `npm test` builds before it tests, so fix it before you next start Jarvis.
- `JARVIS_HUB_ACTIONS`: `off` (default) or `on`, and only with `JARVIS_HUB_TOOLS=on`. On lets Jarvis use the hub's three actions: scanning the library, and stopping or starting a download. Before each one, his own code (not his instructions) asks you in the chat what he wants to do, and waits for you to type `yes`, in any case. Anything else (even `exit`, which you'd then type again to leave) or no answer within 60 seconds means it isn't done, and he's told so. Ctrl+C closes Jarvis, so nothing runs. Only what you type after the question counts: in a terminal, anything half-typed before it is cleared. Two actions are asked one after the other. The log records whether this was on, so `npm run compare` keeps those answers apart.
  - The wait doesn't count towards the question's 2-minute limit, but it does show in that answer's time.
  - Jarvis takes only the hub tools he knows by name (the seven read tools, plus these three when this is on). A tool added to the MCP server later is left out on the plain engine until Jarvis is updated too; the Agent SDK still offers it to the model, but refuses it if he tries.
  - Before stopping or starting a download with a full hash, his code asks the API for it (`GET /media/downloads/<hash>`) and shows the start of its hash, how far it got and its name, so you're not relying on what Jarvis says. If the hub doesn't have that hash, the question says so. If the lookup fails or takes over 5 seconds, the question says the name couldn't be looked up. A hash that isn't 40 lower-case hex characters isn't looked up, and the question says so. Names come last, on one line, with hidden characters taken out, control characters shown as `�`, double quotes and look-alikes changed to `'`, and cut at 80 characters. Text he reads, such as a torrent name or, with `JARVIS_SESSION_NOTES` on, the sessions' notes, could still carry instructions aimed at him; records 0011 and 0012 have more.
- `JARVIS_SESSION_NOTES`: `off` (default) or `on`. On gives Jarvis the notes your two Claude Code sessions keep for themselves (the `MEMORY.md` in each one's auto memory, for `~/docker` and `~/hub-memory`), added to his instructions when he starts, so he can tell you what you've been working on. He keeps the first 200 lines or 25,000 characters of each, the limits in Claude Code's docs (which say 25KB), cut back to the end of a line, with hidden characters such as zero-width spaces taken out. If both are full, that's something like 12,000 to 17,000 tokens more in every request (Claude's estimate), which the cache makes cheaper while you keep asking within 5 minutes of the last question. He says at start-up how many lines he found for each session. The log records whether he had any.
  - Start him with `bash host/jarvis.sh`, which mounts each session's whole memory folder read-only at `/notes`, whatever this setting says. Only `MEMORY.md` is read, and none of his tools can read outside the brain. The script also needs `API_TOKEN` in `api/.env` and passes it in, though he doesn't use it unless the hub's tools are on.
  - The script finds the folders the way the bundled Claude Code named them in a test (the docs only say the folder comes from the git repo): the repo's full path with every character other than letters and digits turned into `-`, under `~/.claude/projects`, or under `$CLAUDE_CONFIG_DIR/projects` if that's set, which the memory docs don't mention. It doesn't know about Claude Code's `autoMemoryDirectory` setting, so if you set that, he finds none. `ls -d ~/.claude/projects/*/memory` shows what's there.
- `JARVIS_VOICE`: `off` (default), `kokoro` or `piper`, written plainly on a line of its own. With `kokoro`, Jarvis has a voice, made by [Kokoro](https://github.com/remsky/Kokoro-FastAPI), a speech engine that runs in its own container (the `kokoro` service). With `piper`, it's made by [Piper](https://github.com/OHF-Voice/wyoming-piper) instead, in the `piper` service, and everything below that says Kokoro applies to Piper too, apart from Kokoro's memory, voice, speed and logging, which `JARVIS_PIPER_VOICE` below covers for Piper (record 0034). He says one sentence out loud when he starts ("Jarvis is ready when you are."), then speaks his answers, a sentence at a time, while they're still being written. Start him with `bash host/jarvis.sh`, which then builds his image for sound, passes in the card named by `JARVIS_SOUND_CARD`, starts Kokoro and waits up to 2 minutes for it to be ready, and stops it again when the chat ends. If `JARVIS_SOUND_CARD` is missing or wrong, or the image won't build, the script stops there and says why. As he starts, he sets `JARVIS_VOLUME`, checks that Kokoro answers, says the sentence and prints a `Voice:` line. If any of that fails, or the sentence takes more than 45 seconds, the line says his voice is off and why, and the chat carries on in text. The one exception is a microphone device in his container, which stops him starting at all. The log records whether he had a voice, so `npm run compare` keeps those answers apart.
  - Kokoro used about 1.2 GiB of memory when it was measured on this server, and has a 2 GiB limit. It has no published port and sits on a Docker network of its own, `speech`, which has no route to the internet or the LAN and which only Jarvis joins. The server has no address on that network either, so Kokoro can't reach the server's own services, such as SSH (record 0024). If Kokoro is already running when the script starts, because you started it yourself (`docker compose up -d --wait kokoro`) or another chat did, the script says so, leaves that container exactly as it is, and doesn't stop it afterwards. Whoever started it stops it: the other chat's script when that chat ends, or you with `docker compose stop kokoro`.
  - Started with plain `docker compose run --rm jarvis`, he has no sound devices, so he says his voice is off.
  - What he speaks is the answer's own words, tidied for the ear: the marks for headings, lists, bold and code are left out, and code blocks, emoji and most file paths and web addresses are skipped. With `JARVIS_SPOKEN_STYLE=on`, anything in code marks is skipped too, found the way Markdown finds it within a line, so a stray backtick pairs with the next one; code marks left open, or code that runs over a line or past 400 characters, are still read out. A word counts as a path if it has a backslash in it, or a slash and one of these: it starts like a path (`/`, `~/`, `./`, `../`), ends in a slash or a file ending, starts with a site's name, has `://` in it, or is written whole in code marks. A table row is read as a list, and a list's number is read with a pause after it. The tool notes, the timing and cost lines and the yes-or-no question before a hub action aren't spoken, but what he said before one of them is spoken while it happens. If the engine starts an answer again, he starts speaking it again from the top. The screen shows exactly what it would without a voice, though `JARVIS_SPOKEN_STYLE` changes how he writes.
  - The prompt comes back as soon as the words are done, and he carries on speaking behind it. `new`, `exit` and Ctrl+C stop the sound at once. A new question, or Enter on an empty line, interrupts him the way `JARVIS_SPEECH_STOP` says, and a note says so: `(stopped talking)`, `(the last answer won't be spoken)` if he hadn't started, or `(stopping after this sentence)`. With `sentence`, if he's already on the last sentence nothing is cut, so there's no note; with `now`, the last sentence is cut short like any other, and noted. An empty line typed before the prompt is back is ignored, so an Enter pressed while you wait doesn't hush him before he's said anything; a question typed then is still asked once the prompt is back (record 0025). Until the prompt is back, which can be a while when he's using tools, only Ctrl+C stops the sound, and that ends the chat. At a hub action's yes-or-no question, an empty line still means no.
  - Each sentence is one request to Kokoro and is played by an `aplay` of its own. `aplay` and `amixer` get only `PATH` from Jarvis's environment, never his API key or tokens. Kokoro is asked for one sentence at a time and gets at most two ahead of what's playing. With `JARVIS_SPEECH_BUNDLE=on`, below, one request can hold several sentences, and what this paragraph says of a sentence's sound (skipped if it can't be made or played, two in a row, the time it gets to play) applies to that whole piece; the 40-sentence limit and the log still count sentences. Only the first 40 sentences of an answer are spoken. A sentence that can't be made or played is skipped. Two in a row that can't be made, or two in a row that can't be played, end the speech for that answer. Either way a note says so before the next answer, or when the chat ends (record 0023). The exception is a sentence he's finishing after being interrupted with `JARVIS_SPEECH_STOP=sentence`: if it can't be played, that's only counted in the log. A sentence gets twice its own length plus 10 seconds to play; a player still going after that is stopped, and the sentence counts as one that couldn't be played. A player that's stopped is asked to end first, and killed outright if it hasn't ended 2 seconds later, so a stuck one can't keep the chat from closing. Before the next sound, even in the next answer, he waits up to 3 seconds for that player to have ended, so a slow one has time to let go of the speakers before another starts. After 3 seconds the next one starts anyway. The wait doesn't count towards the next sound's time to play, and the log times a sound from when it reaches its player, after the wait. Only this chat's players are waited for, not another chat's.
  - With `JARVIS_LOG=on`, each answer given with his voice on gets a second line in the log when its speech is over: how long after the question the first sentence was sent to Kokoro, its sound came back and the first sound that played reached the player, the longest silence between two sentences (from one sentence's player finishing to the next sound reaching the player, so it leaves out `aplay` starting up and any quiet inside a sound, and it's empty when fewer than two sentences played; with `JARVIS_SPEECH_BUNDLE=on` it's between pieces, since sentences in one piece share one sound), how many sentences were spoken, failed (split into those that couldn't be made and those that couldn't be played) or left, how many requests the speech engine got and how many sentences went in them, including any made before an answer started again (record 0036), and whether the speech was stopped early, given up on or cut at 40 sentences. Never the words, and never the error a sentence failed with (record 0032). `npm run compare` shows the time to first sound and the longest silence, with the first question of each chat kept apart from later ones because Claude is slower on it. Kokoro is already warm by then, from the start-up sentence. A second table adds up, for each setting, the sentences played to the end, failed and not played in full, and the answers that made no sound, were stopped, were given up on or went over 40 sentences. Under it, each setting where sentences failed gets a line saying how many couldn't be made and how many couldn't be played. Log lines from before that split don't say which, so that setting's line counts them separately. Then a line for each setting says how many sentences the engine (Kokoro or Piper) was asked for in how many requests, and how many that is a request on average, which shows whether `JARVIS_SPEECH_BUNDLE` is really bundling; older log lines don't have it and are left out of it.
  - Kokoro is set to log errors only (`API_LOG_LEVEL` on the `kokoro` service). Left to itself it writes the first 50 characters of every piece of text it's asked to speak into its log, which Docker keeps; that's from its v0.10.0 code and docs, read and not yet seen on this server. A Kokoro that was already running when the setting changed keeps its old one. Stop it with `docker compose stop kokoro`, and the next `bash host/jarvis.sh` makes a new container with the new setting.
- `JARVIS_KOKORO_VOICE`: which of Kokoro's voices he speaks in, default `bm_george`. It takes any of Kokoro's voice names (`bm_fable`, `bm_lewis` and `bm_daniel` are other British male ones), or a blend like `bm_george(2)+bm_fable(1)`. Kokoro checks the name itself, so a wrong one shows in the `Voice:` line.
- `JARVIS_KOKORO_SPEED`: how fast Kokoro speaks, default `1`, its usual pace. Any number from `0.25` to `4`, like `0.9` for a little slower. It's sent with every piece of speech, the start-up sentence included. With Kokoro on, each answer's line in the log records it (`kokoroSpeed`), and `npm run compare` keeps different speeds apart; lines from before it was logged show as "speed not logged". The voice's name (`JARVIS_KOKORO_VOICE`) isn't logged.
- `JARVIS_PIPER_VOICE`: which of Piper's voices he speaks in with `JARVIS_VOICE=piper`, default `en_GB-alan-medium`, a British male voice. A name is the voice's language, speaker and quality, like `en_GB-northern_english_male-medium`; they're listed at https://huggingface.co/rhasspy/piper-voices/tree/main. It's checked every time he starts, voice or not.
  - Piper has no internet, so download the voice once before its first chat, after setting this: `bash host/jarvis.sh piper-voice`. It saves the voice named here in `piper/voices` (git-ignored, so a voice is never in this public repo), with its `MODEL_CARD`, which says where its recordings came from and their licence. Nothing is saved unless all three files arrive. Run it again to replace a voice. With the voice not downloaded, `bash host/jarvis.sh` stops before starting anything and says so.
  - Piper splits each piece of text into sentences itself and makes them one at a time, so with `JARVIS_SPEECH_BUNDLE=on` it gets fewer requests but no longer pieces to work on.
  - To start Piper by hand, as the Kokoro text above describes for Kokoro, use `PIPER_VOICE=<voice> docker compose up -d --wait piper`. Without `PIPER_VOICE` it's given `en_GB-alan-medium`, and Piper stops at once if the voice it's given isn't downloaded.
  - A `low` or `x_low` voice is played at 16,000 Hz and a `medium` or `high` one at 22,050 Hz. A voice whose settings give another rate isn't saved, and if Piper ever sends sound at another rate, that piece fails with a message saying so.
  - The alan voice's licence isn't clear: it's fine-tuned from a voice whose recordings are for research only, and its own recordings' licence reads "All Rights Reserved" (record 0034). It's used at home and never shared.
  - Piper has a 1 GiB memory limit, no published port, and the same network as Kokoro, `speech`, with no internet. It reads `piper/voices` read-only. It logs its start and its errors, never the words it speaks; it would only log them with `--debug`, which isn't set.
- `JARVIS_SPEECH_START`: `sentence` (default) or `clause`. With `sentence`, the first thing he says is the answer's whole first sentence. It's sent to Kokoro once the next sentence has begun, or a line ends, a tool starts or the answer ends. With `clause`, the first piece can end at the first comma, semicolon, colon or dash that has at least 20 spoken characters before it, so he starts sooner at the cost of a pause there. Only the first piece of an answer is cut that way, and the first piece after each tool he uses. The log records which, so `npm run compare` shows the time to first sound for each. It's checked every time he starts, voice or not.
- `JARVIS_SPEECH_STOP`: `now` (default) or `sentence`: what a new question or an empty line does while he's talking. With `now`, he stops at once, mid-word if need be. With `sentence`, he finishes the sentence he's on (with `JARVIS_SPEECH_BUNDLE=on`, the piece he's on, which can be several sentences) and says nothing after it; a new question is still sent straight away, and its answer's first sound waits until that sentence is over. Either way `new`, `exit` and Ctrl+C stop him at once. The log records which, so `npm run compare` shows each setting's times side by side. It's checked every time he starts, voice or not.
- `JARVIS_SPEECH_BUNDLE`: `off` (default) or `on`. With `on`, an answer's first piece (its first sentence, or its first clause with `JARVIS_SPEECH_START=clause`) still goes to Kokoro on its own, so its first sound comes as soon as before. After that, whenever Kokoro is free, the sentences already waiting go to it together. A sentence is only joined onto one that ends with a full stop, question or exclamation mark or ellipsis, so a line ending in a colon, or a list item without a full stop, isn't run into what follows. List items that end with a full stop are joined like any other sentences. A piece is no longer than twice the last piece Kokoro made, or 250 characters, whichever is smaller. Nothing is held back to wait for more. Kokoro's notes on its voices say they're weakest on very short pieces and suggest bundling them (https://huggingface.co/hexgrad/Kokoro-82M/blob/main/VOICES.md). Each piece is played by one `aplay`, so with `JARVIS_SPEECH_STOP=sentence` he finishes the whole piece he's on, which can be several sentences. The log records which, so `npm run compare` shows the times for each. It's checked every time he starts, voice or not (record 0033).
- `JARVIS_SPOKEN_STYLE`: `off` (default) or `on`. With `on` and his voice on, his instructions gain a paragraph asking him to write for the ear: lead with the answer, keep sentences short with the first one shortest, write numbers and units as they're said, leave out headings, tables and bold, use a list only when the order matters, and put file paths, commands, settings, web addresses and code in code marks without needing them to make sense of a sentence. What's in code marks is shown on screen but not spoken, with the exceptions above. It changes what's written too, since there's one answer for both. With his voice off, or if it can't start, his instructions are as they were. The log records which, so `npm run compare` shows the times for each. It's checked every time he starts, voice or not (record 0031).
- `JARVIS_PERSONA`: `off` (default) or the name of a file in `jarvis/persona/` without the `.md`, like `butler` (record 0050). He reads that file once when he starts and adds it to his instructions straight after his own, before the live facts, spoken style and session notes, under a line saying it shapes his manner only, never changes what he can do, and lasts the whole chat, tool use included. Only lowercase letters, numbers and dashes are allowed in the name, so it can't point outside that folder, and he won't start if the file is missing, empty or over 4,000 characters once tidied (blank space at either end trimmed, hidden characters taken out, as for session notes). Every character is sent with every question, so keep it short: `butler.md` with the line before it is about 1,400 characters, something like 350 tokens (Claude's estimate). His start-up line names it and counts its words, and the log records its name (never its words), so `npm run compare` shows each persona's numbers side by side. Edit the file and start him again to change it. `jarvis/persona/` is in this public repo, so keep personal details out of it; they belong in the brain.
- `JARVIS_LIVE_FACTS`: `off` (default) or `on` (record 0050). With `on`, his own code writes a short paragraph about what's switched on in this chat and adds it to his instructions: whether his voice is on and which engine is speaking, how you can talk to him (typing, `/talk`, the wake word, the talk button, and the follow-up window), whether he has the hub's tools and actions, and that he can't run commands, change files, browse the web or set reminders. With `JARVIS_EARS` on, it also lists the code words his own code answers before he sees them, and tells him that typed messages never count, so if you ask for one of those and it reaches him, you typed it or your words didn't match, and he should tell you the words to say out loud rather than claim he did it; with no hub token, it adds that notes, the phone and train times won't work until hub tools are on. It's written from what actually started (a voice that fails to start counts as off), and it says to trust it over older notes about himself. With everything on it's about 1,300 characters, something like 300 tokens (Claude's estimate). The log records whether it was on, so `npm run compare` shows the numbers with and without it.
- `JARVIS_FILLER`: `off` (default) or `on` (record 0044). With `on` and his voice on, when a tool starts in the middle of an answer and he has then been quiet for 1.2 seconds (nothing playing, being made or waiting to play, and the last answer's speech over), he plays two short low notes, 230 ms in all, unlike the wake word's chime. It plays at most once per tool call, and not at all once the answer's words come back, a yes-or-no question or a note comes up, the answer ends or is stopped, or his speech has been given up after two failures. A hub action asks first, so it gets none. A stop cuts it off. His speech isn't over until it has played, so the chat holds the wake word through it and ears doesn't hear it. It isn't logged.
- `JARVIS_EARS`: `off` (default), `push` or `wake`. With `push` or `wake`, `bash host/jarvis.sh` puts him on ears's network with `docker-compose.talk.yaml` and passes in `EARS_TOKEN` from `ears/.env`, and he can take a spoken question (record 0038). Type `/talk`: he stops talking at once and ears records for up to 30 seconds. Press Enter on an empty line to send it: he waits for Whisper's text, shows it as `You said: ...`, and answers it like a typed question. Type anything else to drop the recording, which ears then ends without sending it to Whisper; if it had already ended at its 30-second limit and been turned into text, ears clears that text instead. If ears doesn't answer a start or a stop, he cancels the recording anyway, in case it went through. His start-up line says whether ears is ready, muted or out of reach; the script doesn't start ears, so start and unmute it first (below). The log keeps how long a spoken question was recorded and how long its text took after Enter, never the words, and `npm run compare` shows them. Once asked, a spoken question is like a typed one: it goes to Anthropic's API, and with `JARVIS_CHATS=resume` it's saved with the chat. With `off` he isn't on ears's network and has no token.
- With `JARVIS_EARS=wake`, "Hey Jarvis" works as well as `/talk`, when ears has `EARS_WAKE=on` (record 0039). The chat waits on ears the whole time it's open, even while he answers, and a line under the prompt says when the wake word is on, or why it's off and what to do. When ears hears "Hey Jarvis" and the chat takes the recording, he stops talking, shows that he's listening, and, with his voice on, plays two short notes. Ears ends the recording once you've stopped talking (by loudness, or with `EARS_WAKE_END=silero` by Silero's speech detector); press Enter on an empty line to send it sooner, or type anything else to drop it. Then he shows `You said: ...` and answers, as with `/talk`. While any recording runs, `/talk`'s included, ears doesn't pass the microphone to openWakeWord, so "Hey Jarvis" said then does nothing. A wake after a `/talk` recording has ended at its 30-second limit, but before you've pressed Enter, takes over, because ears only keeps the latest recording (record 0040). Only one open chat takes each wake: a chat waiting for you to type takes it at once, and one that's still busy, answering or asking you something, waits a second first, so an idle chat gets it if there is one (record 0040). A chat that ends while it has a wake recording it hasn't finished with cancels it, so its text isn't left in ears. A false wake from the TV asks Claude whatever Whisper heard, unless ears heard nothing it counted as speech, in which case it's dropped; mute ears when you don't want him listening. The log marks these questions with `wake`, and which way ears was set to end the recording with `ender` (`loudness` or `silero`, even when you sent it with Enter or it ran to 30 seconds), and the pause it was set to end on with `pauseMs` (from `EARS_WAKE_PAUSE`), and `npm run compare` counts them, splitting their recording times by `ender` once both appear, and by `pauseMs` once two pauses appear. If ears ignores a "Hey Jarvis" because openWakeWord reported it more than 2 seconds after the sound, the chat says so on a line of its own, with how far behind it was. If the chat stops watching ears for any reason but closing, its status line says so (`wake word off: this chat stopped watching ears (...)`), rather than carrying on without the wake word.
- `JARVIS_FOLLOW_UP`: `off` (default) or a whole number of seconds from 2 to 15, only with `JARVIS_EARS=wake` (record 0043). Once he has answered a question you asked with "Hey Jarvis" (not when the answer failed) and his last sound has played, he waits half a second and asks ears to listen again for that many seconds without the wake word. A line under the prompt says he's listening for a follow-up; there's no chime. Start speaking within that time and it's recorded and asked like a wake question, and then the next window opens. Say nothing and it's dropped without going to Whisper, with a line saying so. Typed and `/talk` questions open no window, and anything typed before it opens (Enter on an empty line included), or a wake word, calls it off. After 5 follow-ups in a row he says to use "Hey Jarvis" again, because anything said in a window, the TV included, is asked, and with `EARS_WAKE_END=silero` the TV's dialogue counts as speech. Ears refuses a window while any chat is speaking, and just after it starts, before it has heard the room; the chat shows why. If asking fails, as when ears doesn't answer in time, he cancels a follow-up ears may have started anyway. Ears needs rebuilding for it with `bash host/ears.sh start`: an older one answers 404, and the chat says so. The log marks these questions with `follow` (and `ender`), and `npm run compare` counts them.
- Not listening to himself: every chat with his voice on and `JARVIS_EARS=push` or `wake` holds the wake word from when he starts answering (and while he says his start-up sentence) until his last sound has played, renewing the hold every 5 seconds, so ears doesn't listen to him. A recording that's already running while any chat holds it, as when a second chat starts speaking during it, hears silence for that stretch instead of him (record 0040). Holds need `EARS_WAKE=on`: with the wake word off, ears takes none, so a `/talk` recording made while another chat is speaking hears him. Ears starts again half a second after the last chat lets go, and a hold runs out by itself after 15 seconds if a chat stops renewing it. A chat with `JARVIS_EARS=off` can't reach ears to hold it, so don't have one speaking while a wake chat is open.
- `JARVIS_SOUND_CARD`: the speakers' name under `/dev/snd/by-path`, like `pci-0000:04:00.6`. `ls -l /dev/snd/by-path` lists the names and the card each leads to, and `cat /proc/asound/cards` says which card is which. `bash host/jarvis.sh` reads it, for the sound test and for a chat with his voice on: it follows the name to the card's number for this boot, and passes in only that card's mixer and speakers. Names stay the same after a restart; card numbers might not, and both cards on this server are called `Generic`, so their `CARD=` names can swap too. Set it again on a new server. Only the script reads it, so it isn't on his start-up line; his `Voice:` line names the card it led to.
- `JARVIS_VOLUME`: `0` to `100`, default `80`. Before anything plays, Jarvis sets the card's `Master` control to this and unmutes it (`0` mutes it), because the server forgets the level when it restarts and comes back muted (record 0015). The sound test does this, and so does a chat with his voice on. It's checked every time he starts, voice or not.
- `JARVIS_CHATS`: `fresh` (default) saves nothing; `resume` saves the chat in `jarvis/data/chats/` and picks it up next time.
  - Saved chats hold everything said, brain text included. Only their owner can read them, and backups copy them.
  - Every question sends the whole saved chat. On Haiku 5.5, a request over 100,000 tokens costs five times as much. Jarvis doesn't trim saved chats yet. The Agent SDK only summarises a chat when it nears its context limit (about 990,000 tokens in a test), so it pays the higher rate long before that.
  - When a chat reaches `JARVIS_LENGTH_WARN` (80,000 tokens unless set), Jarvis says once that it's getting long (once per start of Jarvis). Past 100,000, where Haiku 5.5's long-prompt price starts, he says so after every answer, with how to start a new one (unless `JARVIS_LENGTH_WARN` is set higher, when he waits for that). It goes by each answer's last request, and works in fresh chats too. With `JARVIS_LENGTH_HINTS=jarvis`, Jarvis is told the size instead and suggests a new chat himself.
  - Type `new` to start a new chat without leaving Jarvis. In a saved chat, the old one is moved to `jarvis/data/chats/old/` (private, the newest 10 per engine kept), Jarvis says exactly where, and it isn't carried on. To get it back, move it back by hand. A plain API chat brings its size back with it (if it was saved since sizes were kept); an Agent SDK one usually has no size known until its first answer. A leftover `*.saving` file is a save that was cut off, and is safe to delete.
  - Lines shaped like a command (a `/` then one word, like `/clear`) aren't sent to Jarvis, on either engine. The Agent SDK would otherwise run them as its own commands; `new` does that job on both. Paths like `/etc/hosts` go through as normal.
  - Run one Jarvis at a time on a saved chat: with two, one of them's questions won't be carried on.
  - The engines save differently: the Agent SDK also keeps questions that failed or were stopped, and the plain API engine keeps only answered ones. On the plain API engine, thinking is left out of the saved chat for good with `JARVIS_THINKING_HISTORY=drop`, or after a thinking restart.

## Running it
Secrets live in `.env` files that git ignores (`api/.env`, `homepage/.env`, `beszel/.env`, `jarvis/.env` and `ears/.env`), so they're never in this repo. The API also expects the brain's inbox at `../hub-memory/inbox`, and won't start without it. The backup's settings and password live in `/etc/home-hub/`, outside this folder and readable only by root.
- Start everything: `docker compose up -d`
- Rebuild the API after a change: `docker compose up --build --wait api`
- Pull from GitHub and rebuild only what changed: `bash host/hub-update.sh`, or `bash host/hub-update.sh --dry-run` to see what it would do. When `mcp/` changes, it also rebuilds the copy Jarvis runs. When Jarvis's packages change (`jarvis/package-lock.json`), it reinstalls them and runs his engine check, since a new Agent SDK brings a new engine. A change to his code alone needs nothing, because he builds himself each time he starts. Close Jarvis before updating: reinstalling packages replaces folders a running chat is using.
- Talk to Jarvis: `docker compose run --rm jarvis`. He's in the `jarvis` profile, so `docker compose up` never starts him. Type `exit` or press Ctrl+C to stop, and `--rm` removes the container. He needs `jarvis/.env` and the brain at `../hub-memory` (mounted read-only), and won't start without them. With `JARVIS_HUB_TOOLS=on`, `JARVIS_SESSION_NOTES=on`, `JARVIS_EARS=push` or `wake`, or his voice on, start him with `bash host/jarvis.sh` instead. He's on his own Docker network, `jarvis`, which only the API shares, so the API is the one container he can reach directly (when `host/jarvis.sh` gives him sound, for a chat with his voice on or for the sound test, he's also on `speech`, where he reaches Kokoro and Piper; with `JARVIS_EARS=push` or `wake` he's also on `ears`, where he reaches ears, Whisper and openWakeWord). Services with a published port or a `.home` name can still be reached through the server's address, as from any device on the LAN, and he can reach the internet, which he needs for Anthropic's API (record 0013).
- Test Jarvis's speakers: `bash host/jarvis.sh sound-test`. It builds his image for sound, `home-hub-jarvis` (`jarvis/Dockerfile`: his usual `node:26-alpine` plus `alsa-utils`, from its cache after the first time), finds the card named by `JARVIS_SOUND_CARD`, sets `JARVIS_VOLUME`, and plays two short beeps, low then high. It adds `docker-compose.sound.yaml`, the only place Jarvis gets sound devices: his card's mixer and speakers, read and write, never a microphone, and the group that owns them (record 0014). The same file puts him on the `speech` network, where Kokoro is when it's running; the sound test doesn't use it. Without it, as with `docker compose run --rm jarvis`, he gets none and runs on the stock image. A newer `node:26-alpine` reaches his image only after `docker pull node:26-alpine`.
- Ears, the service that owns Jarvis's microphone, and Whisper, which turns what it records into text (records 0035 and 0037). Jarvis uses them with `JARVIS_EARS=push` (record 0038) or `wake` (record 0039). Both are in the `ears` profile, so `docker compose up` never starts them.
  - Set it up once. `ears/.env` holds `EARS_TOKEN`, at least 32 characters (`openssl rand -hex 32` makes one), and `EARS_MICROPHONE`:
    - `card`: a real microphone, on the sound card that `EARS_SOUND_CARD` names, by its name in `ls /dev/snd/by-path` (like `JARVIS_SOUND_CARD`). That can be the laptop's own card, `pci-0000:04:00.6`, for its built-in microphone (it works, seen on 20 Nov) or a headset's in its jack, or a USB microphone's own card. At start, ears sets the card's `EARS_MIC_CONTROL` (default `Capture`) to `EARS_MIC_LEVEL` (0 to 100, default 80) and switches capture on, because a card's levels go back to how the driver starts them after a reboot. `EARS_MIC_LEVEL=keep` leaves the card's levels alone. `EARS_MIC_BOOST` is left alone unless it's set: a whole number of steps from 0 to 10 sets the card's `EARS_MIC_BOOST_CONTROL` (default `Internal Mic Boost`) at start too, for a microphone that's still too quiet with `EARS_MIC_LEVEL=100` (record 0041). A card's boost only goes so high (3 on many laptops' chips, per `amixer`), and amixer stops at its top. A card that names its controls differently needs `EARS_MIC_CONTROL`; `docker run --rm --device /dev/snd/controlC1 node:26-alpine sh -c "apk add --no-cache -q alsa-utils && amixer -c 1 scontrols"` lists card 1's controls from a throwaway container. That gives the container card 1's mixer, so it could change the card's levels, and nothing else of the sound devices; never give a throwaway container all of `/dev/snd`, which includes every microphone.
    - `pretend`: a quiet tone, so the rules around recording can be tried with no microphone.
    - Left out: it records nothing.
  - Then run `bash host/ears.sh mute`, which makes `ears/switch/`; ears won't start without that folder. And download Whisper's model once with `bash host/ears.sh whisper-model`, about 82 MB into `whisper/models/base-int8`: the `base-int8` model from its pinned version on Hugging Face, checked by size and, for the model itself, by its SHA-256, plus the tokenizer that model leaves out, from `openai/whisper-tiny`, which faster-whisper would otherwise fetch every time it starts. Whisper's network has no internet, so it can't fetch anything itself. Both `whisper-model` and `start` check the four files are there at their right sizes, and won't go on with part of a model.
  - Check the microphone from where you'll talk to it with `bash host/ears.sh mic-test`, or `bash host/ears.sh mic-test 10` to wait 10 seconds first (up to 60) so you can get there (record 0041). Stay quiet for the first 2 seconds, which it measures the room from, then talk as you would to Jarvis. It records 10 seconds from `EARS_SOUND_CARD`'s microphone with ears's own `EARS_MIC_LEVEL`, `EARS_MIC_CONTROL`, `EARS_MIC_BOOST` and `EARS_MIC_BOOST_CONTROL`, so it hears what Whisper and the wake word would. Then it prints the room's level and what counts as speech, in the same words and on the same scale as ears's log line for the wake word, how long you were above that, your typical and loudest level, your longest pause (ears ends a wake-word recording after 1.5 seconds of quiet, or `EARS_WAKE_PAUSE`), whether anything clipped, and the one setting to change next if it's too quiet or too loud. Turning the microphone up raises your voice and the room together, so when your voice is under six times the room's level (or, with no speech, never above three times it), more gain can't help, and it says to get closer, quieten the room or try another microphone instead. Then it plays the recording back on `JARVIS_SOUND_CARD`'s speakers at `JARVIS_VOLUME`. Change one setting at a time and run it again; ears itself uses a changed setting after `bash host/ears.sh stop` and `start`. It records in a throwaway container from ears's image (built as `home-hub-ears`) that has only that card's microphone and mixer, and plays in one from Jarvis's image that has only the speakers and mixer. The sound goes from one to the other through a pipe on the server, never a file, and neither container has a network or keeps a Docker log. It's a command you run by hand, so it has no setting to switch it on, and it refuses to run anywhere but a terminal someone is typing in. Just before it records, if ears is running, it asks ears whether it's muted (`ask.js health`, which prints the status code and one word), because only one program can have the microphone open at a time, and ears comes back muted after a restart whatever the switch file says. If ears answers anything else, it stops and asks you to mute ears first; if ears doesn't answer clearly, it stops and says to wait or to stop ears. It never mutes or stops ears itself.
  - Start them with `bash host/ears.sh start`, and stop them with `bash host/ears.sh stop`, which stops openWakeWord too. Start builds ears's image from `ears/` (from its cache after the first time; `host/hub-update.sh` doesn't rebuild it), starts Whisper (and openWakeWord, with `EARS_WAKE=on`) and waits for it to be healthy, then starts ears. Stop ends them within a second or so. With `EARS_MICROPHONE=card` it adds `docker-compose.mic.yaml`, the only place ears gets a sound device: that one card's mixer and microphone, read and write, never its speakers, and the group that owns them. Started any other way, as with `docker compose up -d ears`, ears gets no device, and with `card` it then won't start, saying how to start it.
  - Mute or unmute it with `bash host/ears.sh mute` or `bash host/ears.sh unmute`. They write `ears/switch/mute`, which ears reads every 200 ms through a read-only mount, so no container can change it through its own mounts. Ears always starts muted, even if the file says unmuted: only an unmute it sees appear after it started counts, and each one counts once. If it can't read the file when it starts, what it first reads counts as old, so unmute again once it can. Muting ends a recording within about a second (one look at the file, plus a second if the recorder has to be killed), and so does a new unmute while recording, in case a mute came and went between two looks. If a mute can't be written, as on a full disk, the script removes the file instead, which also counts as muted.
  - Try it from inside its container: `docker compose exec ears node dist/ask.js state`, or `start`, or `stop`. It prints the status code and ears's answer, and exits with 1 if ears said no. `health` prints only the status code and the state's one word: it's what ears's health check runs, because Docker keeps what a health check prints, and the state can hold the text. Its API is `GET /state`, `POST /recording/start`, `POST /recording/stop` and `POST /recording/cancel` on port 8090, with `EARS_TOKEN` as a Bearer token. Every answer includes `lastId`, the number of the last recording that ended, and a start's answer includes `id`, the new recording's number. Numbers carry on from the time ears started, in milliseconds, so a restarted ears doesn't reuse one a chat may still hold, as long as the server's clock doesn't go back. Stop and cancel can name the recording with `?id=<number>`, and then act only on that one: one that has already ended while a newer one runs is refused with 409, and one ears has moved on from is refused with 410 (record 0040). Jarvis always names his; without `?id=`, as from `ask.js`, they act on whatever ears has. Cancel ends a recording without sending it to Whisper, drops the text if Whisper is already working on it, or clears the text if it's already made. It's on its own network, `ears`, which is internal and isolated. Its container runs with Docker's own init as its first process, so ears isn't process 1 (Linux ignores a stop sent to process 1 unless the program itself handles it), a read-only filesystem, every Linux capability dropped and `no-new-privileges`, so nothing in it can gain rights it wasn't started with. Whisper and openWakeWord share the network, and Jarvis joins it only through `docker-compose.talk.yaml`, with `JARVIS_EARS=push` or `wake`.
  - It reports one state: `muted`, `idle`, `recording`, `working` or `failed`. Failed means its recorder ended by itself or couldn't start, and it records nothing until it's unmuted again. A recording stops when asked, when ears is muted, after 30 seconds, or if more sound comes than 37.5 seconds' worth (a quarter extra, for sound arriving in bursts). Ending it ends the recorder and anything it started that's still in its process group; with the wake word on, recordings share one recorder, which ends when ears is muted or no wake chat is waiting. The recorder is `arecord` for a card, giving 16-bit mono at 16,000 Hz.
  - A recording that was asked to stop, or ended at its time or sound limit, is turned into text: ears is `working` while Whisper does it, records nothing new meanwhile, and gives Whisper a minute. The answer to `stop` waits for the text, and the state's `last` holds it (`text`), or why there's none (`textProblem`). A recording ended by a mute, by a new unmute or a cancel (even one that comes while a stop is still ending it) or by its recorder failing is never sent to Whisper, and a mute or a new unmute while Whisper is working drops its text even if it comes. The sound stays in ears's memory until Whisper has it, and Whisper writes each recording to a file in its `/tmp`, which is in memory, and removes it when it's done. Memory can be moved to swap, if the server uses swap. The text stays in ears's state until the next recording ends, ears is muted or asked to cancel, or ears stops; a mute or a cancel clears it and says so. Nothing writes it anywhere.
  - `docker compose logs ears` has a line for each start, stop (why, and how long), mute, unmute, text made (how long, never the words), text not made (why), text cleared by a mute, never the sound, and never the token unless a recorder prints it when it fails. Whisper would log every transcript at its normal level, and has no setting for that, so `whisper/sitecustomize.py`, which Python loads at start because `PYTHONPATH` points at it, lifts that one logger to warnings only. Its other lines, and any errors, still show in `docker compose logs whisper`; one says how long each recording was, never what was said.
  - The wake word (record 0039). With `EARS_WAKE=on` in `ears/.env` (it needs `EARS_MICROPHONE` set), `bash host/ears.sh start` also starts openWakeWord, and ears listens for "Hey Jarvis" whenever it's unmuted and a Jarvis chat with `JARVIS_EARS=wake` is open. With no such chat, the microphone is closed. While it listens, one `arecord` runs the whole time, and every recording, `/talk`'s included, takes its sound from it, because a microphone opened directly, as ears opens it, can only be open in one program at a time. Ears passes the sound to openWakeWord, and on "Hey Jarvis" it starts a recording. The recording keeps the half second before the detection (mostly the end of "Hey Jarvis" itself, so a command said straight after it isn't clipped), measures the room from the 3 seconds before, and ends once it's been quiet for 1.5 seconds after you speak, or however long `EARS_WAKE_PAUSE` says (see below) (speech being three times the room's level, and never below 300; the first 0.8 seconds, the end of "Hey Jarvis" and the chime, don't count), or at 30 seconds. With no speech within 5 seconds it ends and is dropped without going to Whisper, which is what a false wake from the TV usually looks like; Enter in the chat before then still sends it. A chat has to take the recording within 2 seconds, or ears drops it without sending it to Whisper: that's also what happens to a wake in the few seconds after the last chat stops waiting. A detection that openWakeWord sends more than 2 seconds after the sound it's about, with no time, or with a time ahead of the sound ears has sent it (left over from before ears paused), is ignored and logged as too late to trust. Ears sends openWakeWord whole milliseconds of sound, up to a second at a time, and holds what's left for the next piece: openWakeWord times what it hears by adding up each piece's length rounded down to a millisecond (its 2.1.0 code, through the `wyoming` library), so pieces of any size made its clock fall about 2.5 ms a second behind ears's on this server, and after about 13 minutes of listening with no recording, hold or closed microphone to restart both clocks, every detection looked late and was ignored. While any chat holds it (when that Jarvis is speaking), ears passes nothing to openWakeWord and throws the sound away; each chat's hold is kept apart and runs out by itself after 15 seconds unless it's renewed, and ears starts again half a second after the last one is let go. Before opening the microphone again, ears waits for the last `arecord` to have ended, because a second one couldn't open it. `EARS_WAKE_THRESHOLD` (above 0 and below 1, default 0.5, openWakeWord's own) is how sure openWakeWord must be: raise it if the TV sets him off. `EARS_WAKE_PAUSE` (seconds, 1 to 5 to a tenth, default 1.5) is how long a pause after you've spoken ends a wake recording or a follow-up: raise it if you pause mid-question and get cut off, at the cost of every answer starting that much later. Stop and start ears to change it; its start-up line about the wake word says what it's set to, `mic-test` judges your longest pause against it, and ears's last recording says which pause it was set to end on (`pauseMs`). To turn the wake word off again, set `EARS_WAKE=off`, then stop and start ears, since `start` alone leaves a running openWakeWord as it is. If openWakeWord can't be reached, ears says why, tries again every 5 seconds, and `/talk` still works. Its API adds `GET /wait?after=<version>`, which answers with the whole state, its version and which run of ears it is, as soon as any of it changes, or after 20 seconds; `POST /wake/claim?id=<number>` to take a wake-word recording; and `POST /wake/hold?by=<id>` and `POST /wake/release?by=<id>`, where each chat names itself with its own id. The `wake` part of a `/wait` answer also has `late`: how many detections ears has ignored as too late since it started, and how far behind the last one was (`behindMs`, or null when openWakeWord gave no time, or a time ahead of the sound ears had sent it). And `POST /wake/follow?within=<milliseconds>` (1,000 to 20,000, record 0043), which starts a recording that already belongs to the chat that asked. It's judged like a wake recording, against the room's level from before the last "Hey Jarvis" and with nothing ignored at the start, and it's dropped without going to Whisper if no speech comes within that time. It's refused with 409 while any chat holds the wake word, or before ears has heard the room. `docker compose logs ears` adds a line when the microphone opens or closes (and why), for each detection (with the room's level; openWakeWord sends no score), for one that came while it wasn't listening or too late to trust, and when the wake word stops or starts working. After a wake, follow-up or talk-button recording that had speech in it, a line says how long after it began speech was first heard, how much speech there was, and the longest pause between words, from the tenths of a second it already judges for the end of the recording (never the words). `bash host/ears.sh wake-report` counts those lines into a short report: how many times it heard "Hey Jarvis", how many it ignored as late or as coming after it stopped listening, how many wake recordings started, failed to start, were taken by a chat or by none in time, and how each ended: no speech in time (a false wake, or nothing said after it), cancelled, muted or failed, turned into text, or not turned into text after all. Then the same for follow-ups, for talk-button recordings, and for other recordings (`/talk`, or `ask.js start`). It reads the whole of ears's log, which Docker keeps from when ears's container was last made (it's made again when its image or settings change, which includes the microphone's card number changing after the server restarts), dropping the oldest lines past about 100 MB (Docker's `local` log driver, set in `host/daemon.json`, keeps five files of 20 MB). `bash host/ears.sh wake-report 6` reads only the last 6 hours (1 to 720). It ends with a line each for wake recordings, follow-up windows and talk-button recordings, leaving out recordings that were cancelled, muted, failed or taken by no chat: the median time until speech was first heard (with the shortest and longest), the median amount of speech, and the median and longest pause between words. The pause that ends a recording isn't a pause between words, so the longest can only reach `EARS_WAKE_PAUSE` less a tenth of a second; if your longest often come close to that, some of your pauses are probably as long as the setting, and it may have cut you off. A wake recording's first speech can't show before 0.9 seconds, since it ignores its first 0.8. A follow-up start later than `JARVIS_FOLLOW_UP` counts as no speech in time instead, so the follow-up times can show the window is longer than you need, not that it's too short. It prints only counts and timings, never what was said.
  - The talk button (record 0045). `bash host/ears.sh talk` starts a recording as if you'd said "Hey Jarvis", for a button to run: on the server, or from another computer over SSH, like `ssh home-server "bash ~/docker/host/ears.sh talk"` from PowerShell (the script finds its own folder, so it runs from anywhere). It runs ears's own helper inside ears (`docker compose exec ears node dist/ask.js talk`), which asks ears's `POST /wake/talk` from inside ears itself, so nothing new can reach ears. A chat with `JARVIS_EARS=wake` takes the recording, chimes and shows a note, and it's judged like a wake recording: the first 0.8 seconds ignored (the chime), against the room's level from up to the last 3 seconds ears heard, as for the wake word (or the level it last measured, if it has heard less than a second since it last started listening), ending after `EARS_WAKE_PAUSE` of quiet or `EARS_WAKE_END`'s speech detector, or dropped without going to Whisper if no speech comes within 5 seconds. None of the sound from before the press is kept. It needs `EARS_WAKE=on` and a chat waiting on ears, but not openWakeWord itself, once ears has heard the room. Pressing again while its recording goes on sends it at once, like Enter on an empty line, once a chat has taken it and it has heard speech; before that, a press just says it's listening. A press is refused, with why, while ears is muted, failed or still sending the last recording, when no chat has waited on ears for 5 seconds, while Jarvis is speaking (rule R11), before ears has heard the room, during `/talk`'s own recording, or while ears is already listening after "Hey Jarvis" or for a follow-up, when you can just speak. It waits until a chat has taken the recording (up to 3 seconds) and prints one line, never what was said: that a chat has taken it and it's listening, that it's already listening, that it sent the recording (or stopped it but there was no text, and why), or why not, and exits 1 when nothing is listening or nothing was sent. When no chat takes it, ears drops it after 2 seconds and the command says so: a Jarvis chat started before this was added doesn't know the button, so start open chats again after updating. A press that got past those checks but that ears couldn't record after is logged with why. A question asked with it is logged with `button: true`, opens a follow-up like a wake question, and `npm run compare` counts it. `wake-report` counts the talk-button recordings, any that failed to start, and their speech timings; presses ears refused before starting one leave nothing in its log. Over SSH, the press reaches ears a second or two later than typing it on the server (Claude's guess; not measured), so wait for the chime.
  - Code words (records 0046 and 0049). Jarvis checks what Whisper heard against a short fixed list before Claude sees it, in his own code, so they're instant, cost nothing and give the AI no new powers. Only spoken questions count, never typed ones, and only when the code word is all you said, give or take an optional "Hey Jarvis" (or the clipped end of it Whisper sometimes writes) and a few filler words: please, oh, no, actually, thanks, okay or Jarvis before, and please, now, Jarvis, thanks, cheers, then, OK, "for now", "for a bit" or "for a while" after. Notes, the phone and train times can also be asked politely: any of "can you", "could you", "would you", "will you", "can u", "please" or "just" before them, and "for me" after, so "Can you please find my phone?" counts. "Note this" is different: it has to be the first thing you say (after an optional "Hey Jarvis" and those polite words), and anything can follow it. "Note this" (or "note this down", "make a note", "take a note", with "of this", "of that" or "of it" if you like, and "for me" after any of them), then anything: saves it in the brain's inbox through the hub (`POST /memory/inbox`, so `MEMORY_UPLOAD=on` in `api/.env` and `JARVIS_HUB_TOOLS=on` in `jarvis/.env`) as a note named like `2026-11-22-voice-note.md`, with when you said it and that Whisper wrote it, and he says "Noted." "Find my phone" on its own (or "help me find my phone", "where's my phone", "ring my phone", "ping my phone"): asks the hub to send your phone a notification (`FIND_PHONE=on`, above). "Train times" on its own (or "trains", "next train", "when's my train", "what time's my train", "is my train on time", "are the trains on time", "how are the trains looking", with "tell me", "give me", "check", "get" or "show me" before them, or "what are" or "what's" followed by "the" or "my"): the next three trains from the hub's board (`TRAINS=on`, above), with any reasons and the board's messages printed under them. "Never mind", "nevermind", "that's all" or "that is all", but not as a question ("That's all?" is asked): nothing is asked, and no follow-up window opens, so it ends a run of follow-ups. "Stop listening" on its own, with the same filler words, is ears's: it keeps no text and mutes itself, as `bash host/ears.sh mute` would, logging that it heard its code word but never the words, and Jarvis says "I've stopped listening." `bash host/ears.sh unmute` brings it back; a muted ears can't hear "start listening". A request to stop listening that ears didn't take ("can you stop listening?", "stop listening for a minute") isn't asked, so Claude can't answer it and no follow-up opens: Jarvis tells you to say just that. A question that only mentions it ("should I stop listening to podcasts?") goes to Claude. A code word isn't logged with the answers, since Claude isn't asked. If Whisper mishears one, or you ask any other way, it goes to Claude as a question like any other: "Can you find my phone number?", "Where's my phone charger?" and "What are trains?" all do.
  - openWakeWord is `rhasspy/wyoming-openwakeword` 2.1.0, pinned by digest, in the `wake` profile, with its "hey jarvis" model inside the image. The model's licence is non-commercial (CC BY-NC-SA 4.0), so it's never in this repo. It runs as user 10400, which has no account on the server, with Docker's own init, a tmpfs `/tmp`, a 256 MB memory limit, no port and no device, and `openwakeword/health.py` mounted read-only as its health check, which asks it to describe itself and passes only if it has `hey_jarvis`. It logs only that it's ready, never what it hears.
  - Silero's speech detector (record 0042). A wake recording ends once it's been quiet for 1.5 seconds (or `EARS_WAKE_PAUSE`) after you speak, and by default "quiet" means quieter than three times the room. A fan, music or the kettle can be loud enough to keep it going, and a quiet voice can drop under the line. With `EARS_WAKE_END=silero` in `ears/.env` (the default is `loudness`), quiet means Silero's speech detector heard no speech instead. It judges each tenth of a second in pieces of 32 ms and counts a tenth as speech when any piece has a chance of 0.5 or more. It's speech it hears, not you: people talking on the TV still count. Everything else about the ending (the first 0.8 seconds ignored, the 1.5 seconds or `EARS_WAKE_PAUSE`, 5 seconds, 30 seconds) stays the same. Ears loads the detector when it starts, only with `EARS_WAKE=on` and `EARS_WAKE_END=silero`, and won't start if it can't; then set it back to `loudness`. If it fails during a recording, or falls more than a second behind, ears logs it once and that recording ends on loudness, with loudness's wording for why. Stop and start ears to change it. It runs inside ears, on one CPU thread, at about a millisecond per tenth of a second of sound in tests on the machine this was built on (the server's CPU wasn't measured), and about 25 MB more of ears's memory while it's loaded (59 MiB against 36 MiB in a rehearsal). Ears's image is now built on `node:26-trixie-slim` (Debian), because onnxruntime's ready-made Linux files need the C library Debian has and Alpine doesn't. `alsa-utils` comes from Debian. The image has `onnxruntime-node` (Microsoft, MIT licence; its install step's fetch of NVIDIA CUDA files is switched off in `ears/.npmrc`, and the image keeps only this machine's files). Microsoft's builds of it send usage telemetry over HTTPS unless `ORT_DISABLE_TELEMETRY=1` is set before it loads (its own privacy notice says so), so ears sets that in its image and in its code, and ears's network has no internet anyway. It also has Silero's model, `silero_vad.onnx` (v6.2.3, MIT licence, 2.3 MB), which the build downloads from a fixed commit on GitHub and checks by size and SHA-256, so building ears needs GitHub and npm. The model is never in this repo. Check it on the server with `docker compose run --rm --no-deps ears node dist/silero-check-run.js`: it plays it a second each of silence, noise and a steady tone, prints each one's highest chance of being speech, and fails if any reaches 0.5. `bash host/ears.sh mic-test` also shows what the detector heard when `EARS_WAKE_END=silero`, beside the loudness check, half a second to a mark. The first `npm ci` in `ears/` downloads onnxruntime-node, about 115 MB, and unpacks about 300 MB, all platforms' files; the tests don't load it, so they still run in `node:26-alpine`.
  - Whisper is `rhasspy/wyoming-whisper` 3.8.1, pinned by digest, with the `base-int8` model in English. It runs as user 10300, which has no account on the server, so it isn't root and owns none of my files, with its model folder and that one file mounted read-only, no port and no device, and `HF_HUB_OFFLINE=1` so Hugging Face's library never tries the network. Docker's own init (`init: true`) is its first process, because its image starts it from a bash script that wouldn't pass a stop on, so it would be killed after 10 seconds. Its memory limit is 1 GiB: it used 456 MiB after one recording on 20 Nov, and 479 MiB after a longer one on 21 Nov. If it ever needs more, Docker stops it, and ears says it can't reach Whisper until it's started again with `bash host/ears.sh start`; then raise the limit.

## Tests
Node isn't installed on the server, so npm runs in a throwaway container. From this folder:
```
docker run --rm -u node -v "$PWD/api:/app" -w /app node:26-alpine npm ci
docker run --rm -u node -v "$PWD/api:/app" -w /app node:26-alpine npm test
```
For the MCP server, use `$PWD/mcp` instead, for Jarvis `$PWD/jarvis`, and for ears `$PWD/ears`. An `.npmrc` in each of `api/`, `mcp/`, `jarvis/` and `ears/` turns off npm's notice that a newer npm exists, which each throwaway container would otherwise print after the results. Their npm is the one in the `node:26-alpine` image, so a newer one comes with a newer image. GitHub runs all four test suites, and Jarvis's engine check, on every push, alongside a secret scan of the whole history. The update script has its own tests, which use a pretend `docker` and throwaway git repos, so they change nothing. GitHub doesn't run them, so run them by hand after changing the script: `bash host/hub-update.test.sh`. Likewise `bash host/jarvis.test.sh` for `host/jarvis.sh`, with a pretend `docker` and pretend sound devices, `bash host/ears.test.sh` for `host/ears.sh` and the ears service's compose settings, and `bash host/ebay-check.test.sh` for `host/ebay-check.sh`, with a pretend `curl`, so it never contacts eBay.
