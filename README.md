# Home Hub

Home Hub is my server, to do what I want with, and to have futuristic things built on it that can help me do what I want: a cool program that knows stuff and can help me out.

## Why I built it
I built it to learn, to help me do more coding stuff, and because it was cool as shit.

## How I built it
I built it using my own ideas, with AI helping me plan and learn what I needed to do to make it. I made all the decisions and made each commit myself.

## How the parts fit
- Everything runs on one Ubuntu server, from one compose file: `docker-compose.yaml`.
- Caddy is the front door. Each service has a `.home` name, and AdGuard Home answers DNS on the home network, which is how those names reach Caddy.
- `hub.home` and `api.home` also answer over HTTPS, using Caddy's own certificate authority. Only devices that have installed Caddy's root certificate trust it, so plain HTTP still works everywhere.
- Nothing is open to the internet. Away from home, everything goes through Tailscale.
- The API (`api/`) is the centre: one module per capability, and every route except logging in needs a token. It reads from qBittorrent and Jellyfin, watches the server's Wi-Fi reconnect log, and can count and add notes in the brain's inbox.
- Every 5 minutes the API checks for problems (low disk or memory, Wi-Fi reconnects, a failed backup) and sends any change to my phone through ntfy. It also pings Healthchecks.io, which tells me if the server goes quiet, and sends a daily summary at 08:00.
- The phone page (`hub/`, at `hub.home`) is plain JavaScript served by Caddy, which passes `/api/*` on to the API.
- Claude Code reaches the API through an MCP server (`mcp/`), a throwaway container started for each session. Its tools read from the API; the three that change things (start a library scan, stop or start a download) always ask first.
- The brain is a separate private repo of notes, `hub-memory`. Its `inbox/` folder is mounted into the API.
- Anything that runs outside Docker lives in `host/`. The main ones are the Wi-Fi watchdog, a systemd timer that reconnects the Wi-Fi when the router stops answering, and the backup.
- Backups use restic. `host/backup.sh` backs up this folder, the brain and Claude Code's settings, stopping the apps that keep databases while it copies them. A systemd timer runs it every night at 03:30, but it stays off until there's a backup drive. Each run's result shows on the phone page, in the daily summary and at `GET /system/backup`, and can ping its own Healthchecks.io check. `docs/restore.md` explains how to get files back.

## Switches
New features are built switched off. Each switch is a line in `api/.env` set to exactly `on` or `off`. Anything else, or a missing switch, stops the API starting, so a typo can't quietly change what's on. `GET /system/features`, the phone page and the daily summary all show what's off. The MCP server has one switch of its own, `MCP_ACTIONS`, which `bash host/hub-mcp.sh read-only` turns off. Jobs that run on the server itself, like the nightly backup, are switched on and off by enabling or disabling their systemd timer.

### The deal watcher's settings
`DEALS` switches it on. While it's on, `api/.env` also needs `DEALS_SEEN` (`memory` or `disk`), `EBAY_ENVIRONMENT` (`production` or `sandbox`), `EBAY_CLIENT_ID`, `EBAY_CLIENT_SECRET` and `DEALS_AI` (`on` or `off`: whether Claude's tools may read the listings). Each search has its own `switch` in `deals/searches.json`. `docs/deals.md` has the rest.

### Jarvis's settings
Lines in `jarvis/.env`. Jarvis prints the `JARVIS_` ones in one line when he starts.
- `ANTHROPIC_API_KEY`: required.
- `JARVIS_LOG`: `on` or `off`, required, like the API's switches. Logs each answer's numbers, never its words, for `npm run compare`.
- `JARVIS_ENGINE`: `sdk` (default) or `api`.
- `JARVIS_THINKING_HISTORY`: `keep` (default) or `drop`. Only the plain API engine uses it.
- `JARVIS_LENGTH_HINTS`: `note` (default) prints the chat-length note below; `jarvis` gives Jarvis the chat's size with each question once it's long, and leaves the suggestion to him. The log records which, so `npm run compare` can show how big chats got before you typed `new`. The size lines stay in a saved chat, so type `new` before switching this setting on a saved chat, or its answers mix the two.
- `JARVIS_LENGTH_WARN`: the chat size, in tokens, where the length warning starts. Default `80000`, 80% of Haiku 5.5's long-prompt line. Set it lower to hear sooner, or to suit another model.
- `JARVIS_LENGTH_CAP`: `off` (default), or a number of tokens above the warning. Once a chat's last request passes it, Jarvis says so, won't send more questions in that chat, and says to type `new`. A guard against long chats quietly costing more. A saved chat's size is kept with it, so the cap still holds after a restart: in the chat file on the plain API engine, and on the Agent SDK in `jarvis/data/chats/agent-sdk-size.json`, which only counts while the transcript it names is still the newest.
- `JARVIS_HUB_TOOLS`: `off` (default) or `on`. On gives Jarvis the hub's read-only tools (status, alerts, switches, downloads, library, Wi-Fi reconnects and backup), through the MCP server in `mcp/`, which he starts inside his own container in read-only mode (unless `JARVIS_HUB_ACTIONS` is on), as one more Node process (about 60 MB) while he runs. Both engines use them. The log records whether he was given them, so `npm run compare` keeps answers with and without the tools apart; on the Agent SDK, a chat whose MCP server didn't start still counts as with. If the MCP server doesn't start or list its tools, Jarvis says so (the plain API engine as he starts, the Agent SDK with his first answer) and carries on with the brain only; the note doesn't say why, and running `npm test` for `mcp/` is the first thing to try. On needs two things, and he won't start without either:
  - Start Jarvis with `bash host/jarvis.sh`, which passes in only `API_TOKEN` from `api/.env`.
  - The MCP server built in `mcp/`, which Jarvis runs from `mcp/dist`: `npm ci`, then `npm test`, as under Tests below. After `mcp/` changes, run `npm ci` and `npm test` for it again, or Jarvis keeps using the old build. `host/hub-update.sh` does both when a pull changes `mcp/`. If the tests fail, `mcp/dist` already holds the new build, because `npm test` builds before it tests, so fix it before you next start Jarvis.
- `JARVIS_HUB_ACTIONS`: `off` (default) or `on`, and only with `JARVIS_HUB_TOOLS=on`. On lets Jarvis use the hub's three actions: scanning the library, and stopping or starting a download. Before each one, his own code (not his instructions) asks you in the chat what he wants to do, and waits for you to type `yes`, in any case. Anything else (even `exit`, which you'd then type again to leave) or no answer within 60 seconds means it isn't done, and he's told so. Ctrl+C closes Jarvis, so nothing runs. Only what you type after the question counts: in a terminal, anything half-typed before it is cleared. Two actions are asked one after the other. The log records whether this was on, so `npm run compare` keeps those answers apart.
  - The wait doesn't count towards the question's 2-minute limit, but it does show in that answer's time.
  - Jarvis takes only the hub tools he knows by name (the seven read tools, plus these three when this is on). A tool added to the MCP server later is left out on the plain engine until Jarvis is updated too; the Agent SDK still offers it to the model, but refuses it if he tries.
  - Before stopping or starting a download with a full hash, his code asks the API for it (`GET /media/downloads/<hash>`) and shows the start of its hash, how far it got and its name, so you're not relying on what Jarvis says. If the hub doesn't have that hash, the question says so. If the lookup fails or takes over 5 seconds, the question says the name couldn't be looked up. A hash that isn't 40 lower-case hex characters isn't looked up, and the question says so. Names come last, on one line, with hidden characters taken out, control characters shown as `�`, double quotes and look-alikes changed to `'`, and cut at 80 characters. Text he reads, such as a torrent name or, with `JARVIS_SESSION_NOTES` on, the sessions' notes, could still carry instructions aimed at him; records 0011 and 0012 have more.
- `JARVIS_SESSION_NOTES`: `off` (default) or `on`. On gives Jarvis the notes your two Claude Code sessions keep for themselves (the `MEMORY.md` in each one's auto memory, for `~/docker` and `~/hub-memory`), added to his instructions when he starts, so he can tell you what you've been working on. He keeps the first 200 lines or 25,000 characters of each, the limits in Claude Code's docs (which say 25KB), cut back to the end of a line, with hidden characters such as zero-width spaces taken out. If both are full, that's something like 12,000 to 17,000 tokens more in every request (Claude's estimate), which the cache makes cheaper while you keep asking within 5 minutes of the last question. He says at start-up how many lines he found for each session. The log records whether he had any.
  - Start him with `bash host/jarvis.sh`, which mounts each session's whole memory folder read-only at `/notes`, whatever this setting says. Only `MEMORY.md` is read, and none of his tools can read outside the brain. The script also needs `API_TOKEN` in `api/.env` and passes it in, though he doesn't use it unless the hub's tools are on.
  - The script finds the folders the way the bundled Claude Code named them in a test (the docs only say the folder comes from the git repo): the repo's full path with every character other than letters and digits turned into `-`, under `~/.claude/projects`, or under `$CLAUDE_CONFIG_DIR/projects` if that's set, which the memory docs don't mention. It doesn't know about Claude Code's `autoMemoryDirectory` setting, so if you set that, he finds none. `ls -d ~/.claude/projects/*/memory` shows what's there.
- `JARVIS_VOICE`: `off` (default) or `kokoro`, written plainly on a line of its own. With `kokoro`, Jarvis has a voice, made by [Kokoro](https://github.com/remsky/Kokoro-FastAPI), a speech engine that runs in its own container (the `kokoro` service). He says one sentence out loud when he starts ("Jarvis is ready when you are."), then speaks his answers, a sentence at a time, while they're still being written. Start him with `bash host/jarvis.sh`, which then builds his image for sound, passes in the card named by `JARVIS_SOUND_CARD`, starts Kokoro and waits up to 2 minutes for it to be ready, and stops it again when the chat ends. If `JARVIS_SOUND_CARD` is missing or wrong, or the image won't build, the script stops there and says why. As he starts, he sets `JARVIS_VOLUME`, checks that Kokoro answers, says the sentence and prints a `Voice:` line. If any of that fails, or the sentence takes more than 45 seconds, the line says his voice is off and why, and the chat carries on in text. The one exception is a microphone device in his container, which stops him starting at all. The log records whether he had a voice, so `npm run compare` keeps those answers apart.
  - Kokoro used about 1.2 GiB of memory when it was measured on this server, and has a 2 GiB limit. It has no published port and sits on a Docker network of its own, `speech`, which has no route to the internet or the LAN and which only Jarvis joins. The server has no address on that network either, so Kokoro can't reach the server's own services, such as SSH (record 0024). If Kokoro is already running when the script starts, because you started it yourself (`docker compose up -d --wait kokoro`) or another chat did, the script says so, leaves that container exactly as it is, and doesn't stop it afterwards. Whoever started it stops it: the other chat's script when that chat ends, or you with `docker compose stop kokoro`.
  - Started with plain `docker compose run --rm jarvis`, he has no sound devices, so he says his voice is off.
  - What he speaks is the answer's own words, tidied for the ear: the marks for headings, lists, bold and code are left out, and code blocks, emoji and most file paths and web addresses are skipped. With `JARVIS_SPOKEN_STYLE=on`, anything in code marks is skipped too, found the way Markdown finds it within a line, so a stray backtick pairs with the next one; code marks left open, or code that runs over a line or past 400 characters, are still read out. A word counts as a path if it has a backslash in it, or a slash and one of these: it starts like a path (`/`, `~/`, `./`, `../`), ends in a slash or a file ending, starts with a site's name, has `://` in it, or is written whole in code marks. A table row is read as a list, and a list's number is read with a pause after it. The tool notes, the timing and cost lines and the yes-or-no question before a hub action aren't spoken, but what he said before one of them is spoken while it happens. If the engine starts an answer again, he starts speaking it again from the top. The screen shows exactly what it would without a voice, though `JARVIS_SPOKEN_STYLE` changes how he writes.
  - The prompt comes back as soon as the words are done, and he carries on speaking behind it. `new`, `exit` and Ctrl+C stop the sound at once. A new question, or Enter on an empty line, interrupts him the way `JARVIS_SPEECH_STOP` says, and a note says so: `(stopped talking)`, `(the last answer won't be spoken)` if he hadn't started, or `(stopping after this sentence)`; if he's already on the last sentence nothing is cut, so there's no note. An empty line typed before the prompt is back is ignored, so an Enter pressed while you wait doesn't hush him before he's said anything; a question typed then is still asked once the prompt is back (record 0025). Until the prompt is back, which can be a while when he's using tools, only Ctrl+C stops the sound, and that ends the chat. At a hub action's yes-or-no question, an empty line still means no.
  - Each sentence is one request to Kokoro and is played by an `aplay` of its own. Kokoro is asked for one sentence at a time and gets at most two ahead of what's playing. With `JARVIS_SPEECH_BUNDLE=on`, below, one request can hold several sentences, and what this paragraph says of a sentence's sound (skipped if it can't be made or played, two in a row, the time it gets to play) applies to that whole piece; the 40-sentence limit and the log still count sentences. Only the first 40 sentences of an answer are spoken. A sentence that can't be made or played is skipped. Two in a row that can't be made, or two in a row that can't be played, end the speech for that answer. Either way a note says so before the next answer, or when the chat ends (record 0023). The exception is a sentence he's finishing after being interrupted with `JARVIS_SPEECH_STOP=sentence`: if it can't be played, that's only counted in the log. A sentence gets twice its own length plus 10 seconds to play; a player still going after that is stopped, and the sentence counts as one that couldn't be played. A player that's stopped is asked to end first, and killed outright if it hasn't ended 2 seconds later, so a stuck one can't keep the chat from closing.
  - With `JARVIS_LOG=on`, each answer given with his voice on gets a second line in the log when its speech is over: how long after the question the first sentence was sent to Kokoro, its sound came back and the first sound that played reached the player, the longest silence between two sentences (from one sentence's player finishing to the next sound reaching the player, so it leaves out `aplay` starting up and any quiet inside a sound, and it's empty when fewer than two sentences played; with `JARVIS_SPEECH_BUNDLE=on` it's between pieces, since sentences in one piece share one sound), how many sentences were spoken, failed (split into those that couldn't be made and those that couldn't be played) or left, how many requests Kokoro got and how many sentences went in them, and whether the speech was stopped early, given up on or cut at 40 sentences. Never the words, and never the error a sentence failed with (record 0032). `npm run compare` shows the time to first sound and the longest silence, with the first question of each chat kept apart from later ones because Claude is slower on it. Kokoro is already warm by then, from the start-up sentence. A second table adds up, for each setting, the sentences played to the end, failed and not played in full, and the answers that made no sound, were stopped, were given up on or went over 40 sentences. Under it, each setting where sentences failed gets a line saying how many couldn't be made and how many couldn't be played. Log lines from before that split don't say which, so that setting's line counts them separately. Then a line for each setting says how many sentences Kokoro was asked for in how many requests, and how many that is a request on average, which shows whether `JARVIS_SPEECH_BUNDLE` is really bundling; older log lines don't have it and are left out of it.
  - Kokoro is set to log errors only (`API_LOG_LEVEL` on the `kokoro` service). Left to itself it writes the first 50 characters of every piece of text it's asked to speak into its log, which Docker keeps; that's from its v0.10.0 code and docs, read and not yet seen on this server. A Kokoro that was already running when the setting changed keeps its old one. Stop it with `docker compose stop kokoro`, and the next `bash host/jarvis.sh` makes a new container with the new setting.
- `JARVIS_KOKORO_VOICE`: which of Kokoro's voices he speaks in, default `bm_george`. It takes any of Kokoro's voice names (`bm_fable`, `bm_lewis` and `bm_daniel` are other British male ones), or a blend like `bm_george(2)+bm_fable(1)`. Kokoro checks the name itself, so a wrong one shows in the `Voice:` line.
- `JARVIS_KOKORO_SPEED`: how fast Kokoro speaks, default `1`, its usual pace. Any number from `0.25` to `4`, like `0.9` for a little slower. It's sent with every piece of speech, the start-up sentence included, and it isn't in the log, like the voice.
- `JARVIS_SPEECH_START`: `sentence` (default) or `clause`. With `sentence`, the first thing he says is the answer's whole first sentence. It's sent to Kokoro once the next sentence has begun, or a line ends, a tool starts or the answer ends. With `clause`, the first piece can end at the first comma, semicolon, colon or dash that has at least 20 spoken characters before it, so he starts sooner at the cost of a pause there. Only the first piece of an answer is cut that way, and the first piece after each tool he uses. The log records which, so `npm run compare` shows the time to first sound for each. It's checked every time he starts, voice or not.
- `JARVIS_SPEECH_STOP`: `now` (default) or `sentence`: what a new question or an empty line does while he's talking. With `now`, he stops at once, mid-word if need be. With `sentence`, he finishes the sentence he's on (with `JARVIS_SPEECH_BUNDLE=on`, the piece he's on, which can be several sentences) and says nothing after it; a new question is still sent straight away, and its answer's first sound waits until that sentence is over. Either way `new`, `exit` and Ctrl+C stop him at once. The log records which, so `npm run compare` shows each setting's times side by side. It's checked every time he starts, voice or not.
- `JARVIS_SPEECH_BUNDLE`: `off` (default) or `on`. With `on`, an answer's first piece (its first sentence, or its first clause with `JARVIS_SPEECH_START=clause`) still goes to Kokoro on its own, so its first sound comes as soon as before. After that, whenever Kokoro is free, the sentences already waiting go to it together. A sentence is only joined onto one that ends with a full stop, question or exclamation mark or ellipsis, so a list item or a line ending in a colon isn't run into what follows. A piece is no longer than twice the last piece Kokoro made, or 250 characters, whichever is smaller. Nothing is held back to wait for more. Kokoro's notes on its voices say they're weakest on very short pieces and suggest bundling them (https://huggingface.co/hexgrad/Kokoro-82M/blob/main/VOICES.md). Each piece is played by one `aplay`, so with `JARVIS_SPEECH_STOP=sentence` he finishes the whole piece he's on, which can be several sentences. The log records which, so `npm run compare` shows the times for each. It's checked every time he starts, voice or not (record 0033).
- `JARVIS_SPOKEN_STYLE`: `off` (default) or `on`. With `on` and his voice on, his instructions gain a paragraph asking him to write for the ear: lead with the answer, keep sentences short with the first one shortest, write numbers and units as they're said, leave out headings, tables and bold, use a list only when the order matters, and put file paths, commands, settings, web addresses and code in code marks without needing them to make sense of a sentence. What's in code marks is shown on screen but not spoken, with the exceptions above. It changes what's written too, since there's one answer for both. With his voice off, or if it can't start, his instructions are as they were. The log records which, so `npm run compare` shows the times for each. It's checked every time he starts, voice or not (record 0031).
- `JARVIS_SOUND_CARD`: the speakers' name under `/dev/snd/by-path`, like `pci-0000:04:00.6`. `ls -l /dev/snd/by-path` lists the names and the card each leads to, and `cat /proc/asound/cards` says which card is which. `bash host/jarvis.sh` reads it, for the sound test and for a chat with `JARVIS_VOICE=kokoro`: it follows the name to the card's number for this boot, and passes in only that card's mixer and speakers. Names stay the same after a restart; card numbers might not, and both cards on this server are called `Generic`, so their `CARD=` names can swap too. Set it again on a new server. Only the script reads it, so it isn't on his start-up line; his `Voice:` line names the card it led to.
- `JARVIS_VOLUME`: `0` to `100`, default `80`. Before anything plays, Jarvis sets the card's `Master` control to this and unmutes it (`0` mutes it), because the server forgets the level when it restarts and comes back muted (record 0015). The sound test does this, and so does the chat with `JARVIS_VOICE=kokoro`. It's checked every time he starts, voice or not.
- `JARVIS_CHATS`: `fresh` (default) saves nothing; `resume` saves the chat in `jarvis/data/chats/` and picks it up next time.
  - Saved chats hold everything said, brain text included. Only their owner can read them, and backups copy them.
  - Every question sends the whole saved chat. On Haiku 5.5, a request over 100,000 tokens costs five times as much. Jarvis doesn't trim saved chats yet. The Agent SDK only summarises a chat when it nears its context limit (about 990,000 tokens in a test), so it pays the higher rate long before that.
  - When a chat reaches `JARVIS_LENGTH_WARN` (80,000 tokens unless set), Jarvis says once that it's getting long (once per start of Jarvis). Past 100,000, where Haiku 5.5's long-prompt price starts, he says so after every answer, with how to start a new one (unless `JARVIS_LENGTH_WARN` is set higher, when he waits for that). It goes by each answer's last request, and works in fresh chats too. With `JARVIS_LENGTH_HINTS=jarvis`, Jarvis is told the size instead and suggests a new chat himself.
  - Type `new` to start a new chat without leaving Jarvis. In a saved chat, the old one is moved to `jarvis/data/chats/old/` (private, the newest 10 per engine kept), Jarvis says exactly where, and it isn't carried on. To get it back, move it back by hand. A plain API chat brings its size back with it (if it was saved since sizes were kept); an Agent SDK one usually has no size known until its first answer. A leftover `*.saving` file is a save that was cut off, and is safe to delete.
  - Lines shaped like a command (a `/` then one word, like `/clear`) aren't sent to Jarvis, on either engine. The Agent SDK would otherwise run them as its own commands; `new` does that job on both. Paths like `/etc/hosts` go through as normal.
  - Run one Jarvis at a time on a saved chat: with two, one of them's questions won't be carried on.
  - The engines save differently: the Agent SDK also keeps questions that failed or were stopped, and the plain API engine keeps only answered ones. On the plain API engine, thinking is left out of the saved chat for good with `JARVIS_THINKING_HISTORY=drop`, or after a thinking restart.

## Folders
- `api/`: the API. Fastify and TypeScript on Node 26, one module per folder in `src/modules/`, with each module's tests beside its code.
- `hub/`: the phone page.
- `mcp/`: the MCP server for Claude Code. Same setup as `api/`.
- `jarvis/`: Jarvis, a text chat that reads the brain, with two engines to compare: the Agent SDK and a plain API call. With `JARVIS_VOICE=kokoro` he also has a voice: one sentence when he starts, then his answers, a sentence at a time. Its settings live in `jarvis/.env` (below), and `jarvis/data/` (git-ignored) holds the answer log and any saved chats. `jarvis/Dockerfile` is his image for sound.
- `host/`: files that run outside Docker (the Wi-Fi watchdog, and the backup script with its service and timer), plus helper scripts: `hub-update.sh` pulls and rebuilds only what changed, `hub-mcp.sh` starts the MCP server, `jarvis.sh` starts Jarvis with the API token for the hub's tools and the sessions' notes (and, with `JARVIS_VOICE=kokoro`, with his speakers, starting and stopping Kokoro around the chat), or runs his sound test, and `hub-get.sh` and `hub-post.sh` try an API route, and `ebay-check.sh` tests the eBay keys without showing them.
- `deals/`: the deal watcher's search list and state file, both git-ignored. Only its `README.md` is tracked.
- `caddy/`: the Caddyfile.
- `homepage/config/`: Homepage's settings. Logins and keys come from `homepage/.env`.
- `docs/`: `restore.md` (getting files back from a backup), `going-private.md` (what to do if this repo goes private), `deals.md` (setting up and using the deal watcher) and `decisions/` (why things are the way they are, one record per decision).
- `.github/`: tests and safety checks on every push, and Dependabot.
- `CLAUDE.md`, `.mcp.json` and `.claude/settings.json`: how Claude Code works in this repo.

## Running it
Secrets live in `.env` files that git ignores (`api/.env`, `homepage/.env`, `beszel/.env` and `jarvis/.env`), so they're never in this repo. The API also expects the brain's inbox at `../hub-memory/inbox`, and won't start without it. The backup's settings and password live in `/etc/home-hub/`, outside this folder and readable only by root.
- Start everything: `docker compose up -d`
- Rebuild the API after a change: `docker compose up --build --wait api`
- Pull from GitHub and rebuild only what changed: `bash host/hub-update.sh`, or `bash host/hub-update.sh --dry-run` to see what it would do. When `mcp/` changes, it also rebuilds the copy Jarvis runs. When Jarvis's packages change (`jarvis/package-lock.json`), it reinstalls them and runs his engine check, since a new Agent SDK brings a new engine. A change to his code alone needs nothing, because he builds himself each time he starts. Close Jarvis before updating: reinstalling packages replaces folders a running chat is using.
- Talk to Jarvis: `docker compose run --rm jarvis`. He's in the `jarvis` profile, so `docker compose up` never starts him. Type `exit` or press Ctrl+C to stop, and `--rm` removes the container. He needs `jarvis/.env` and the brain at `../hub-memory` (mounted read-only), and won't start without them. With `JARVIS_HUB_TOOLS=on`, `JARVIS_SESSION_NOTES=on` or `JARVIS_VOICE=kokoro`, start him with `bash host/jarvis.sh` instead. He's on his own Docker network, `jarvis`, which only the API shares, so the API is the one container he can reach directly (when `host/jarvis.sh` gives him sound, for a chat with his voice on or for the sound test, he's also on `speech`, where he reaches Kokoro). Services with a published port or a `.home` name can still be reached through the server's address, as from any device on the LAN, and he can reach the internet, which he needs for Anthropic's API (record 0013).
- Test Jarvis's speakers: `bash host/jarvis.sh sound-test`. It builds his image for sound, `home-hub-jarvis` (`jarvis/Dockerfile`: his usual `node:26-alpine` plus `alsa-utils`, from its cache after the first time), finds the card named by `JARVIS_SOUND_CARD`, sets `JARVIS_VOLUME`, and plays two short beeps, low then high. It adds `docker-compose.sound.yaml`, the only place Jarvis gets sound devices: his card's mixer and speakers, read and write, never a microphone, and the group that owns them (record 0014). The same file puts him on the `speech` network, where Kokoro is when it's running; the sound test doesn't use it. Without it, as with `docker compose run --rm jarvis`, he gets none and runs on the stock image. A newer `node:26-alpine` reaches his image only after `docker pull node:26-alpine`.

## Tests
Node isn't installed on the server, so npm runs in a throwaway container. From this folder:
```
docker run --rm -u node -v "$PWD/api:/app" -w /app node:26-alpine npm ci
docker run --rm -u node -v "$PWD/api:/app" -w /app node:26-alpine npm test
```
For the MCP server, use `$PWD/mcp` instead, and for Jarvis `$PWD/jarvis`. An `.npmrc` in each of `api/`, `mcp/` and `jarvis/` turns off npm's notice that a newer npm exists, which each throwaway container would otherwise print after the results. Their npm is the one in the `node:26-alpine` image, so a newer one comes with a newer image. GitHub runs all three test suites, and Jarvis's engine check, on every push, alongside a secret scan of the whole history. The update script has its own tests, which use a pretend `docker` and throwaway git repos, so they change nothing. GitHub doesn't run them, so run them by hand after changing the script: `bash host/hub-update.test.sh`. Likewise `bash host/jarvis.test.sh` for `host/jarvis.sh`, with a pretend `docker` and pretend sound devices, and `bash host/ebay-check.test.sh` for `host/ebay-check.sh`, with a pretend `curl`, so it never contacts eBay.
