# Home Hub

Home Hub is my server, to do what I want with, and to have futuristic things built on it that can help me do what I want: a cool program that knows stuff and can help me out.

## Why I built it
I built it to learn, to help me do more coding stuff, and because it was cool as shit.

## How I built it
I built it using my own ideas, with AI helping me plan and learn what I needed to do to make it. I made all the decisions and made each commit myself.

## How the parts fit
- Everything runs on one Ubuntu server, from one compose file: `docker-compose.yaml`.
- Caddy is the front door. Each service has a `.home` name, and AdGuard Home answers DNS on the home network, which is how those names reach Caddy.
- `hub.home` and `api.home` also answer over HTTPS, using Caddy's own certificate authority. Only devices that have installed Caddy's root certificate trust it, so plain HTTP still works everywhere.
- Nothing is open to the internet. Away from home, everything goes through Tailscale.
- The API (`api/`) is the centre: one module per capability, and every route except logging in needs a token. It reads from qBittorrent and Jellyfin, watches the server's Wi-Fi reconnect log, can count and add notes in the brain's inbox, and with catch-up on, reads recent commits from GitHub.
- Every 5 minutes the API checks for problems (low disk or memory, Wi-Fi reconnects, a failed backup) and sends any change to my phone through ntfy. It also pings Healthchecks.io, which tells me if the server goes quiet, and sends a daily summary at 08:00.
- The phone page (`hub/`, at `hub.home`) is plain JavaScript served by Caddy, which passes `/api/*` on to the API.
- Claude Code reaches the API through an MCP server (`mcp/`), a throwaway container started for each session. Its tools read from the API; the ones that change things (start a library scan, stop or start a download, add or cancel a watcher, run a dev chore, set, cancel or snooze a reminder, and Spotify's controls) always ask first.
- The brain is a separate private repo of notes, `hub-memory`. Its `inbox/` folder is mounted into the API.
- Anything that runs outside Docker lives in `host/`. The main ones are the Wi-Fi watchdog, a systemd timer that reconnects the Wi-Fi when the router stops answering, and the backup.
- Backups use restic. `host/backup.sh` backs up this folder, the brain and Claude Code's settings, stopping the apps that keep databases while it copies them. A systemd timer runs it every night at 03:30, but it stays off until there's a backup drive. Each run's result shows on the phone page, in the daily summary and at `GET /system/backup`, and can ping its own Healthchecks.io check. `docs/restore.md` explains how to get files back.

## The hub page on the phone
`hub.home` can be installed on the phone as an app (record 0077): it has a web app manifest (`hub/manifest.webmanifest`) and icons, and opens full screen on its own. Browsers only install, and only give a page the microphone, over https, so use `https://hub.home`, which Caddy serves with a certificate from its own certificate authority (`tls internal`). A phone only trusts that once Caddy's root certificate is installed on it:
- Copy the root certificate where the hub page can serve it: `sudo cp caddy/data/caddy/pki/authorities/local/root.crt hub/caddy-root.crt` (the caddy image keeps its data in `/data`, which is `caddy/data` here, and only root can read it), then `sudo chown "$USER": hub/caddy-root.crt`. Git ignores `hub/caddy-root.crt`. It's the public half only; the private key stays where it is.
- On the phone, open `http://hub.home/caddy-root.crt` to download it, then install it as a CA certificate. That address is the only thing `hub.home` still serves over plain http: everything else there is sent on to `https://hub.home` (record 0083). On Android that's in Settings, under Security, Encryption and credentials, Install a certificate, CA certificate (the names vary a little by phone). Chrome on Android trusts certificates installed there; many other apps don't, which doesn't matter here.
- Check it's the right certificate, since it came over plain http, where anyone else on the Wi-Fi could have swapped it: on the server, `openssl x509 -in hub/caddy-root.crt -noout -fingerprint -sha256` prints its SHA-256 fingerprint (public, not a secret), and on the phone, tapping the certificate under User credentials should show the installed one's (the names vary by phone, and some may not show it). If they don't match, remove it from the phone and download it again.
- Open `https://hub.home` in Chrome, log in, and choose Install app (or Add to home screen) from its menu.

`https://hub.home` is sent with security headers (record 0084): a content security policy that lets the page use only its own files, with no code or styles written inside it, plus no showing inside another site's frame and no referrer. Anything added to the phone page or the wall has to fit that; `bash host/caddyfile.test.sh` checks it.

With `LOGIN_GUARD=on` in `api/.env` (record 0083), the login cookie is always https-only, a login over plain http is refused with a line saying to use `https://hub.home`, and after 10 wrong tokens in a minute every login is refused, the right one too, until the oldest of them is a minute old. That pause is for every device at once, so someone sending wrong tokens can hold up a new login, never one that's already in. Logs hold the count, never a token. With it off, logins work as before.

Installing your own certificate authority on a phone means anything signed with that authority's key is trusted by the phone, for any website, not only `.home` ones. Caddy's key is in `caddy/data` on the server, written there by Caddy as root, and in the backups. If the server or a backup were ever taken, remove the certificate from the phone (it's listed under User credentials) and let Caddy make a new authority. There's no service worker, so the app always loads the page fresh from the server and doesn't work offline, and Chrome won't offer to install it by itself: use the menu.

## Switches
New features are built switched off. Each switch is a line in `api/.env` set to exactly `on` or `off`. Anything else, or a missing switch, stops the API starting, so a typo can't quietly change what's on. `GET /system/features`, the phone page and the daily summary all show what's off. The MCP server has one switch of its own, `MCP_ACTIONS`, which `bash host/hub-mcp.sh read-only` turns off. Jobs that run on the server itself, like the nightly backup, are switched on and off by enabling or disabling their systemd timer.

### The deal watcher's settings
`DEALS` switches it on. While it's on, `api/.env` also needs `DEALS_SEEN` (`memory` or `disk`), `EBAY_ENVIRONMENT` (`production` or `sandbox`), `EBAY_CLIENT_ID`, `EBAY_CLIENT_SECRET` and `DEALS_AI` (`on` or `off`: whether Claude's tools may read the listings). Each search has its own `switch` in `deals/searches.json`. `docs/deals.md` has the rest.

### Finding your phone
`FIND_PHONE` switches on `POST /phone/find`, which sends your phone ntfy's top priority, "Here's your phone", to `NTFY_TOPIC`, so `api/.env` needs that topic while it's on. ntfy's docs describe that priority as really long vibration bursts and the default sound, with a pop-over; whether it sounds through Do Not Disturb or silent mode is down to the phone and its ntfy settings (not checked). It's sent at most once every 10 seconds. Jarvis asks it when you say "find my phone" (record 0046). It's urgent, so bedtime never holds it (record 0068).

To make it ring rather than ping (record 0071), `FIND_PHONE_RING` (optional) says how:
- `once` (the default, as before): one message.
- `clear`: one message with a sequence ID (`find-` and 8 random hex characters, in ntfy's `X-Sequence-ID` header), cleared after `FIND_PHONE_SECONDS` with ntfy's `PUT /<topic>/<sequence ID>/clear`. It's for a phone whose ntfy app is set to keep alerting for the highest priority until the notification is dismissed (ntfy's "insistent" notifications, Android app v1.16.0 on): the clear is what dismisses it. Updating and clearing need ntfy server v2.16.0 and Android app v1.22.2 or later, per [ntfy's release notes](https://docs.ntfy.sh/releases/); ntfy.sh runs the latest server. Whether a clear stops a phone that's still ringing isn't known: it's the first thing to try.
- `repeat`: the same message with the same sequence ID every 5 seconds for `FIND_PHONE_SECONDS`, so the phone replaces it each time rather than stacking them, then it's left showing.

`FIND_PHONE_SECONDS` (optional): how long, a whole number from 10 to 120, 30 if left out. Bad values for either stop the API starting, even with `FIND_PHONE` off. While it's ringing, another find is a 429 saying it's already ringing, and the answer to a find says how it rings and for how long. `POST /phone/found` stops it early and clears it (`{"stopped": true, "cleared": true}`, or `"cleared": false` if ntfy didn't take the clear), or says `{"stopped": false}` when nothing is ringing; it's switched off with `FIND_PHONE`. `docker compose logs api` has a line when it's sent once or starts ringing (how, for how long, and the sequence ID), when ntfy didn't take it, and when it stops (why, after how many seconds, how many sends went and failed, and whether it was cleared), never the topic. [ntfy's publishing docs](https://docs.ntfy.sh/publish/) describe sequence IDs and clearing. With `JARVIS_HUB_TOOLS=on`, after you ask Jarvis to find your phone, saying "found it" (or "found my phone", "I've found it", "stop ringing", "you can stop ringing") on its own within 2 minutes asks for `POST /phone/found` and he says whether it stopped; outside those 2 minutes, and once it has stopped, they're ordinary words that go to Claude, and in guest mode they aren't his.

### Train times
`TRAINS` switches on `GET /trains`, the next five trains from one station to another (or, with a change station, the next three journeys: see "Journeys with a change" below), from National Rail's live departure boards (Darwin) through the Rail Data Marketplace (record 0047). While it's on, `api/.env` also needs:
- `RAIL_DATA_KEY`: the consumer key from your free Rail Data Marketplace account, on the "Live Departure Board" product's Specification tab. It's a secret, like the other keys in `api/.env`.
- `TRAINS_FROM` and `TRAINS_TO`: the two stations' three-letter codes, in capitals (National Rail's station pages show them).
- `TRAINS_BOARD_URL`: the departure board's address on that Specification tab, up to but not including the station code. In community copies of that tab it looks like `https://api1.raildata.org.uk/1010-live-departure-board-dep1_2/LDBWS/api/20220120/GetDepartureBoard`, but copy yours. It must be https on `raildata.org.uk`, with no `?`, `#` or `{` part.

The hub asks `TRAINS_BOARD_URL/TRAINS_FROM?numRows=5&filterCrs=TRAINS_TO&filterType=to`, sending the key in an `x-apikey` header. That's how community examples of the board's JSON version ask it; the official specification is behind the marketplace's login and wasn't checked, so `bash host/hub-get.sh /trains` is the first test. One copy of the specification describes `filterType=to` as trains starting or ending at `TRAINS_TO`; it's believed to mean trains that call there, which that first test should show with a train known to run on past it. It gives each train's booked and expected time, platform, whether it's cancelled (or cancelled at `TRAINS_TO`) and why, how many buses the board lists, and up to three of the board's own messages, which on a day with no trains may be all there is. The board covers about the next two hours, as far as community clients show (not checked), so "no trains" means none in that time. It says why when the board can't be reached, refuses the key, can't find the address (a 404 usually means `TRAINS_BOARD_URL` includes the station code), redirects or sends something that isn't a board, never with the key, and gives up after 8 seconds. Jarvis says the next three when you say "train times" (record 0046).

### Journeys with a change
`TRAINS_CHANGE_AT` makes train times follow a journey with one change (record 0053). With it set, `TRAINS_TO` is where you end up, not where you change, and while `TRAINS` is on `api/.env` also needs:
- `TRAINS_CHANGE_AT`: the change station's three-letter code, in capitals, different from both ends.
- `TRAINS_CHANGE_MINUTES`: how long the change takes you, door to door, in whole minutes from 1 to 30. The boards give whole minutes, so every gap is a whole number of minutes: with 3, a 3-minute gap is enough and a 2-minute one is tight.
- `RAIL_ARRIVALS_KEY`: the consumer key of the free "Live Arrival Board" product, a second subscription on the Rail Data Marketplace with its own key. It's a secret, like `RAIL_DATA_KEY`.
- `TRAINS_ARRIVALS_URL`: that product's address from its Specification tab, ending in `GetArrBoardWithDetails`, without the station code.
- `TRAINS_BOARD_URL` must then end in `GetDepartureBoard` or `GetDepBoardWithDetails`: the hub uses the detailed board, `GetDepBoardWithDetails`, which sits next to the plain one and comes with the same Live Departure Board subscription and key.

The hub asks two boards at the change station at once:
- the arrival board, for trains and buses due in from `TRAINS_FROM` (`TRAINS_ARRIVALS_URL/TRAINS_CHANGE_AT?numRows=5&filterCrs=TRAINS_FROM&filterType=from`, with `RAIL_ARRIVALS_KEY`). Its detailed reply lists each one's earlier stops, so it gives the time at `TRAINS_FROM` too, and it keeps a train listed after it has left `TRAINS_FROM` until it gets in, which is what lets the hub follow it while you're on it. A departure board drops a train soon after it leaves.
- the detailed departure board, for trains and buses on to `TRAINS_TO` (the detailed address next to `TRAINS_BOARD_URL`, then `/TRAINS_CHANGE_AT?numRows=10&filterCrs=TRAINS_TO&filterType=to`, with `RAIL_DATA_KEY`), with when each is due in at `TRAINS_TO`.

`GET /trains` then gives `from`, `via`, `to`, `walk`, up to three messages from the two boards (each once), and the next three journeys by when they leave `TRAINS_FROM`, counting one that has left but isn't in yet. Each journey has its first train's time and expected time, whether it's cancelled or a bus, why it's late, when it's due and expected in at the change, and its platform there, then:
- `best`: the connection that gets you in soonest among those leaving you at least your walk. That's not always the first to leave: a slower train a few minutes earlier isn't best.
- `fallback`: the soonest in of the others leaving no earlier than the best, for if you miss it.
- `tight`: a connection that would get you in sooner than the best but leaves you less than your walk (a minute at least), so you know there's one worth running for.

Each connection has its time, expected time, platform, destination, when it's due and expected in, whether it's a bus, why it's late, and `change`, the minutes you'd have. A cancelled connection, one cancelled at `TRAINS_TO`, or one leaving before you're in isn't offered. A connection delayed with no time yet counts from when it was due, and one with no expected time in is taken to be as late in as it is leaving. A first train with no expected time in has no connections until it has one. Times work across midnight. The boards sometimes write "Ontime" without the space; it's read as "On time", here and on the direct board. Errors say which board failed and which setting to check, never a key. Jarvis says the next three journeys when you say "train times": each first train, the minutes you'd have at the change for its best connection and when that gets in, any tight one, and the fallback.

### Morning train alerts
`TRAIN_ALERTS` switches on a morning check of the trains between the same two stations, sent to your phone through `NTFY_TOPIC` (record 0048). It needs `TRAINS=on` too, and while it's on, `api/.env` also needs:
- `TRAIN_ALERT_DAYS`: the days to check, from `mon`, `tue`, `wed`, `thu`, `fri`, `sat` and `sun`, with commas between, like `mon,wed`.
- `TRAIN_ALERT_WINDOW`: the trains to watch, by the time they're due to leave, as two 24-hour times with a dash between, like `07:00-08:30`. Both ends count, and it must end by 22:59, so the hour after it is still the same day.
- `TRAIN_ALERT_REMINDER`: when to send the reminder, a 24-hour time like `06:45`. It must be before the window ends, and no more than 2 hours before it ends, since the board only looks about that far ahead.

London time throughout. On those days, at the reminder's time, the hub sends "Morning trains": each train in the window with whether it's on time, how late or cancelled and why, and its platform once the board has one, then any buses the board lists and its own messages. If the board's furthest train is due before the window ends, it says how far the board reaches, since it asks for only 10 trains. From then on it asks the board every 2 minutes and sends "Train change" when a train in the window:
- is cancelled, at high priority;
- becomes 5 minutes late or more, and again whenever that moves by 5 minutes or more;
- is shown as delayed with no expected time, when it wasn't already 5 minutes late;
- after one of those, is back to 2 minutes late or less, or is 5 minutes or more less late than last sent;
- runs again after being cancelled;
- moves from one platform to another (a platform appearing for the first time isn't sent);
- leaves the board more than a minute before it's due, while the board lists later trains and has fewer than 10 on it, which may mean it was cancelled or replaced by a bus.

With `TRAINS_CHANGE_AT` set, the window is the trains leaving `TRAINS_FROM`, the reminder gives each journey in it as `GET /trains` would (first train, its time in, the connection, any tight one, the fallback), and both boards are asked for 10 rows. On top of the first trains' own changes above, it sends "Train change" when a journey:
- loses its connection, because the gap has dropped under your walk, the first train now gets in after it leaves, or it's cancelled or gone from the board: at high priority, saying which, with the next best;
- gets a better connection back, once the gap is a minute more than your walk, so a gap hovering at your walk doesn't flip back and forth;
- has no connection on the board at all, at high priority, or finds one;
- has its connection move platform;
- has a sooner connection become possible but tight, said once for each connection.

A journey first seen after the reminder only sends its own first train's problems, and its connection is noted quietly. A first train with no expected time in keeps its last connection until it has one.

So a train hovering around 5 minutes late, or flipping between a time and no time, doesn't send each flip. A train is known by the time it's due, so a change of destination (a train ending its journey early, say) doesn't make it a new train; only two trains due at the same time are told apart by destination. A train first seen after the reminder, as the board reaches further, is only sent if something's already wrong with it. It stops once the window has ended and none of its trains is still on the board, or an hour after the window ends, whichever comes first, and starts again the next set day.

If the board fails for 5 minutes or more, whether it can't be reached, refuses the key or sends something that isn't a board, it says so with when it started failing (about 6 minutes after the first failure, since it asks every 2 minutes), and keeps trying every 2 minutes. When the board answers again it says so, unless the reminder follows straight away, and if it's still failing an hour after the window ends, it says it has stopped checking for the day. Each outage is sent once. The API's log says when it couldn't reach the board and when it can again, never with the key. A notification ntfy didn't take is sent with the next check, 2 minutes later. It keeps nothing on disk: if the API restarts before the window ends, the reminder comes again with the trains as they are then, and if it restarts after the window ends, it only sends what's wrong with the window's trains still on the board. The notifications pass through ntfy.sh like the other alerts. The hub adds no station or destination names to them, with a change station too, but the board's own reasons and messages go as they are, and those can name stations.

While `TRAIN_ALERTS` is on, `GET /trains/changes` gives today's change lines too (record 0051), for Jarvis to say aloud: each check that found changes is one entry, numbered from 1, with when it was found and its lines, only the newest 50 kept and none of the reminder's or the outage notices. `?after=<number>&run=<run>` gives only the entries after that number; the `run` changes each time the API starts, and since the numbers start again then, asking with an old run gives all of today's entries. Entries are found as each check runs, whether or not ntfy takes them, and kept in memory only, so a restart empties them. After a restart past the window's end, the first check's lines go to your phone as before but aren't added, since they're what was already wrong. It's behind the API's token like every route, and since Jarvis asks every 30 seconds, asking isn't logged, refusals and wrong tokens included, unless the API itself fails.

### Expiry alerts
`EXPIRY_ALERTS` switches on reminders for things that run out on a date, like the server's Tailscale key, a GitHub token or a yearly subscription, sent to your phone through `NTFY_TOPIC`, so `api/.env` needs that topic while it's on (record 0057).

The list is `expiry/items.json`, which git ignores: copy `api/src/modules/expiry/items.example.json` there and edit it in VS Code. Each item has a `name`, a `date` written `YYYY-MM-DD`, and an optional `note`. It's read again at every check, so a change needs no restart. It holds names and dates only, never a key, token or password: a name (up to 40 characters) or note (up to 100) is refused if it has anything but letters, digits, spaces and `' - . , ( ) & / + : _`, a word over 20 characters, or a word of 12 or more mixing letters and digits, since that could be a key pasted in by mistake. A note can hold a web address that starts `https://`, like `Renew at https://login.example.com/admin`: each part of it between dots and slashes is checked as a word instead, so a key hidden in the address is still refused. A note of `null` counts as no note, like `""`. Two items with the same name, in any case, and more than 50 items are refused too. One refused entry stops the whole list, as with the deal watcher's: the error names the file and the entry by its number, never what was refused, and goes to the API's log, to `GET /system/alerts` (so the alerts send it to your phone while `ALERTS` is on) and to `GET /expiry`. With the switch off the list isn't read, so a missing or broken one never stops the API starting.

Every 5 minutes, from 08:00 London time, the API checks the list and sends one notification for everything due: an item is warned about at 30, 14, 7, 3 and 1 days before, on the day, and once when it's overdue. ntfy turns a message over 4,096 bytes into a file attachment, so a warning that long lists what fits in 3,500 bytes, soonest first, and ends by saying how many more there are. One first seen part way through, or after a day the check couldn't run, is warned about once for where it is then, with its real days left. A notification ntfy doesn't take is tried again at the next check. It's high priority when something is a day away or less, due today or overdue. What was sent is kept in `expiry/sent.json`, written by the API beside the list, so a restart sends nothing again; a new date for an item, as after renewing it, starts its warnings again. If that file can't be saved, the alerts say so, and a warning may be sent again after a restart. Deleting it while the API is stopped is safe: each item within 30 days, or overdue, gets one warning for where it is now.

The names, dates and notes go through ntfy.sh in the notifications and the daily summary, so keep them general. `GET /expiry` gives today's London date and each item with its date, note, days left (below 0 once passed) and whether it's overdue, soonest first, and says when expiry alerts are switched off or the list has a problem. The daily summary adds an "Expiring:" line when something is within 30 days or overdue, the phone page lists them under "Expiring", and Claude Code reads them with `get_expiries`.

### The server doctor
`GET /system/doctor` answers "is everything OK?" in one go, from what the hub can already see (record 0058). It has no switch of its own: it only reads, and adds nothing the other routes couldn't already reach. It's behind the API's token like every route. It gives an overall `state` (`ok`, `warn` or `problem`), a `summary` in plain words such as "1 problem: Heartbeat. 1 thing to look at: Disk.", the time it checked, and thirteen `checks`, each with a `name`, a `state` (`ok`, `warn`, `problem`, or `off` when its feature is switched off, which never counts as a problem), a `detail` in plain words and `next`, what to try, or null when it's ok or off:
- Disk: a problem under a tenth free (the alerts' rule), something to look at under a fifth.
- Memory: a problem under a tenth available (the alerts' rule).
- Wi-Fi: something to look at after any reconnect in the last 24 hours (the alerts' rule).
- Backups: off until one has run, a problem when the last run failed (the alerts' rule), something to look at when the last good one is more than a week old or the status can't be read.
- Heartbeat (`HEARTBEAT`) and Phone alerts (`ALERTS`): the API remembers, in memory only, whether its last ping to Healthchecks.io, and its last 5-minute alert check (reading the problems and sending any change to ntfy), worked, and when. A failure is a problem. Before the first one has finished after a start, it's something to look at. A restart forgets both.
- qBittorrent and Jellyfin: asked as `/media/downloads` and `/media/library` ask them, with their keys; no answer within 6 seconds, or an error, is a problem.
- Brain inbox (`MEMORY_INBOX`): a problem when it can't be counted.
- Deal watcher (`DEALS`): its own problems from the alerts; a day's calls used up on its own is something to look at.
- Train times (`TRAINS`): asks the departure board once, as `GET /trains` does (three boards with `TRAINS_CHANGE_AT`), so each check is one more call on your Rail Data Marketplace key; no answer is a problem.
- Expiry list (`EXPIRY_ALERTS`): anything overdue, a list it can't read, or warnings it couldn't save are problems; anything due within 7 days is something to look at. It names the items.
- Watchers (`WATCHERS`): how many things are being watched; a watcher whose last check couldn't read its source, or whose notification is waiting to be sent again, is something to look at. It asks nothing new: it only reads the watchers' own list.

The checks are asked at the same time, so one that doesn't answer holds the rest up by 6 seconds at most, which keeps the answer inside the 10 seconds Claude Code's hub tools wait and the 12 seconds Jarvis's code words wait. What qBittorrent, Jellyfin and the departure board answered is kept for 10 seconds, so the phone page asking for the doctor and for catch-up together makes one call to each of them, not two. Only an answer is kept: after a call that failed or didn't answer within the 6 seconds, the next ask tries again. It never reaches Docker, and never shows a key, a token or the Healthchecks address. The phone page shows it under "Is everything OK?", Claude Code reads it with `get_doctor`, the `server-doctor` skill (`.claude/skills/server-doctor/`) looks into anything that isn't fine with the hub's other read tools and suggests what to run, and Jarvis reads its summary out when you say "server check" (below).

### Watchers
`WATCHERS` switches on "tell me when": you ask Claude Code or Jarvis to tell you when something happens, and the hub sends your phone one notification through `NTFY_TOPIC` when it does, so `api/.env` needs that topic while it's on (record 0059). The kinds of thing it can watch are fixed in the hub's code (`api/src/modules/watchers/kinds.ts`); Claude only picks a kind and fills in its numbers, and nothing is saved until you've said yes. There are three kinds:
- `download-finished`, with `name`, a few words of the download's name (2 to 40 characters of letters, digits, single spaces and `' - . , ( ) & / + : _`, refused if a word could be a pasted key, as on the expiry list): fires when a torrent whose name holds those words, in any case, finishes in qBittorrent after the watcher was made. It asks qBittorrent for its completed torrents and reads when each one finished, so a download that finished before you asked never counts.
- `disk-free-below`, with `percent`, a whole number from 1 to 99: fires when the server's free disk space, as `GET /system/status` reads it in whole GB, is below that percentage. If it's already below, it fires at the next check.
- `service-answering`, with `service`, `qbittorrent` or `jellyfin`: fires when that service answers the hub, asked as `/media/downloads` and `/media/library` ask it. If it's already answering, it fires at the next check.

Each also has `hours`, how long to watch before giving up: a whole number from 1 to 168 (a week), 24 if left out. `POST /watchers` with a JSON body like `{"kind": "disk-free-below", "percent": 15}` adds one, `GET /watchers` lists them, and `DELETE /watchers/<id>` cancels one by the 8-character id the list gives. A body with anything else in it (another kind's field, an unknown field, a number out of range, text that isn't plain) is a 400 saying what's allowed, never repeating what was sent, and a body over 1 KB is refused. The same watch twice, or an 11th, is a 409. All three routes are behind the API's token like every route, and say watchers are switched off with a 404 while `WATCHERS` is off.

While any watcher exists, the API checks once a minute, asking only the sources the watchers need, each once, with 8 seconds at most to answer. When one happens, it sends one notification naming only what you asked about (never a torrent's full name) and the watcher is gone. Two edges: a watcher cancelled in the moment its notification is being sent still notifies, and if ntfy takes the message but answers after the 10 seconds the hub waits, the hub counts it as not sent and sends it again at the next check, with the same sequence ID (`watcher-` and its id), so a phone on ntfy's Android app v1.22.2 or later replaces the first rather than showing it twice (record 0071). If ntfy doesn't take it, it's tried again at the next check without asking the source again. A source that can't be read (qBittorrent down, say) never fires or removes a watcher: its last check says it couldn't read it, `GET /watchers` and the server doctor show that, and it keeps trying. For `service-answering`, not answering is what's being watched, so it's never a failed read. A watcher that reaches its time without happening sends one low-priority note saying it stopped watching and that it didn't happen (and if the last check couldn't read its source, that too), once, and goes. One that happened but still couldn't be sent by its time is dropped without that note, and the API's log says so. Watchers are kept in memory only, so restarting or rebuilding the API forgets them, without a notification. What you asked about (the kind, a download's words, the percentage) goes through ntfy.sh in the notification, so keep it general.

The phone page lists them under "Watching for", each with a Cancel button; it can't add one. Claude Code reads them with `get_watchers` and adds or cancels them with `add_watcher` and `cancel_watcher`, which always ask first, like the other actions. With `JARVIS_HUB_ACTIONS=on`, Jarvis can use the same two actions, and his own code asks you yes or no in the chat first, saying exactly what would be watched and for how long. Jarvis never says a fired watcher out loud: it's a phone notification only.

### Catch-up
`CATCH_UP` switches on "where was I?" for coming back to my projects after time away (record 0060): `GET /catch-up` gathers recent commits in the GitHub repos I list and what's waiting on the hub, in one answer. It only reads. It's behind the API's token like every route, and says catch-up is switched off with a 404 while `CATCH_UP` is off.

- `CATCH_UP_REPOS` (optional): up to 10 GitHub repos, each written `owner/repo`, with commas and no spaces between, like `alpha/one,beta/two`. Owners and names are checked against GitHub's own naming rules, and a repo listed twice is refused; a refusal names the setting, never its value. Left out, GitHub is never asked and the answer has only the hub's part.
- `CATCH_UP_GITHUB_TOKEN` (optional, a secret): a fine-grained GitHub token, starting `github_pat_`, for private repos. It needs read-only access to the repos' Contents and nothing else. Public repos need no token, so start without one. Classic tokens (`ghp_`) are refused, because they can't be limited to some repos and to reading.

`GET /catch-up?days=7` looks back that many London days, counting today, from midnight there (so `days=1` is today so far), 1 to 30, 7 if left out; anything else is a 400. For each listed repo it asks GitHub's REST API (`https://api.github.com/repos/<owner>/<repo>/commits`, with `since` and `per_page=30`, API version `2026-03-10`) for one page of commits, all repos at once, each with 4 seconds to answer, never following a redirect (GitHub answers a renamed repo with one, so that repo then says to check its name). The token, when there is one, goes only in that request's `Authorization` header, never in a reply, an error or a log. Each repo gives its commits per London day, newest first, with the short sha, the time and the message's first line, cut to 120 characters with control and hidden characters taken out, at most 30 (`more` is true when GitHub has more); a repo that can't be read says why in plain words (not found or private, the token refused, the hourly limit used up and until when, no answer, a redirect, an empty repo), never with GitHub's own reply, and the others still answer. Each repo's answer is kept for 10 minutes for the same number of days, or 1 minute if that repo failed, so the phone page and Claude asking again don't use up GitHub's limit: 60 calls an hour without a token, shared by everything behind the same public IP address, or 5,000 with one. Each different number of days is its own ask of every repo, so 10 repos asked for 6 different numbers of days in an hour would use all 60. When GitHub says the limit is used up, or says how long to wait, no repo is asked again before the time it gave (a minute at least, an hour at most, as [GitHub's rate limit rules](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api) ask): answers already kept are still given, and the other repos say they weren't asked and until when. `commitsAskedAt` is the oldest time any repo in the reply was asked, or `null` if none was.

The hub's part reuses what its modules already read, each with 5 seconds at most: notes waiting in the brain inbox (a count only, as `GET /memory/inbox` gives it; the hub can't read the notes), things on the expiry list due within 7 days or overdue, watchers still waiting, the alerts' problems, the last backup, and the server doctor's overall state and summary (asking qBittorrent, Jellyfin and, while `TRAINS` is on, the departure board, each with 4 seconds). A part whose feature is switched off says `off` with its setting, and one that can't be read says `failed` with why; neither fails the answer. A `summary` says it all in plain words. Commit messages are other people's text, so the tool's description tells Claude to treat them as untrusted.

The phone page shows it under "Where was I?" while it's on: the summary and each repo's latest commit. Claude Code reads it with `get_catch_up` (allowed without asking, like the other read tools), and the `catch-up` skill (`.claude/skills/catch-up/`) turns it into a plain "where was I?", suggesting read-only git commands for the repo it runs in. Jarvis doesn't have it. Nothing here reaches a work system: adding work tickets would need its own decision, and recent ideas from the brain would too.

### Modes
`MODES` switches on the hub's modes (record 0068): `normal`, `guest`, `bedtime`, `gaming`, `coding` and `away`. The hub keeps which one it's in, so Jarvis, the phone page and Claude Code all see the same one, in `api/data/mode.json`, written by the API (`api/data/` is mounted into it at `/data`, and git ignores everything in it but its README), so a restart keeps it. With `MODES` off, nothing is held, nothing is read or written there, and both routes say modes are switched off with a 404.

- `GET /mode` gives `mode`, `since` (when it started), `until` (when it ends by itself and goes back to `normal`, or `null`), `by` (`voice`, `typed`, `phone`, `owner`, `schedule` for a timer or a mode's end, or `start` when the API started with nothing saved) and `held`, how many phone alerts are being held.
- `POST /mode` with a JSON body like `{"mode": "away", "until": "2026-01-31T18:00:00Z", "by": "voice"}` switches it. `by` must be `voice`, `typed`, `phone` or `owner`, which is Jarvis saying it was your own voice (record 0072) and is the only spoken way out of guest mode. Only `away` (up to 30 days ahead) and `bedtime` (up to 24 hours ahead) can have `until`, which must be in the future. Anything else in the body is a 400 saying what's allowed, and a body over 1 KB is refused. Asking for the mode it's already in keeps its `since` and changes only `until` and `by`.
- Guest mode can be switched on any way, but off only typed or from the phone page: while it's on, a switch with `"by": "voice"` is a 409 saying so. That's the hub's own rule, so it holds whatever asks.
- Bedtime holds phone alerts. While it's on, every message the hub would send through ntfy goes through one gate in `api/src/modules/notify/notifier.ts`, and each one that isn't urgent is held in the API's memory instead. Urgent ones always go straight through: finding the phone, a train alert with a cancellation in it, and a reminder marked urgent. When bedtime ends, by its time or by a switch to any other mode, everything held goes as one message, "Held during bedtime: 3 alerts", each with the London time it came, the newest last, up to 3,500 bytes (ntfy turns longer messages into a file), then "And 4 more." for what didn't fit. It keeps at most 100 and counts the rest. A send ntfy doesn't take is tried again every 30 seconds. Held alerts are kept in memory only, never on disk, since some (the deal watcher's) must never be written down, so a restart during bedtime loses them; the saved count means the next message says how many were lost, or a message says just that if nothing else was held. The other modes hold nothing: in `away` everything goes straight to the phone.
- `BEDTIME_UNTIL` (optional): a 24-hour time before midday, like `07:30`, in London time. Bedtime switched on without `until` ends at the next one. Left out, bedtime lasts until it's switched or given `until`.
- `BEDTIME_FROM` (optional, default `off`): a 24-hour time from `00:00` to `05:59`, like `00:30`, to start bedtime every night at that time, ending at `BEDTIME_UNTIL`, which it then needs. It starts from `normal`, `gaming` or `coding`, never from `guest` (only typing or the phone page end that) or `away` (timed switches are skipped while away). It starts once a night: switched off by hand, it doesn't start again until the next night, and the API remembers that across a restart. A restart inside the window starts it, unless it already started that night.
- A bad `BEDTIME_FROM` or `BEDTIME_UNTIL` stops the API starting even while `MODES` is off, like the deal watcher's choices, so a typo can't wait for the day it's switched on.
- The check for a mode's end and for `BEDTIME_FROM` runs every 30 seconds.

`docker compose logs api` has a line for the mode at start (as saved, or none), each switch (from, to, how, until, and how many alerts were held), each refused switch, each alert held (its tags and priority, never its words or the topic), each held message sent (how many, how many lost, its size in bytes, and when the first held one came), a held message ntfy didn't take, alerts lost in a restart (how many), a bedtime start time skipped (and the mode it found), and a mode that couldn't be saved. The phone page shows it under "Mode" with a button for each mode ("Guest on" or "Guest off", Normal, Bedtime, Gaming, Coding, Away), each switching with `"by": "phone"`. Claude Code reads it with `get_mode` (allowed without asking); nothing gives Claude Code a way to change it. Jarvis may read it with `get_mode` too; what each mode does to Jarvis is his own (his settings, below).

### Reminders
`REMINDERS` switches on the hub's scheduler (record 0070): reminders, timers (a reminder a few minutes from now) and timed mode switches, sent to your phone through `NTFY_TOPIC`, so `api/.env` needs that topic while it's on. They're kept in `api/data/reminders.json` (written by the API, readable only by it), so they survive a restart, and one that came due while the API was down goes off as soon as it's back, marked late. With it off, nothing is read or written there and every route says reminders are switched off with a 404.

- `POST /reminders` with a JSON body like `{"text": "Take the bins out", "at": "2026-01-31T19:00:00Z", "repeat": null, "urgent": false, "kind": "reminder"}` sets one and answers with it, including its 8-character `id`. `text` is 1 to 200 characters of plain text (runs of spaces become one; control and hidden characters are refused). `at` is an ISO 8601 time with `Z` or an offset, in the future and at most a year ahead. `repeat` is `null` (once), `daily`, `weekdays` (Monday to Friday) or `weekly`, at the same London time, so it follows the clocks changing. `urgent` makes it high priority and lets it through bedtime (record 0068). `kind` is `reminder` or `mode`; a `mode` one has `mode` (one of the modes) and switches the hub's mode at its time instead of sending anything, and can't be urgent. Only `text` and `at` are needed. Anything else in the body is a 400 saying what's allowed, a body over 1 KB is refused, and a 51st is a 409.
- `GET /reminders` lists them, soonest first: each one's `id`, `text`, `kind`, `mode`, `first` (the time it was set for), `at` (its next time, or `null` once a one-off has gone off), `repeat`, `urgent`, `snoozedTo`, `firedAt` and `createdAt`.
- `DELETE /reminders/<id>` cancels one, repeats and all. `POST /reminders/<id>/snooze` with `{"minutes": 10}` (1 to 240) sends it again that many minutes from now, even after it went off; a repeating one keeps its next time too. `POST /reminders/<id>/done` removes a one-off, or drops a repeating one's snooze and keeps its next time. A timed mode switch can't be snoozed (409).
- When a reminder is due, the hub sends it to your phone, titled "Reminder", with its text (and, if it's over 2 minutes late, when it was due and that it's late because the hub was down), and adds it to a feed for Jarvis: `GET /reminders/due?after=<seq>` gives `{"seq": 7, "due": [{"id", "text", "at", "late", "urgent"}]}`, the reminders that went off after that `seq` (all those kept, with no `after`). It's a plain poll that answers at once; ask again with the `seq` it gave. The feed keeps a day's worth, at most 50, and its numbers are saved, so they carry on after a restart. It's logged at warnings only, so polling it doesn't fill the log.
- A one-off reminder stays in the list for a day after it goes off, so it can still be snoozed, then goes by itself. A repeating one missed several times while the API was down goes off once, late, then at its next time.
- A timed mode switch at its time switches the mode as the schedule (`by: "schedule"`), the way `BEDTIME_FROM` does: skipped while away or in guest mode, and skipped if it's more than 30 minutes late, since a mode switch belongs to its time. It needs `MODES=on`: with modes off, setting one is a 409.
- The check runs every 5 seconds. A reminder ntfy doesn't take still goes in Jarvis's feed, and is tried again at each check for an hour, then dropped and logged.
- If `api/data/reminders.json` can't be read, it's moved aside to `reminders.json.bad` (never overwritten), the API starts with none, and the log says so.

What you write goes through ntfy.sh in the notification, so keep it general. `docker compose logs api` has a line for the reminders at start (how many, how many repeat, how many are mode switches, how many were missed, the feed's number, and whether the file was read), each one set (its id, kind, mode, repeat, urgent, time and how many minutes away), cancelled, snoozed (minutes), done, due (its id, feed number, whether and how late, urgent, repeat, whether it was a snooze, whether ntfy took it, and its next time), each timed mode switch (the mode and what happened), one that couldn't be sent or was dropped, and ones removed a day after going off: ids and numbers, never what a reminder says. Claude Code reads them with `get_reminders` and sets, cancels and snoozes them with `set_reminder`, `cancel_reminder` and `snooze_reminder`, which ask first like the other actions. With `JARVIS_HUB_ACTIONS=on`, Jarvis's plain API engine can use those three without asking you yes first, since they're harmless and can be undone; the Agent SDK engine doesn't allow them yet. Jarvis speaking reminders from the feed is his own (his settings, below).

### Dev chores
`CHORES` switches on dev chores (record 0073): asking the server, through the hub, to run one job from a short fixed list, without giving any container the Docker socket. The jobs:
- `rebuild-api`: `docker compose up -d --build --wait api` from `~/docker`, 15 minutes at most. It restarts the API itself, so the API isn't there to answer for a moment.
- `run-tests`: the `api`, `mcp`, `jarvis` and `ears` tests, one after another, each in a throwaway `node:26-alpine` container (with `--init`, so the time limit stops the container and not just the `docker` command) with its folder mounted read-only, copied inside the container without its `node_modules`, `dist`, `.env` and `data`, then `npm ci` and `npm test` there, 10 minutes each at most. The secrets and data are left out because `npm ci` runs other people's install scripts with the internet. That differs from the README's way above (which runs `npm ci` in the folder itself) so that nothing on the server changes and a running Jarvis keeps his packages. It needs the internet for npm, like `npm ci` always does.
- `pull-images`: `docker compose pull --ignore-buildable`, 20 minutes at most: it downloads newer images for the services that use one (not those built here: the API, ears and the MCP server), and restarts nothing, so a newer image is used only at the next `docker compose up -d`. It pulls the services that start by default, not those in a profile.

How it works: `POST /chores/<job>` writes one file, `chores/requests/<id>.job`, holding only the job's name, and answers `{"id", "job", "requestedAt"}` with a 16-character id. `chores/requests/` is mounted into the API read-write and `chores/results/` read-only, both from `chores/` in this folder (git ignores what's in them). A systemd path unit, `home-hub-runner@<user>.path`, notices the file and starts `home-hub-runner@<user>.service`, which runs `/usr/local/bin/home-hub-runner` (installed from `host/runner.sh`) as that user, not root, with `NoNewPrivileges`. Both are templates (`host/home-hub-runner@.path` and `@.service`): the part after `@` when they're enabled is the user, so no user's name is written in the repo, and they expect that user's home at `/home/<user>` with this folder at `/home/<user>/docker` (systemd's `%h` would be root's home in a unit like these, so they can't use it). The runner removes the request, checks the name against its own list (anything else is refused, and nothing from the request ever reaches a shell or a command as an argument), runs that job's commands with a time limit (`timeout`, then a kill 30 seconds later), and writes `chores/results/<id>.json` (its state, exit code, whether it timed out, how long it took, when it started and ended, and its limit) and `<id>.out` (the last 40 lines of output, at most 4,000 bytes, with colour codes and control characters taken out). It keeps the last 20. `GET /chores/<id>` gives the result: `state` is `waiting`, `running`, `done`, `refused` (with `why`) or `dropped` (with `why`), with `job`, `exit`, `timedOut`, `seconds`, `startedAt`, `endedAt`, `limitSeconds` and `output` as lines.

One at a time: while a request waits for the runner or one is running (until its limit plus 2 minutes, in case the runner was stopped part-way), another is a 409 saying why. A request the runner hasn't picked up within 2 minutes is removed and its result says the path unit may not be running. A job that isn't on the list is a 400, and with `CHORES` off both routes say chores are switched off with a 404. The runner also takes a lock (`flock`), so running it by hand while it runs does nothing, and handles one request each time it starts (the path unit starts it again while one is left). The API writes a request under a dot name and then renames it, so the runner never reads one half-written. Anything in `chores/requests` that isn't a plain file named with 16 hex characters and `.job` (a folder, a link, an odd name) is renamed to `.set-aside-<time>` and never run, so the path unit stops firing for it; those can be deleted.

Being in the `docker` group makes your user as powerful as root on this server, so the runner is too: that's why its list is fixed in the script and short, and why each new job needs its own decision. Install it once with `sudo install host/runner.sh /usr/local/bin/home-hub-runner`, `sudo install -m 644 host/home-hub-runner@.path host/home-hub-runner@.service /etc/systemd/system/`, `sudo systemctl daemon-reload` and `sudo systemctl enable --now "home-hub-runner@$USER.path"`; `bash host/hub-update.sh` offers to install a changed copy, and restarts the path unit for every user it's enabled for. `journalctl -u "home-hub-runner@$USER"` has a line for each request (its id, the job, started with its limit, and how it ended: exit code, seconds, whether it timed out and how many bytes of output), each refusal and why, and how many it handled; `docker compose logs api` has a line for each request, refusal and dropped request (ids and job names). Claude Code reads a result with `get_chore` and asks for one with `run_chore`, which always asks first. With `JARVIS_HUB_ACTIONS=on`, Jarvis can too, and his code asks you yes or no first, saying which chore and what it does. A chore's output comes from Docker, npm and the tests, so its tool tells Claude to treat it as untrusted text. `bash host/runner.test.sh` tests the runner with a pretend `docker`, never running anything.

### Sessions
`SESSIONS` switches on the session manager (record 0074): the hub keeps which of my Claude Code sessions is waiting on me, working or stopped, and the chores runner (above) can start and stop them in `tmux`. I'm not sure I want it, so it's off unless I switch it on.

- How the hub hears: Claude Code's hooks ([its hooks reference](https://code.claude.com/docs/en/hooks)) run `bash host/hub-session.sh <name> <state>` when a session starts (`SessionStart`: waiting), when I send a prompt (`UserPromptSubmit`: working), after each tool it uses (`PostToolUse`: working, so it's right again after I answer a permission prompt), when it asks for a permission or sits idle waiting for me (`Notification` with `permission_prompt` or `idle_prompt`: waiting), when it finishes answering (`Stop`: waiting) and when it ends (`SessionEnd`: stopped). This repo's `.claude/settings.json` has those hooks for the session called `docker`; the brain repo's are in record 0074's guide, to add there by hand. The script does nothing at all unless `api/.env` has `SESSIONS=on`, so with it off (or on a computer without `api/.env`) nothing changes. It reads `API_TOKEN` from `api/.env` (git-ignored) and gives it to `curl` on its input, never as an argument, where other users of the server could see it, and posts `{"state": "..."}` to `POST /sessions/<name>/state` through Caddy, waiting 3 seconds at most. It prints nothing, because Claude Code adds what a `UserPromptSubmit` or `SessionStart` hook prints to what Claude sees, and always exits 0, so a hub that's down never gets in the session's way. The same state again within 5 minutes isn't sent again (it remembers the last in `~/.cache/home-hub/`), which keeps `PostToolUse` cheap.
- `GET /sessions` lists each session's `name`, `state` (`waiting`, `working` or `stopped`), `since` (when it got to that state) and `lastSeen`. `GET /sessions/changes?after=<seq>` gives the changes after that `seq`, each with its `name`, `state`, what it `was` and `at`, for a day, at most 50, like the reminders' feed; it's a plain poll, logged at warnings only. Names are 1 to 20 lowercase letters, digits and `-`, and the hub keeps 10 at most. They're kept in memory only: a restart forgets them until each session's next change.
- Starting and stopping: with `CHORES=on` too, `POST /chores/session-start-<name>` and `POST /chores/session-stop-<name>` are chores. The runner looks the name up in `host/hub-sessions.conf` (git-ignored, mine to write, copied from `host/hub-sessions.example.conf`): one line per session, its name, its `tmux` session's name and its folder, like `docker docker /home/you/docker`, at most 10. A name that isn't there, or a line whose `tmux` name isn't letters, digits, `-` and `_`, or whose folder isn't a plain absolute path inside my home that exists, is refused. Starting runs `claude` (from `~/.local/bin` or the usual places) in a new detached `tmux` session in that folder, unless one with that name is already running; stopping ends that `tmux` session, and Claude Code with it. Each has 30 seconds. These sessions run on a `tmux` server of their own, `tmux -L home-hub`, because one the runner starts carries the runner's `NoNewPrivileges` (`sudo` fails in it): `tmux -L home-hub ls` lists them and `tmux -L home-hub attach -t <name>` shows one, and your own `tmux` is left alone. Nothing from the request but the name is used, and the name is only compared with the file's. The runner's service has `KillMode=process`, so a `tmux` session it starts keeps running after the chore ends.

`docker compose logs api` has a line for each change of state (the name, from, to, the feed's number and how long it had been in the old state) and for a session refused because 10 are known; the runner's journal has the session chores like any other. Claude Code reads them with `get_sessions` (allowed without asking) and starts or stops one with `run_chore`, which always asks. With `JARVIS_HUB_ACTIONS=on`, Jarvis can too, saying which session he'd start or stop; what he says out loud about a session that's waiting is his own (his settings, below). `bash host/hub-session.test.sh` tests the hook script with a pretend `curl`, and checks the hooks in `.claude/settings.json`.
### Spotify
`SPOTIFY` switches on control of your Spotify account from the hub (record 0075): what's playing, your devices, playback, the queue, search, your playlists and your library, through Spotify's Web API. It needs a Spotify app of your own in Development Mode on [Spotify's developer dashboard](https://developer.spotify.com/dashboard), which needs Premium on the account that owns it ([quota modes](https://developer.spotify.com/documentation/web-api/concepts/quota-modes)), with your account on its user list. Every route is behind the API's token like the others, and each says Spotify is switched off with a 404 while `SPOTIFY` is off. While it's on, `api/.env` also needs:
- `SPOTIFY_CLIENT_ID`: the app's Client ID from its settings in the dashboard, 32 characters of 0 to 9 and a to f. It isn't a secret with this sign-in (the hub uses PKCE, so there's no client secret anywhere), but it still never goes in a log.
- `SPOTIFY_REDIRECT_URI`: exactly the Redirect URI you added in the app's settings, character for character. Spotify only takes https, or http on `127.0.0.1` or `[::1]` with a port, and never `localhost` ([redirect URIs](https://developer.spotify.com/documentation/web-api/concepts/redirect_uri)), and so does the hub. `https://hub.home/spotify.html` sends you straight back to the hub's Spotify page; `http://127.0.0.1:8888/callback` works from any browser, but the page then fails to load and you paste its address into the hub's Spotify page instead.
Signing in: open `hub.home/spotify.html` (log in on the hub page first) and press "Sign in to Spotify". The page asks `POST /spotify/sign-in`, which makes a new random verifier and state, keeps them in the API's memory for 10 minutes (a newer sign-in replaces an older one, and a restart forgets it), and gives Spotify's authorize address with the S256 challenge, the state and these permissions: `user-read-playback-state`, `user-modify-playback-state`, `user-read-currently-playing`, `playlist-read-private`, `playlist-read-collaborative`, `playlist-modify-public`, `playlist-modify-private`, `user-library-modify`, `user-follow-modify` (Spotify's page for saving to the library lists it) and `user-read-private` (for who's signed in). After you agree, Spotify sends the browser back to the redirect address with a code, the page passes the code and state to `POST /spotify/callback` and takes them out of its address, and the API swaps the code for tokens at `https://accounts.spotify.com/api/token` with the verifier, as [Spotify's PKCE guide](https://developer.spotify.com/documentation/web-api/tutorials/code-pkce-flow) shows. A state that doesn't match, has been used, or is over 10 minutes old is refused without asking Spotify. The callback is a `POST` behind the API's token rather than a page Spotify's redirect lands on, because the hub's login cookie is `SameSite=Strict` and isn't sent on a redirect from another site; the page's own request is from the hub, so it is.

The refresh token is saved in `spotify/tokens.json` (git-ignored, mounted into the API at `/spotify`, written readable only by the API's user, and denied to Claude Code in `.claude/settings.json`); the access token stays in memory. The access token is renewed a minute before it runs out, with the refresh token and Client ID and no secret ([refreshing tokens](https://developer.spotify.com/documentation/web-api/tutorials/refreshing-tokens)), two asks at once sharing one renewal, and a new refresh token is saved when Spotify sends one. If Spotify says the refresh token is no longer good (`invalid_grant`), the file is removed and the hub says to sign in again. `POST /spotify/sign-out` removes it too. `GET /spotify/status` says whether it's signed in, since when, when it last renewed, the permissions and any problem, without asking Spotify.

The routes, each built only on an endpoint [Spotify's February 2026 changes](https://developer.spotify.com/documentation/web-api/references/changes/february-2026) list as still available to Development Mode apps (the [migration guide](https://developer.spotify.com/documentation/web-api/tutorials/february-2026-migration-guide) has the renames):
- `GET /spotify/playing` (`GET /me/player`, with episodes): whether anything's active and playing, the track or episode, how far in, the device, shuffle, repeat and what it's playing from.
- `GET /spotify/devices` (`GET /me/player/devices`): each device's id, name, type, whether it's active, its volume and whether that can be set. Spotify only lists a device while Spotify is open on it, and not every model.
- `GET /spotify/queue` (`GET /me/player/queue`): what's playing and up to 20 next.
- `GET /spotify/search?q=...&types=track,album,artist,playlist&limit=5` (`GET /search`): `q` is 1 to 200 characters, `types` some of those four (all if left out), `limit` 1 to 10, Spotify's new most (5 if left out).
- `GET /spotify/playlists?limit=20&offset=0` (`GET /me` once for each sign-in, then `GET /me/playlists`): `limit` 1 to 50, `offset` up to 1000, each with whether it's yours.
- `POST /spotify/play` `{ uri?, device? }` (`PUT /me/player/play`): a track or episode on its own, or an album, artist or playlist as what it plays from; with no `uri` it resumes. `POST /spotify/pause`, `/next` and `/previous` `{ device? }`; `/seek` `{ positionMs }` (0 to 24 hours); `/volume` `{ percent }` (0 to 100); `/shuffle` `{ on }`; `/repeat` `{ mode }` (`off`, `track` or `context`); `/queue` `{ uri }` (a track or episode); `/transfer` `{ device, play? }` (`PUT /me/player`).
- `POST /spotify/playlists/<id>/add` `{ uris, position? }` (`GET /playlists/<id>` for its owner, then `POST /playlists/<id>/items`): 1 to 100 track or episode addresses, each once, only to a playlist that's yours or collaborative; anyone else's is a 403 and nothing is added.
- `POST /spotify/library/save` `{ uris }` (`PUT /me/library`): 1 to 40 tracks, episodes, albums, shows or playlists, each once. Spotify's page gives the addresses as one comma-separated list without saying whether it's the query or the body; the hub sends it in the query, as the page's example is written (not checked against Spotify).

`uri` is always a Spotify address like `spotify:track:` and 22 letters and digits, and `device` a device's id from `GET /spotify/devices`; left out, Spotify uses the active device. Fields a route doesn't know are dropped. The hub only reaches `accounts.spotify.com` and `api.spotify.com`, 8 seconds each, never following a redirect, and reads at most 1 MB of a reply. A refused access token is renewed and the call tried once more. Spotify's refusals come back as plain words, never Spotify's own message: no active device (409), Premium needed, a control that isn't allowed right now, or a 403 with no reason, which in Development Mode usually means the account isn't on the app's user list (403), not found (404), a wait (429 with `Retry-After`, and whether Spotify said the app's quota is used up), or a problem at Spotify (502), or no answer (504). Names of songs, artists, playlists and devices are other people's text, with control and hidden characters taken out and cut at 120 characters; the tools say to treat them as untrusted.

Each Spotify call adds a line to `docker compose logs api`: what it was (like `pause`, `search`, `play (album)`, `add 3 to a playlist`), Spotify's status, how long it took, Spotify's reason code and wait when it gave them, plus counts (devices and how many active, search results and kinds, playlists and how many yours). Signing in, renewing and signing out each add a line with the time taken, the number of permissions and whether a new refresh token came. Never a token, the code, the verifier, the state, the Client ID, a device or playlist id, a Spotify address or what was searched for.

Claude Code reads it with `get_spotify_playing`, `get_spotify_devices`, `get_spotify_queue`, `get_spotify_search` and `get_spotify_playlists`, allowed without asking like the other read tools, and changes it with `spotify_play`, `spotify_pause`, `spotify_next`, `spotify_previous`, `spotify_seek`, `spotify_volume`, `spotify_shuffle`, `spotify_repeat`, `spotify_queue_add`, `spotify_transfer`, `spotify_playlist_add` and `spotify_save`, which always ask first and aren't there in read-only mode. Jarvis has them too: see `JARVIS_MUSIC_YES`. To play through the server's own speakers it would need a Spotify Connect receiver on the server, which isn't part of this: record 0075 lists the maintained ones.

### The weekly digest
A job on the server writes what you've been doing in your Claude Code sessions (record 0076): `host/digest.sh`, installed as `/usr/local/bin/home-hub-digest` and run by the systemd timer `home-hub-digest@<you>.timer` as your own user, never root. Like the backup, it's switched on and off by enabling or disabling its timer; with the timer off nothing runs, and Jarvis only reads its file with `JARVIS_DIGEST=on`. The timer fires once a day at 04:40 London time (up to 10 minutes later, at random), and `Persistent=true` runs a missed one when the server comes back. Each time, the script decides whether a digest is due.

Its settings are in `host/digest.env` (git-ignored; copy `host/digest.example.env` to start), read the way `ears.sh` reads `ears/.env`:
- `DIGEST_REPOS`: the folders of the Claude Code sessions to read, up to 4, with commas between, like `~/docker,~/hub-memory`. Each one's transcripts are found the way `host/jarvis.sh` finds the sessions' notes: `~/.claude/projects/` (or `$CLAUDE_CONFIG_DIR/projects`) and the folder's full path with every character other than letters and digits turned into `-`. Only the `.jsonl` files at the top of that folder are read, not subagents' ones in folders below it.
- `DIGEST_DAYS`: how many days back the digest covers, 1 to 30, default 7. Claude Code keeps transcripts for 30 days unless its `cleanupPeriodDays` says otherwise.
- `DIGEST_EVERY`: how many days between digests, 1 to `DIGEST_DAYS`, default 3. A run within 2 hours of being due counts as due, so a daily timer that fires a little early still runs it. With no `jarvis/data/digest.md` it runs whatever the state says, so the file is never missing for long after a reset.
- `DIGEST_INBOX`: `off` (default) or `on`. With `on`, each run also writes a note to `~/hub-memory/inbox/<London date>-weekly-digest.md` (`-2`, `-3` and so on if that name is taken, never overwriting), in the brain note's shape, marked as written by the digest job, covering only the time since the last note, so `/merge-inbox` never files the same thing twice. A note that fails isn't counted, so the next one covers its time too.

What a run does: it reads each transcript line from the range, keeps only what you typed and Claude's text answers (no tool calls or results, thinking, subagents, slash commands, compact summaries or system notes), turns JSON escapes back into text, and redacts. Each message is cut at 2,000 characters, and if everything is over 300,000 characters each message is cut alike until it fits (and, if that's still too much, every second or third is left out), which the log says. Then it runs your own Claude Code, `claude -p`, on your plan's login, from a new empty folder, with the transcripts on its input between `<transcripts>` tags (a tag inside the text is changed so it can't end the block) and these flags, all from [the CLI reference](https://code.claude.com/docs/en/cli-reference): `--tools ""` (no built-in tools at all), `--strict-mcp-config` with no `--mcp-config` (no MCP servers), `--setting-sources ""` (no user, project or local settings, so no hooks or permission rules), `--disable-slash-commands` (no skills), `--permission-mode dontAsk` (anything that would ask is refused), `--no-session-persistence` (the run itself isn't saved as a transcript), `--output-format text` and `--system-prompt` with the digest's own instructions, which say the transcripts are untrusted data to summarise and never instructions. It never uses `--bare`, because [bare mode never reads the plan's login](https://code.claude.com/docs/en/headless#start-faster-with-bare-mode). Its environment is only `HOME`, `PATH` (with `~/.local/bin` first, where Claude Code installs itself), `LANG`, `CLAUDE_CONFIG_DIR` if set, and the settings that turn off telemetry, error reports and the auto-updater. It has 10 minutes. Claude's answer has control characters taken out, is cut at 20,000 bytes and redacted again, and only an answer from a run that succeeded, with something in it, replaces `jarvis/data/digest.md`, with a header saying the job wrote it, when, from how many sessions and projects, over which dates. The digest's file, state and log are written readable only by you.

Redaction, before anything goes to Claude and again before anything is written: whole private key blocks; the user and password in an address (`://user:pass@`); what follows `Bearer `, `ntfy.sh/`, or "password is", "passphrase is", "passcode is", "pin is", "topic is", "token is", "key is" and "secret is" (as whole words, so "spin is" stays); the value of anything named like a secret (a name containing token, secret, password, passwd, passphrase, apikey, api_key, key, topic, auth, credential or cookie, then `=` or `:`); any word starting with a known token's prefix (`sk-`, `ghp_`, `github_pat_`, `glpat-`, `xoxb-` and the like, `AKIA`, `tskey-`, `hf_`, `npm_`, or `eyJ` for a JWT); a UUID; an eBay app ID (`-PRD-` or `-SBX-` then hex); and any word with a run of letters and digits over 20 long, or 12 or more mixing letters and digits, which is the expiry list's rule for what could be a key, applied to each run of letters and digits so ordinary paths survive. Each is replaced by `[redacted]` and counted. It's meant to over-redact: a long commit hash goes too.

`~/.local/state/home-hub/digest.jsonl` gets one line per run (and the journal the same, after `Digest:`): when, the result (`written`, `failed`, `empty`, `no-messages` or `dry-run`), how it was run, `DIGEST_DAYS` and `DIGEST_EVERY`, projects found, sessions, messages, messages kept, days that had messages, bytes in and out, redactions in and out (counts only), how far messages were cut and whether some were left out, Claude's seconds and exit code, the whole run's seconds, and the same numbers for the inbox note (or `off`, or why there was none). Never a word of the transcripts or the answer. A check that finds nothing due prints one line to the journal and logs nothing. `~/.local/state/home-hub/digest-state` holds the last digest's time and how far the last note went. Only one run at a time: a second says so and stops. The lock, log and state are kept there rather than in `jarvis/data`, which Jarvis's container can write to, and the job stops if `jarvis/data` or `jarvis/data/digest.md` is a link.

By hand from `~/docker`: `bash host/digest.sh --dry-run` reads and redacts and prints the numbers without asking Claude or writing anything; `bash host/digest.sh --force` writes a digest now whether or not it's due. Both use your plan only when they ask Claude, which `--dry-run` never does. Claude Code's docs say the transcripts' format is internal and changes between versions, so a Claude Code update can stop it finding anything: a `no-messages` result with sessions you know were busy is the sign.

### Talking to Jarvis from the phone
`TALK` switches on the hub's side of talking to Jarvis from the phone page (record 0078); Jarvis's side is `JARVIS_PHONE` (his settings, below). Hold the microphone button in the middle of the page's bottom bar while you talk, and let go to send. What he heard shows on the phone, then his answer, then his voice plays as soon as it's ready. He answers in the chat he's already in, after anything he's in the middle of, and the server's speakers stay quiet. If he needs a yes, it's asked on the phone with Yes and No buttons, and no answer within a minute counts as no. He asks the hub's mode before each phone question, whatever `JARVIS_MODES` says, and in guest mode says no to the phone with a line, without hearing it; if the hub's mode can't be read, he says no too, in case it's guest mode. What you say from the phone goes to Claude as it is: his own code's spoken words (a mode's name, note this, find my phone, train times, snooze or done for a reminder) aren't caught from there, so use the page's own buttons for those. Claude is told which questions came from the phone.

- The microphone only works on a secure page, so use `https://hub.home`, which needs Caddy's root certificate installed on the phone ("The hub page on the phone", above, says how). `http://hub.home` now sends the page on to https (record 0083); if the page is ever opened somewhere that isn't secure, the button says so instead.
- The page records with the browser's microphone, turns it into 16-bit mono sound at 16,000 samples a second itself, and posts it to `POST /talk` (at most 30 seconds, `application/octet-stream`). The hub keeps it for Jarvis, who asks with `GET /talk/next`, which waits up to 20 seconds for one; the hub counts him as running while he's asked in the last 45 seconds, and refuses a recording when he isn't. The page asks the hub whether he's running every 30 seconds on the Home tab (and when it comes back into view), greys the button when he isn't, and won't record then, so you don't talk for nothing. At most 3 wait at once, and one he doesn't take within a minute is dropped.
- Jarvis turns it into words with ears's Whisper and posts them to `POST /talk/<id>/heard`, then his answer to `/reply` (or why he couldn't to `/failed`), any yes he needs to `/ask` (the phone answers at `/answer`), and his voice as a WAV to `/voice`, or to `/no-voice` when it couldn't be made, so the phone stops waiting for it. The phone follows it all at `GET /talk/<id>` and plays `GET /talk/<id>/voice`. One he took but never answered, as when he was restarted part-way, fails after 6 minutes.
- Everything is kept in the hub's memory only: the sound goes as soon as Jarvis takes it, and everything about a recording is forgotten after 10 minutes, 20 at most (checked every minute). `docker compose logs api` has a line when one arrives (its id and size), when Jarvis takes it, and when he answers or can't; never the words.
- Every route is behind the hub's token like the others, and a 404 that says so while `TALK` is off.

### The wall
`WALL` switches on the hub's side of showing Jarvis on a wall or a TV (record 0080); Jarvis's side is `JARVIS_WALL` (his settings, below). Jarvis tells the hub what he's doing as it happens, and the hub keeps the latest for a screen to read.

- What he's doing is one of `waiting`, `heard` (a moment after "Hey Jarvis" or the talk button), `listening`, `thinking`, `looking` (a look-up), `speaking`, `done` (a moment after an answer, once he's quiet), and `needs` (waiting for your yes). With `JARVIS_EARS=wake` he also says whether ears is muted. With it he sends what ears heard you say, with whose voice it was when `JARVIS_VOICES` is on (`owner`, `unknown`, or another known voice as a number from 0 to 4, given out in turn as voices are first heard, so up to five never share one; it starts again when he restarts; never a name), and his own words as he writes them, the last 600 characters, for questions said out loud. A question typed or asked from the phone shows him working and needing you, but never its words or his answer. A retry starts his words again.
- He posts it to `POST /wall/jarvis` whenever it changes (at most every quarter of a second), and every 20 seconds anyway. A screen reads it with `GET /wall/jarvis?after=<seq>`, which waits up to 20 seconds for something newer than the `seq` it last saw (`-1` for straight away). The hub counts him as running while he's posted in the last 45 seconds. Jarvis stops sending words 45 seconds after they came and the hub forgets them after a minute; both keep them in memory only. `POST /wall/jarvis` and `GET /wall/jarvis` log only warnings, so `docker compose logs api` never holds the words.
- `WALL_TOKEN` is a second token, only for screens: it reads `GET /wall` and `GET /wall/jarvis` and nothing else. It can't post his state, change a mode, ring the phone or reach any other route, so a TV in a room guests sit in, which may not trust Caddy's certificate, carries nothing that can act. It must be 32 to 200 printable characters with no spaces, and not the same as `API_TOKEN`; make one with `openssl rand -hex 24`. A screen logs in once with `POST /wall/login` and `{ "token": "..." }`, which sets a `wall_token` cookie (HttpOnly, SameSite Strict, kept a year); `POST /wall/logout` clears it, and needs no token. The hub's own login never takes it, and the wall's login never takes the hub's token. Either token also works as a Bearer header.
- `WALL_SPEAKING` is how the wall shows him speaking, `wobble` or `string`. `WALL_TOKEN` and `WALL_SPEAKING` are only needed while `WALL=on`.
- The page is `hub.home/wall.html` (record 0081), made for a TV or a projector: open it full screen, type the wall's token once, and leave it. It reads `GET /wall` every 30 seconds for everything but Jarvis, and follows him with `GET /wall/jarvis`.
- `GET /wall` is the one picture the page needs, put together by the hub from its own reads and kept 20 seconds so several screens share it: the day and London's time, the phase, the mode, the speaking style, the orbit's items (the server doctor's checks, the next train, the last backup, today's deal alerts as a count and never a listing, the next reminder, the alerts, and what Spotify is playing), the next train in full, the next three reminders in the coming day, and the song. Parts that are switched off are left out; a part that fails or takes over 5 seconds shows as "couldn't check" and the rest still come. The server doctor's answer is kept 5 minutes and the departure board's 1 minute (each doctor run still shares the doctor's own 10-second answers), so while a screen is open the wall adds at most one board call a minute (two with `TRAINS_CHANGE_AT`) and one qBittorrent and Jellyfin call every 5 minutes, around the clock. Spotify is asked with each picture, about every 30 seconds, with one `playback state` line in the API's log each time.
- What it shows, following the B3 designs:
  - Daytime: Jarvis in the middle of a dashed orbit, with B's labelled items and big numbers spread evenly round it, the inner ring with its two slowly turning dots, and A's green, blue and yellow arcs (the server, the backup and the alerts, turning orange when one needs a look).
  - Morning: from `TRAIN_ALERT_REMINDER` to the end of `TRAIN_ALERT_WINDOW`, on `TRAIN_ALERT_DAYS`, with `TRAIN_ALERTS=on`, the next train drifts to the middle beside him, with how long until it leaves.
  - Something arrives: a new item on the orbit, or more deal alerts or alerts, and sparks burst off him; the new thing sits in the middle for 6 seconds, then flies out to the orbit.
  - Bedtime: in bedtime mode the orbit fades to C's quiet line, with the time, one line on how things are, the next reminder and the next train, and he goes sleepy.
  - What drifts to the middle, first match wins: anything that needs you (a failed backup, alerts, a server problem), a timer in its last 3 minutes, something new, then the morning train. The other items glide round to space themselves out as things come and go.
- Jarvis's twelve poses: waiting, heard you, listening, thinking, looking it up, speaking, done, needs you, muted, sleepy (bedtime), guest mode, and can't connect (the page can't reach the hub twice in a row); "Jarvis is off" when he hasn't posted in 45 seconds. Speaking is the wobble, or the string with `WALL_SPEAKING=string`. While Spotify is playing, the sun ring pulses round him when he's quiet. The next reminder inside the hour shows as a ring that empties clockwise, like a clock.
- What was heard shows under him for 8 seconds: "You said" in the mode's colour for your voice (or any voice, with `JARVIS_VOICES` off), and "Heard" for anyone else's, in one of five colours of its own, none of them a mode's colour, given out in turn so up to five people never share one, or plain white for a voice no voiceprint matches. His words show for 10 seconds, as many whole sentences from the end as fit, for questions said out loud only. Words stay on in guest mode.
- The whole wall takes the mode's colour, as on the phone page's mode buttons: normal blue, gaming orange, coding yellow, bedtime soft blue, guest green, away grey.
- The ground is pure black, which is no light at all on a projector. Every word and number is big and still; only Jarvis, the rings and the dots move. The page scales to fit any screen and keeps its shape. It loads no fonts, like the phone page, so it uses the screen's own.
- Set-up mode fits the wall to a shape on a wall (record 0082). Move the pointer or press a key and a "Fit to the wall" button shows for 5 seconds (or press F). Drag the four numbered corners onto the corners of the space, pick one and nudge it with the arrow keys (Shift for 10 pixels), then save; Reset goes back to filling the screen, and Cancel or Escape puts back what was there. A shape that folds over itself, is mirrored or has a side under 40 pixels isn't used. The fit is kept in that browser (`localStorage`), for that screen size only, so a different screen starts plain; if the browser won't keep it, it lasts until the page is closed. How it works: the four corners of the page and the four corners you dragged make eight equations, which `hub/wall-fit.js` solves for the eight numbers of a perspective map, and the page is drawn through it as a CSS `matrix3d`. Everything outside the shape stays black.
- On the Xbox: open Microsoft Edge, go to `https://hub.home/wall.html` and click past the certificate warning (nothing found shows an Xbox can be told to trust Caddy's certificate; past the warning the connection is still encrypted, though Edge can't check it's really the server), type the wall's token, and press the controller's menu button for full screen. Plain `http://hub.home/wall.html` is sent on to https (record 0083). The wall's token can't do anything but show the wall, so a screen that gives it away gives nothing that can act.
- While `WALL` is off every route is a 404 that says so to the hub's token; the wall's token gets a 401, as it does anywhere it isn't allowed.

### Jarvis's settings
Lines in `jarvis/.env`. Jarvis prints the `JARVIS_` ones in one line when he starts.
- `ANTHROPIC_API_KEY`: required.
- `JARVIS_LOG`: `on` or `off`, required, like the API's switches. Logs each answer's numbers, never its words, for `npm run compare`.
- `JARVIS_ENGINE`: `sdk` (default) or `api`.
- `JARVIS_THINKING_HISTORY`: `keep` (default) or `drop`. Only the plain API engine uses it.
- `JARVIS_LENGTH_HINTS`: `note` (default) prints the chat-length note below; `jarvis` gives Jarvis the chat's size with each question once it's long, and leaves the suggestion to him. The log records which, so `npm run compare` can show how big chats got before you typed `new`. The size lines stay in a saved chat, so type `new` before switching this setting on a saved chat, or its answers mix the two.
- `JARVIS_LENGTH_WARN`: the chat size, in tokens, where the length warning starts. Default `80000`, 80% of Haiku 5.5's long-prompt line. Set it lower to hear sooner, or to suit another model.
- `JARVIS_LENGTH_CAP`: `off` (default), or a number of tokens above the warning. Once a chat's last request passes it, Jarvis says so, won't send more questions in that chat, and says to type `new`. A guard against long chats quietly costing more. A saved chat's size is kept with it, so the cap still holds after a restart: in the chat file on the plain API engine, and on the Agent SDK in `jarvis/data/chats/agent-sdk-size.json`, which only counts while the transcript it names is still the newest.
- `JARVIS_HUB_TOOLS`: `off` (default) or `on`. On gives Jarvis the hub's read-only tools (status, alerts, switches, downloads, library, Wi-Fi reconnects, backup, what's being watched, expiries, the server check, catch-up, and the deal watcher's status, searches, matches, one listing in full and what its rules hid, and Spotify's playback state, devices, queue, search and playlists), through the MCP server in `mcp/`, which he starts inside his own container in read-only mode (unless `JARVIS_HUB_ACTIONS` is on), as one more Node process (about 60 MB) while he runs. Both engines use them. The log records whether he was given them, so `npm run compare` keeps answers with and without the tools apart; on the Agent SDK, a chat whose MCP server didn't start still counts as with. If the MCP server doesn't start or list its tools, Jarvis says so (the plain API engine as he starts, the Agent SDK with his first answer) and carries on with the brain only; the note doesn't say why, and running `npm test` for `mcp/` is the first thing to try. On needs two things, and he won't start without either:
  - Start Jarvis with `bash host/jarvis.sh`, which passes in only `API_TOKEN` from `api/.env`.
  - The MCP server built in `mcp/`, which Jarvis runs from `mcp/dist`: `npm ci`, then `npm test`, as under Tests below. After `mcp/` changes, run `npm ci` and `npm test` for it again, or Jarvis keeps using the old build. `host/hub-update.sh` does both when a pull changes `mcp/`. If the tests fail, `mcp/dist` already holds the new build, because `npm test` builds before it tests, so fix it before you next start Jarvis.
- `JARVIS_HUB_ACTIONS`: `off` (default) or `on`, and only with `JARVIS_HUB_TOOLS=on`. On lets Jarvis use the hub's actions: scanning the library, stopping or starting a download, adding or cancelling a watcher, running a dev chore and Spotify's controls; and setting, cancelling and snoozing reminders, which don't need your yes (record 0070). Before each one (apart from Spotify's playback controls, as `JARVIS_MUSIC_YES` says), his own code (not his instructions) asks you in the chat what he wants to do, and waits for you to type `yes`, in any case. Anything else (even `exit`, which you'd then type again to leave) or no answer within 60 seconds means it isn't done, and he's told so. Ctrl+C closes Jarvis, so nothing runs. Only what you type after the question counts: in a terminal, anything half-typed before it is cleared. Two actions are asked one after the other. The log records whether this was on, so `npm run compare` keeps those answers apart.
  - The wait doesn't count towards the question's 2-minute limit, but it does show in that answer's time.
  - Jarvis takes only the hub tools he knows by name (the seven read tools, plus these three when this is on). A tool added to the MCP server later is left out on the plain engine until Jarvis is updated too; the Agent SDK still offers it to the model, but refuses it if he tries.

- `JARVIS_BRAIN_QUESTIONS`: `off` (default) or `on`, which needs `JARVIS_HUB_TOOLS=on`, and `MEMORY_UPLOAD=on` in `api/.env` to file anything (record 0061). With `on`, typing `/questions`, or saying "brain questions" or "any questions for me" (the spoken list is with the code words below, and with it off they go to Claude as before), has Jarvis ask you a gap question or two about your brain. He never asks unprompted, and he never writes to the brain.
  - Finding them: his own code sends Claude a fixed instruction through the chat you're in, asking it to read the brain with its usual read-only tools and find up to two things worth asking: two files that contradict each other, a dated fact that looks out of date, or something mentioned but never explained. Your answers aren't sent to Claude.

While they're open, everything you type is an answer except an empty line, `exit`, `quit`, `new`, `+`, `-` and `/` commands, and everything you say is an answer, code words included, except skip, never mind and a request to stop listening. A request to stop listening ends the questions like never mind, filing what you'd answered, and is never filed or asked: Jarvis says what he says outside them, and no follow-up listens again. So does ears muting itself because "stop listening" was all you said. An answer over 4,000 characters is refused and the question stays open.
  - Filing: when the questions end, by answering the last one, `never mind`, a request to stop listening, `new`, `exit` or the chat closing, his own code (not Claude, and not through any tool Claude has) sends one note to the hub's `POST /memory/inbox`, titled `brain questions`, so it's named like `2026-11-26-brain-questions.md`. For each question it holds `Jarvis asked:` with the question, the files, what looked wrong to him, and your answer marked `typed` (exactly as typed) or `spoken, as Whisper heard it`, with the date and time. It's written as questions and facts, never as instructions to change anything. Skipped gaps aren't filed, and if nothing was answered nothing is sent. If the hub refuses or can't be reached, he says why in plain words and prints the whole note in the chat so you can keep it.

- `JARVIS_CLOCK`: `off` (default) or `on` (record 0062). Jarvis has no clock of his own: Claude only knows what's in the chat. With `on`, his code gives him one, in two ways. - `JARVIS_INTRO`: `off` (default) or `on` (record 0067). - `JARVIS_GUEST`: `off` (default) or `on` (record 0069). Guest mode, for when someone else is talking to him. Typing `/guest`, or saying "guest mode" on its own (or "turn on guest mode", "switch to guest mode"), ends the chat and starts a fresh guest chat: he keeps his voice, the persona, the intro and the clock, and with `JARVIS_WEB` on a guest can look things up (`/lookup` or "look up"), each one marked `guest` in both logs. A guest chat has no brain (on the Agent SDK it gets no tools at all and a working folder that's empty; on the plain API, no tools but the look-up), no session notes, no hub tools or actions, no brain questions and isn't saved, and his instructions say he's talking with a guest and to share nothing about you beyond the intro. The hub's code words (notes, the phone, trains, the server check) and brain questions get "That isn't available in guest mode." without reaching the hub, train changes aren't said or shown (a line says one came in), and `new` starts another guest chat. Only typing `/guest off`, or the phone page with `MODES=on`, ends it, with another fresh chat that has everything back; your saved chat is left as it was. Saying "guest mode off", or any other mode, while in it gets "Only Phil can turn guest mode off" or "Modes can't be changed in guest mode", so a guest can't talk him out of it; until ears can tell your voice apart, that's on purpose. Guest answers go in the answer log with `guest: true`, and `npm run compare` keeps them in their own group. With `JARVIS_MODES` off, guest mode lives in Jarvis alone; with it on, it's the hub's mode, so the phone page's guest button switches him too. If the hub doesn't hear guest mode (it's down, say), he goes into guest mode anyway, privacy first, saying "Guest mode is on, but the hub didn't hear, so your phone won't show it until the hub's back." He tells the hub as soon as it answers, and again every 15 seconds until the hub says guest back, and until then the hub's own mode never takes him out of it; typing `/guest off` before then leaves it in Jarvis alone and puts back the mode from before. With `MODES=off` in the hub he goes into guest mode too, says the phone won't show it, and `/guest off` leaves it in Jarvis the same way. With `JARVIS_EARS=wake`, guest mode always lets every voice through ears's voice ID (below), whatever `JARVIS_VOICES` says, so guests can be heard with `require`.
- `JARVIS_MODES`: `off` (default) or `on`, needs `JARVIS_HUB_TOOLS=on` and `MODES=on` in `api/.env` (record 0068). Jarvis follows the hub's mode, asking `GET /mode` every 5 seconds, and changes it with `POST /mode`. Said on its own (politely if you like, or as your last sentence): "bedtime" (or "bedtime mode", "I'm going to bed", "time for bed"), "gaming mode", "coding mode", "normal mode" (or "back to normal"), and "I'm back" when you're not in normal mode or "good morning", "morning", "I'm up" or "I'm awake" during bedtime, which go back to normal. "I'm not here" (or "I'm going out", "I'm going away", "I'm heading out", "away mode") sets away at once and asks "When will you be back?", listening for the answer with `JARVIS_FOLLOW_UP` set, or take it typed; whatever you say next is read as when, and if it can't be read away stays on until you're back. "I'm away until Sunday evening" does it in one go. "Bedtime at half twelve" (or "set bedtime for 1 am") schedules bedtime once through the hub's reminders (`REMINDERS=on`). When is worked out by one small question to the chat model on Jarvis's API key, given London's time now and your words, 4 seconds at most, that can only answer a London time within 60 days or unknown. Typed: `/mode` shows the mode, and `/mode normal`, `bedtime`, `gaming`, `coding` or `away` changes it. In bedtime, gaming and away he says nothing you didn't ask for: train changes are shown but not said (coding and normal still say them), and he still answers what you ask. A mode changed from the phone page or by the hub's own times is shown as a line, never said. Mode words aren't asked of Claude or logged; with this off they go to Claude like anything else. With `JARVIS_GUEST` off, the hub going into guest mode (from the phone page, say) holds him: he won't answer, look things up, use the hub's code words or start brain questions until it's out of guest mode, which `/mode normal` or the phone page does.
- `JARVIS_REMINDERS`: `off` (default) or `on`, needs `JARVIS_HUB_TOOLS=on` and `REMINDERS=on` in `api/.env` (record 0070). Jarvis asks the hub's `GET /reminders/due` every 10 seconds, and when one is due and he's quiet he says it, like "Reminder: Take the bins out.", then, with `JARVIS_FOLLOW_UP` set, listens for your answer as after any spoken answer. For five minutes after, "snooze" (10 minutes), "snooze for 20 minutes" (or "snooze it five minutes", "remind me again in half an hour", up to 4 hours), "done" (or "I've done it") and "cancel it" (or "stop reminding me"), said or typed, go to the hub for that reminder, never to Claude; anything else is asked as usual. Reminders due before he started are skipped, except any from the last 2 minutes, and one the hub sends late says sorry for it. Your phone always gets it from the hub too. Which modes he says them in: normal, coding and gaming; in bedtime only one marked urgent; never when away or in guest mode, where a line shows it came in (in guest mode without what it says). Setting one is Claude's: say "remind me in 20 minutes to check the oven" and he uses the hub's reminder tools. Setting and snoozing need no yes from you; cancelling one through Claude does, since a cancelled reminder is gone (saying "cancel it" just after one goes off is handled by his own code and needs none). The tool can't set a timed mode switch: "bedtime at half twelve" is his own code's, so text Claude reads can't schedule a mode.
- `JARVIS_SESSIONS`: `off` (default) or `on`, needs `JARVIS_HUB_TOOLS=on` and `SESSIONS=on` in `api/.env` (record 0074). Jarvis asks the hub's `GET /sessions/changes` every 10 seconds, and when a Claude Code session starts waiting on you or stops, he says "The docker session is waiting on you." (or "has stopped") once he's quiet, but only in coding mode; in the other modes it's a line on screen, and in guest mode nothing at all. Changes from before he started are skipped. Starting and stopping a session is a dev chore, through the hub's tools with your yes.
- `JARVIS_PHONE`: `off` (default) or `on`, needs `JARVIS_HUB_TOOLS=on`, `JARVIS_EARS=push` or `wake` (for ears's Whisper, which he uses to hear the phone), and `TALK=on` in `api/.env` (record 0078). Jarvis asks the hub for recordings from the phone, turns each into words with Whisper, prints it after `From your phone:`, and answers it in the same chat, with the server's speakers quiet. Claude gets it with `[Asked from his phone, through the hub.]` on a line after it, and none of his code words are matched on it. His answer goes back to the phone as text, then in his voice when his voice is on (as text only when it's off). A yes he needs goes to the phone, without the "type yes" wording, with a line in the terminal. Before each one he asks the hub's mode (`GET /mode`), whatever `JARVIS_MODES` says, and in guest mode (with or without a guest chat) he says no to the phone with a line and hears nothing; if the mode can't be read he says no as well, and with `MODES=off` in the hub there's no guest mode, so he answers. A phone question waits while he's talking, listening or asking brain questions, and is taken when he's quiet. The answer log marks each question from the phone with `phone: true`.
- `JARVIS_WALL`: `off` (default) or `on`, needs `JARVIS_HUB_TOOLS=on` and `WALL=on` in `api/.env` (record 0080). Jarvis tells the hub what he's doing, what ears heard and his own words, for the wall ("The wall", above). When he starts he prints whether the hub took it, waiting up to 3 seconds for that first post, and while he runs a line says when the hub stops answering and when it's back. Nothing else he does waits on the hub. With `JARVIS_LIVE_FACTS=on` he's told that a screen in the room shows what he says to spoken questions.
- `JARVIS_VOICES`: `off` (default) or `on`, needs `JARVIS_EARS=push` or `wake`, and ears's `EARS_VOICE_ID` set to `observe` or `require` with voiceprints made (record 0072). Jarvis reads who ears thinks each spoken question came from and shows it under what you said, like `(voice: yours, 0.82)`, `(voice: alex, 0.71)` or `(voice: one Jarvis doesn't know, 0.20)`, and the answer log records `owner`, `known` or `unknown`, never the name. Your voice (ears's `EARS_VOICE_OWNER`) can end guest mode by saying "guest mode off" and change modes while in it; nobody else's can. A spoken question ears gave no verdict on, usually because it had under a second of speech, counts as not yours: it's answered, but its mode words (any mode, guest mode off included, but not guest mode on, which only takes things away) get "I couldn't tell it was you, so I won't change the mode. Say it again, a bit longer." Another voice he knows can still change modes outside guest mode, as before. While he's in guest mode he tells ears to let every voice through even with `require` (`POST /wake/guests`), and stops when guest mode ends, and again when he starts and when he ends in guest mode, so it can't stay open after him; he does that whenever `JARVIS_EARS=wake`, with this on or off (with `push`, voice ID never holds a recording back, so there's no door to open). Ears's scores haven't heard your microphone or your room yet, so try `observe` for a while before relying on this.
- `JARVIS_OTHER_VOICES`: what he does when a question comes in a voice that isn't yours, with `JARVIS_VOICES=on`. `answer` (default) answers it as he would you; guest mode is what limits people. `name` answers it too, but tells Claude who asked, with a line like `[Said by alex, going by their voice, not Phil.]` after the question (or that the voice isn't known), so he doesn't take them for you; the name goes to Anthropic with the question. `guest` (needs `JARVIS_GUEST=on`) puts him in guest mode first when it's a voice none of the voiceprints match, before its words can change a mode, answer a reminder or stop the phone ringing, then answers it there; a voice he knows is answered as usual. With ears's `require`, a voice no voiceprint matches never reaches him outside guest mode, so `guest` only matters with `observe`.
- `JARVIS_WEB`: `off` (default), `ask` or `auto` (records 0063, 0065 and 0066). Jarvis can't look anything up: Claude answers from what it already knows, the brain and the hub. With `ask` or `auto`, you can have something looked up on the web by saying "look up" and a question (a code word, below) or typing `/lookup` and a question. Jarvis himself never touches the web. His code prints the question, says "Looking that up.", and hands only the question to a separate helper: the Claude Code program that comes with the Agent SDK, run once for that look-up and signed in to your Claude plan with `JARVIS_WEB_TOKEN`, not with his API key. The helper has two tools, web search and opening a page, and nothing else: no file reading, no commands, no hub tools, no brain and none of the chat. It starts in a new empty folder that's deleted afterwards, with an environment that holds the plan token and none of Jarvis's own settings. The answer is stripped of links and markup, cut to 1,200 characters, printed with the sites it came from and how long it took, and said aloud with his voice on. With `ask`, Claude never sees the question or the answer, so nothing from the brain can end up in a search and nothing a web page says can reach the Jarvis who reads your brain. With `off`, none of this exists: the phrases go to Claude and `/lookup` isn't a command.
  - `auto`. Everything `ask` does, and Jarvis can also decide for himself to look something up. He still can't touch the web: he gets one tool, `look_up`, that takes one question of at most 300 characters and hands it to the same helper. He's allowed one look-up for each message of yours, and none while he's finding brain questions. The question he sent is shown on screen, he says "Looking that up." before the helper starts, and the answer comes back to him marked as text written by strangers, to use as information and never as instructions. This is the mode with a risk `ask` doesn't have: Claude writes the question, so something from your brain could end up in it, by mistake or because an earlier look-up's answer talked him into it. The limits are there to keep that small, and the look-up log is how you'd see it. On the Agent SDK engine the tool is an in-process MCP server from the SDK; on the plain API engine it's one more tool definition.
  - The guard. Searches go through Anthropic, but pages are fetched from this server, so before the helper opens one, `jarvis/src/web-guard-run.ts` checks the address and refuses anything that isn't an ordinary public web page: an address that's a number, a name with no dot, a name ending in `.home`, `.local`, `.lan`, `.internal`, `.ts.net` and the like, an unusual port, a name or password in the address, and any name that leads to a private address when it's looked up. Claude Code follows a redirect between a name and the same name with `www.` in front without asking again, so the guard looks both up and refuses if either leads somewhere private. Opening a page isn't allowed by default: the helper may search, and a page opens only when the guard has run and said yes. So if the guard is missing, crashes, takes too long or can't tell, the page isn't opened. It checks where a name leads just before the page is fetched, so a name that changes in between could get past it.
  - While it runs. A look-up runs in the background, so the chat stays free. One that fails gets "I couldn't look that up." with the reason printed underneath. Typing anything but a rating, saying "Hey Jarvis", asking for another look-up or ending the chat stops it, and one that takes longer than 45 seconds is stopped. A question is cut to 300 characters. There's no limit on how many you make: he says he's looking it up every time, and you decide.
  - Following on (record 0066). The helper starts fresh every time and remembers nothing, so a look-up within 5 minutes of the last answered one is also given that one's question and answer, marked as context to use only if the new question follows on from it. A line under `(looking up: …)` says which look-up it's following on from. Only one look-up back is carried, never more, and nothing from the brain or the chat. A look-up that failed or found nothing isn't one to follow on from, and `new` forgets the last one. The helper is told to say what it took an unclear question to mean and never to offer to look again, since it can't hear the answer.
  - After a spoken look-up. With `JARVIS_FOLLOW_UP` set, a look-up asked out loud whose answer came back opens a follow-up window, like any answer. What you say in it, unless it's a code word, goes first to a small check: his code asks the fast model one question, with the last look-up's question and answer and what you said, and it can only answer `look` or `chat`. On `look` it's looked up again, following on; on `chat`, no answer within 3 seconds, or a failed check, it goes to Jarvis like any follow-up. A line under what you said shows which, and how long the check took. It's sent with Jarvis's API key, costs a fraction of a cent, and the next window after one of his own answers isn't checked. Saying "look up" in the window is a look-up already, so it skips the check.
  - `JARVIS_WEB_BY`: `claude` (default) or `api` (record 0064). Who does the looking up. `claude` is the helper above. `api` asks Anthropic's API with its own web search tool switched on, in one request from Jarvis's code with his API key: no program is started and no page is fetched from this server, since the search results reach Claude with their text, so the guard has nothing to do. It makes at most three searches for a look-up and is sent the question and nothing else, like the other helper. It's here so the two can be compared: each look-up's line in the logs says which did it, and `npm run compare` shows them side by side. With `api`, `JARVIS_WEB_TOKEN` isn't needed.
  - What it costs. Look-ups by `claude` run on your Claude plan, so they come out of the same allowance as your chats and Claude Code, not out of API credits. Claude Code still reports what each would have cost at list prices, which `npm run compare` shows. Look-ups by `api` are paid for from API credits: a cent a search, plus the tokens.
  - `JARVIS_WEB_TOKEN`: needed when `JARVIS_WEB` isn't `off` and `JARVIS_WEB_BY` is `claude`. `claude setup-token`, run on the server, prints a token that lasts a year; put it in `jarvis/.env` on one line. It's a secret: never in the repo and never pasted into a chat. Jarvis reads it once as he starts and removes it from his own environment, so only the helper is ever given it. Its expiry date is worth a line in `expiry/items.json`.
  - `JARVIS_WEB_LOG`: `off` (default) or `on`. With `on`, each look-up adds a line to `jarvis/data/look-ups.jsonl`, which git ignores: its numbers, the question that was sent, the sites it found, opened and was refused, whether it followed on from the one before (whose question and answer then went too) and how long the check took when it came from a follow-up, and for one that failed, what went wrong in the helper's own words. Never the answer. A look-up is logged in the chat that started it, including one stopped by typing, `new` or `exit`. It's the one log that holds your words, because the question is the one thing that leaves the server; delete the file to clear it. With `JARVIS_LOG=on`, each look-up's numbers alone also go to the answer log, and `npm run compare` reports them: how many, how they ended, how long they took and how long Claude Code took to start, searches, pages opened and refused, tokens, the estimated cost, what kind of thing went wrong, how many followed on, and how each one signed in: "your plan token, no API key" means Claude Code ran on your plan, and "an API key in Claude Code's environment" would mean it didn't.
- Not listening to himself: every chat with his voice on and `JARVIS_EARS=push` or `wake` holds the wake word from when he starts answering (and while he says his start-up sentence) until his last sound has played, renewing the hold every 5 seconds, so ears doesn't listen to him. A recording that's already running while any chat holds it, as when a second chat starts speaking during it, hears silence for that stretch instead of him (record 0040). Holds need `EARS_WAKE=on`: with the wake word off, ears takes none, so a `/talk` recording made while another chat is speaking hears him. Ears starts again half a second after the last chat lets go, and a hold runs out by itself after 15 seconds if a chat stops renewing it. A chat with `JARVIS_EARS=off` can't reach ears to hold it, so don't have one speaking while a wake chat is open. With `EARS_INTERRUPT` set in `ears/.env`, ears does listen for some things during a hold, so you can interrupt him: see ears below (record 0055).
- `JARVIS_SOUND_CARD`: the speakers' name under `/dev/snd/by-path`, like `pci-0000:04:00.6`. `ls -l /dev/snd/by-path` lists the names and the card each leads to, and `cat /proc/asound/cards` says which card is which. `bash host/jarvis.sh` reads it, for the sound test and for a chat with his voice on: it follows the name to the card's number for this boot, and passes in only that card's mixer and speakers. Names stay the same after a restart; card numbers might not, and both cards on this server are called `Generic`, so their `CARD=` names can swap too. Set it again on a new server. Only the script reads it, so it isn't on his start-up line; his `Voice:` line names the card it led to.
- `JARVIS_VOLUME`: `0` to `100`, default `80`. Before anything plays, Jarvis sets the card's `Master` control to this and unmutes it (`0` mutes it), because the server forgets the level when it restarts and comes back muted (record 0015). The sound test does this, and so does a chat with his voice on. It's checked every time he starts, voice or not.
- `JARVIS_CHATS`: `fresh` (default) saves nothing; `resume` saves the chat in `jarvis/data/chats/` and picks it up next time.
  - Saved chats hold everything said, brain text included. Only their owner can read them, and backups copy them.
  - Every question sends the whole saved chat. On Haiku 5.5, a request over 100,000 tokens costs five times as much. Jarvis doesn't trim saved chats yet. The Agent SDK only summarises a chat when it nears its context limit (about 990,000 tokens in a test), so it pays the higher rate long before that.
  - When a chat reaches `JARVIS_LENGTH_WARN` (80,000 tokens unless set), Jarvis says once that it's getting long (once per start of Jarvis). Past 100,000, where Haiku 5.5's long-prompt price starts, he says so after every answer, with how to start a new one (unless `JARVIS_LENGTH_WARN` is set higher, when he waits for that). It goes by each answer's last request, and works in fresh chats too. With `JARVIS_LENGTH_HINTS=jarvis`, Jarvis is told the size instead and suggests a new chat himself.
  - Type `new` to start a new chat without leaving Jarvis. In a saved chat, the old one is moved to `jarvis/data/chats/old/` (private, the newest 10 per engine kept), Jarvis says exactly where, and it isn't carried on. To get it back, move it back by hand. A plain API chat brings its size back with it (if it was saved since sizes were kept); an Agent SDK one usually has no size known until its first answer. A leftover `*.saving` file is a save that was cut off, and is safe to delete.
  - Lines shaped like a command (a `/` then one word, like `/clear`) aren't sent to Jarvis, on either engine. The Agent SDK would otherwise run them as its own commands; `new` does that job on both. Paths like `/etc/hosts` go through as normal.
  - Run one Jarvis at a time on a saved chat: with two, one of them's questions won't be carried on.
  - The engines save differently: the Agent SDK also keeps questions that failed or were stopped, and the plain API engine keeps only answered ones. On the plain API engine, thinking is left out of the saved chat for good with `JARVIS_THINKING_HISTORY=drop`, or after a thinking restart.

## Folders
- `api/`: the API. Fastify and TypeScript on Node 26, one module per folder in `src/modules/`, with each module's tests beside its code.
- `hub/`: the phone page, and `wall.html` with `wall.js`, `wall-logic.js`, `wall-fit.js` and `wall.css`, the wall's page (records 0081 and 0082). `wall-logic.test.js` and `wall-fit.test.js` test them with `node --test`.

## Running it
Secrets live in `.env` files that git ignores (`api/.env`, `homepage/.env`, `beszel/.env`, `jarvis/.env` and `ears/.env`), so they're never in this repo. The API also expects the brain's inbox at `../hub-memory/inbox`, and won't start without it. The backup's settings and password live in `/etc/home-hub/`, outside this folder and readable only by root.
- Start everything: `docker compose up -d`
- Rebuild the API after a change: `docker compose up --build --wait api`
- Pull from GitHub and rebuild only what changed: `bash host/hub-update.sh`, or `bash host/hub-update.sh --dry-run` to see what it would do. When `mcp/` changes, it also rebuilds the copy Jarvis runs. When Jarvis's packages change (`jarvis/package-lock.json`), it reinstalls them and runs his engine check, since a new Agent SDK brings a new engine. A change to his code alone needs nothing, because he builds himself each time he starts. Close Jarvis before updating: reinstalling packages replaces folders a running chat is using.
- Talk to Jarvis: `docker compose run --rm jarvis`. He's in the `jarvis` profile, so `docker compose up` never starts him. Type `exit` or press Ctrl+C to stop, and `--rm` removes the container. He needs `jarvis/.env` and the brain at `../hub-memory` (mounted read-only), and won't start without them. With `JARVIS_HUB_TOOLS=on`, `JARVIS_SESSION_NOTES=on`, `JARVIS_EARS=push` or `wake`, or his voice on, start him with `bash host/jarvis.sh` instead. He's on his own Docker network, `jarvis`, which only the API shares, so the API is the one container he can reach directly (when `host/jarvis.sh` gives him sound, for a chat with his voice on or for the sound test, he's also on `speech`, where he reaches Kokoro and Piper; with `JARVIS_EARS=push` or `wake` he's also on `ears`, where he reaches ears, Whisper and openWakeWord). Services with a published port or a `.home` name can still be reached through the server's address, as from any device on the LAN, and he can reach the internet, which he needs for Anthropic's API (record 0013).
- Jarvis always on (record 0079): `host/jarvis-always.sh`, installed as `/usr/local/bin/home-hub-jarvis`, keeps him running in a `tmux` session of his own, and the systemd unit `home-hub-jarvis@<you>.service` starts it at boot as your own user, never root, with `NoNewPrivileges`. In the session it starts ears once (with `JARVIS_EARS=push` or `wake`), which always starts muted, so the room's microphone stays off until `bash host/ears.sh unmute`; then it runs `bash host/jarvis.sh` and starts him again whenever he stops: after 5 seconds, or after a minute if he ran for less than a minute, so a setting he won't start with doesn't spin. Ctrl+C or `exit` in the chat stops him and he comes back; Ctrl+C during that wait stops the loop. `home-hub-jarvis attach` shows him (detach with Ctrl+B then D, and he keeps running), `status` says whether he's running, `stop` presses Ctrl+C in his session and stops the loop (closing the session if he hasn't stopped within 30 seconds, and stopping his container if it's still there), `start` starts him again and `restart` does both. His session is on its own `tmux` server, `tmux -L jarvis`, with 50,000 lines of scrollback and the mouse on, so the mouse wheel scrolls back through what he said; your own `tmux` and the session manager's (`tmux -L home-hub`) are left alone. With it on, Kokoro (or Piper), ears, Whisper and openWakeWord run all the time, which is about 2 to 3 GB of the server's memory (a rough figure from their limits and Kokoro's usual use, not measured together). `bash host/hub-update.sh` won't reinstall his packages or rebuild the hub's tools he runs (`mcp/`) while he's running (stop him first), and says to restart him when anything he uses changed. `bash host/jarvis-always.test.sh` tests the script with a pretend `tmux`, `docker` and Jarvis.
- Test Jarvis's speakers: `bash host/jarvis.sh sound-test`. It builds his image for sound, `home-hub-jarvis` (`jarvis/Dockerfile`: his usual `node:26-alpine` plus `alsa-utils`, from its cache after the first time), finds the card named by `JARVIS_SOUND_CARD`, sets `JARVIS_VOLUME`, and plays two short beeps, low then high. It adds `docker-compose.sound.yaml`, the only place Jarvis gets sound devices: his card's mixer and speakers, read and write, never a microphone, and the group that owns them (record 0014). The same file puts him on the `speech` network, where Kokoro is when it's running; the sound test doesn't use it. Without it, as with `docker compose run --rm jarvis`, he gets none and runs on the stock image. A newer `node:26-alpine` reaches his image only after `docker pull node:26-alpine`.
- Ears, the service that owns Jarvis's microphone, and Whisper, which turns what it records into text (records 0035 and 0037). Jarvis uses them with `JARVIS_EARS=push` (record 0038) or `wake` (record 0039). Both are in the `ears` profile, so `docker compose up` never starts them.
  - Set it up once. `ears/.env` holds `EARS_TOKEN`, at least 32 characters (`openssl rand -hex 32` makes one), and `EARS_MICROPHONE`:
    - `card`: a real microphone, on the sound card that `EARS_SOUND_CARD` names, by its name in `ls /dev/snd/by-path` (like `JARVIS_SOUND_CARD`). That can be the laptop's own card, `pci-0000:04:00.6`, for its built-in microphone (it works, seen on 20 Nov) or a headset's in its jack, or a USB microphone's own card. At start, ears sets the card's `EARS_MIC_CONTROL` (default `Capture`) to `EARS_MIC_LEVEL` (0 to 100, default 80) and switches capture on, because a card's levels go back to how the driver starts them after a reboot. `EARS_MIC_LEVEL=keep` leaves the card's levels alone. `EARS_MIC_BOOST` is left alone unless it's set: a whole number of steps from 0 to 10 sets the card's `EARS_MIC_BOOST_CONTROL` (default `Internal Mic Boost`) at start too, for a microphone that's still too quiet with `EARS_MIC_LEVEL=100` (record 0041). A card's boost only goes so high (3 on many laptops' chips, per `amixer`), and amixer stops at its top. A card that names its controls differently needs `EARS_MIC_CONTROL`; `docker run --rm --device /dev/snd/controlC1 node:26-alpine sh -c "apk add --no-cache -q alsa-utils && amixer -c 1 scontrols"` lists card 1's controls from a throwaway container. That gives the container card 1's mixer, so it could change the card's levels, and nothing else of the sound devices; never give a throwaway container all of `/dev/snd`, which includes every microphone.
    - `pretend`: a quiet tone, so the rules around recording can be tried with no microphone.
    - Left out: it records nothing.
  - Then run `bash host/ears.sh mute`, which makes `ears/switch/`; ears won't start without that folder. And download Whisper's model once with `bash host/ears.sh whisper-model`, about 82 MB into `whisper/models/base-int8`: the `base-int8` model from its pinned version on Hugging Face, checked by size and, for the model itself, by its SHA-256, plus the tokenizer that model leaves out, from `openai/whisper-tiny`, which faster-whisper would otherwise fetch every time it starts. Whisper's network has no internet, so it can't fetch anything itself. Both `whisper-model` and `start` check the four files are there at their right sizes, and won't go on with part of a model.
  - Check the microphone from where you'll talk to it with `bash host/ears.sh mic-test`, or `bash host/ears.sh mic-test 10` to wait 10 seconds first (up to 60) so you can get there (record 0041). Stay quiet for the first 2 seconds, which it measures the room from, then talk as you would to Jarvis. It records 10 seconds from `EARS_SOUND_CARD`'s microphone with ears's own `EARS_MIC_LEVEL`, `EARS_MIC_CONTROL`, `EARS_MIC_BOOST` and `EARS_MIC_BOOST_CONTROL`, so it hears what Whisper and the wake word would. Then it prints the room's level and what counts as speech, in the same words and on the same scale as ears's log line for the wake word, how long you were above that, your typical and loudest level, your longest pause (ears ends a wake-word recording after 1.5 seconds of quiet, or `EARS_WAKE_PAUSE`), whether anything clipped, and the one setting to change next if it's too quiet or too loud. Turning the microphone up raises your voice and the room together, so when your voice is under six times the room's level (or, with no speech, never above three times it), more gain can't help, and it says to get closer, quieten the room or try another microphone instead. Then it plays the recording back on `JARVIS_SOUND_CARD`'s speakers at `JARVIS_VOLUME`. Change one setting at a time and run it again; ears itself uses a changed setting after `bash host/ears.sh stop` and `start`. It records in a throwaway container from ears's image (built as `home-hub-ears`) that has only that card's microphone and mixer, and plays in one from Jarvis's image that has only the speakers and mixer. The sound goes from one to the other through a pipe on the server, never a file, and neither container has a network or keeps a Docker log. It's a command you run by hand, so it has no setting to switch it on, and it refuses to run anywhere but a terminal someone is typing in. Just before it records, if ears is running, it asks ears whether it's muted (`ask.js health`, which prints the status code and one word), because only one program can have the microphone open at a time, and ears comes back muted after a restart whatever the switch file says. If ears answers anything else, it stops and asks you to mute ears first; if ears doesn't answer clearly, it stops and says to wait or to stop ears. It never mutes or stops ears itself.
  - Start them with `bash host/ears.sh start`, and stop them with `bash host/ears.sh stop`, which stops openWakeWord too. Start builds ears's image from `ears/` (from its cache after the first time; `host/hub-update.sh` doesn't rebuild it), starts Whisper (and openWakeWord, with `EARS_WAKE=on`) and waits for it to be healthy, then starts ears. Stop ends them within a second or so. With `EARS_MICROPHONE=card` it adds `docker-compose.mic.yaml`, the only place ears gets a sound device: that one card's mixer and microphone, read and write, never its speakers, and the group that owns them. Started any other way, as with `docker compose up -d ears`, ears gets no device, and with `card` it then won't start, saying how to start it.
  - Mute or unmute it with `bash host/ears.sh mute` or `bash host/ears.sh unmute`. They write `ears/switch/mute`, which ears reads every 200 ms through a read-only mount, so no container can change it through its own mounts. Ears always starts muted, even if the file says unmuted: only an unmute it sees appear after it started counts, and each one counts once. If it can't read the file when it starts, what it first reads counts as old, so unmute again once it can. Muting ends a recording within about a second (one look at the file, plus a second if the recorder has to be killed), and so does a new unmute while recording, in case a mute came and went between two looks. If a mute can't be written, as on a full disk, the script removes the file instead, which also counts as muted.
  - Try it from inside its container: `docker compose exec ears node dist/ask.js state`, or `start`, or `stop`. It prints the status code and ears's answer, and exits with 1 if ears said no. `health` prints only the status code and the state's one word: it's what ears's health check runs, because Docker keeps what a health check prints, and the state can hold the text. Its API is `GET /state`, `POST /recording/start`, `POST /recording/stop` and `POST /recording/cancel` on port 8090, with `EARS_TOKEN` as a Bearer token. Every answer includes `lastId`, the number of the last recording that ended, and a start's answer includes `id`, the new recording's number. Numbers carry on from the time ears started, in milliseconds, so a restarted ears doesn't reuse one a chat may still hold, as long as the server's clock doesn't go back. Stop and cancel can name the recording with `?id=<number>`, and then act only on that one: one that has already ended while a newer one runs is refused with 409, and one ears has moved on from is refused with 410 (record 0040). Jarvis always names his; without `?id=`, as from `ask.js`, they act on whatever ears has. Cancel ends a recording without sending it to Whisper, drops the text if Whisper is already working on it, or clears the text if it's already made. It's on its own network, `ears`, which is internal and isolated. Its container runs with Docker's own init as its first process, so ears isn't process 1 (Linux ignores a stop sent to process 1 unless the program itself handles it), a read-only filesystem, every Linux capability dropped and `no-new-privileges`, so nothing in it can gain rights it wasn't started with. Whisper and openWakeWord share the network, and Jarvis joins it only through `docker-compose.talk.yaml`, with `JARVIS_EARS=push` or `wake`.
  - It reports one state: `muted`, `idle`, `recording`, `working` or `failed`. Failed means its recorder ended by itself or couldn't start, and it records nothing until it's unmuted again. A recording stops when asked, when ears is muted, after 30 seconds, or if more sound comes than 37.5 seconds' worth (a quarter extra, for sound arriving in bursts). Ending it ends the recorder and anything it started that's still in its process group; with the wake word on, recordings share one recorder, which ends when ears is muted or no wake chat is waiting. The recorder is `arecord` for a card, giving 16-bit mono at 16,000 Hz.
  - A recording that was asked to stop, or ended at its time or sound limit, is turned into text: ears is `working` while Whisper does it, records nothing new meanwhile, and gives Whisper a minute. The answer to `stop` waits for the text, and the state's `last` holds it (`text`), or why there's none (`textProblem`). A recording ended by a mute, by a new unmute or a cancel (even one that comes while a stop is still ending it) or by its recorder failing is never sent to Whisper, and a mute or a new unmute while Whisper is working drops its text even if it comes. The sound stays in ears's memory until Whisper has it, and Whisper writes each recording to a file in its `/tmp`, which is in memory, and removes it when it's done. Memory can be moved to swap, if the server uses swap. The text stays in ears's state until the next recording ends, ears is muted or asked to cancel, or ears stops; a mute or a cancel clears it and says so. Nothing writes it anywhere.
  - `docker compose logs ears` has a line for each start, stop (why, and how long), mute, unmute, text made (how long, never the words), text not made (why), text cleared by a mute, never the sound, and never the token unless a recorder prints it when it fails. Whisper would log every transcript at its normal level, and has no setting for that, so `whisper/sitecustomize.py`, which Python loads at start because `PYTHONPATH` points at it, lifts that one logger to warnings only. Its other lines, and any errors, still show in `docker compose logs whisper`; one says how long each recording was, never what was said.
  - The wake word (record 0039). With `EARS_WAKE=on` in `ears/.env` (it needs `EARS_MICROPHONE` set), `bash host/ears.sh start` also starts openWakeWord, and ears listens for "Hey Jarvis" whenever it's unmuted and a Jarvis chat with `JARVIS_EARS=wake` is open. With no such chat, the microphone is closed. While it listens, one `arecord` runs the whole time, and every recording, `/talk`'s included, takes its sound from it, because a microphone opened directly, as ears opens it, can only be open in one program at a time. Ears passes the sound to openWakeWord, and on "Hey Jarvis" it starts a recording. The recording keeps the half second before the detection (mostly the end of "Hey Jarvis" itself, so a command said straight after it isn't clipped), measures the room from the 3 seconds before, and ends once it's been quiet for 1.5 seconds after you speak, or however long `EARS_WAKE_PAUSE` says (see below) (speech being three times the room's level, and never below 300; the first 0.8 seconds, the end of "Hey Jarvis" and the chime, don't count), or at 30 seconds. With no speech within 5 seconds it ends and is dropped without going to Whisper, which is what a false wake from the TV usually looks like; Enter in the chat before then still sends it. A chat has to take the recording within 2 seconds, or ears drops it without sending it to Whisper: that's also what happens to a wake in the few seconds after the last chat stops waiting. A detection that openWakeWord sends more than 2 seconds after the sound it's about, with no time, or with a time ahead of the sound ears has sent it (left over from before ears paused), is ignored and logged as too late to trust. Ears sends openWakeWord whole milliseconds of sound, up to a second at a time, and holds what's left for the next piece: openWakeWord times what it hears by adding up each piece's length rounded down to a millisecond (its 2.1.0 code, through the `wyoming` library), so pieces of any size made its clock fall about 2.5 ms a second behind ears's on this server, and after about 13 minutes of listening with no recording, hold or closed microphone to restart both clocks, every detection looked late and was ignored. While any chat holds it (when that Jarvis is speaking), ears passes nothing to openWakeWord and throws the sound away; each chat's hold is kept apart and runs out by itself after 15 seconds unless it's renewed, and ears starts again half a second after the last one is let go. Before opening the microphone again, ears waits for the last `arecord` to have ended, because a second one couldn't open it. `EARS_WAKE_THRESHOLD` (above 0 and below 1, default 0.5, openWakeWord's own) is how sure openWakeWord must be: raise it if the TV sets him off. `EARS_WAKE_PAUSE` (seconds, 1 to 5 to a tenth, default 1.5) is how long a pause after you've spoken ends a wake recording or a follow-up: raise it if you pause mid-question and get cut off, at the cost of every answer starting that much later. Stop and start ears to change it; its start-up line about the wake word says what it's set to, `mic-test` judges your longest pause against it, and ears's last recording says which pause it was set to end on (`pauseMs`). To turn the wake word off again, set `EARS_WAKE=off`, then stop and start ears, since `start` alone leaves a running openWakeWord as it is. If openWakeWord can't be reached, ears says why, tries again every 5 seconds, and `/talk` still works. Its API adds `GET /wait?after=<version>`, which answers with the whole state, its version and which run of ears it is, as soon as any of it changes, or after 20 seconds; `POST /wake/claim?id=<number>` to take a wake-word recording; and `POST /wake/hold?by=<id>` and `POST /wake/release?by=<id>`, where each chat names itself with its own id. The `wake` part of a `/wait` answer also has `late`: how many detections ears has ignored as too late since it started, and how far behind the last one was (`behindMs`, or null when openWakeWord gave no time, or a time ahead of the sound ears had sent it). And `POST /wake/follow?within=<milliseconds>` (1,000 to 20,000, record 0043), which starts a recording that already belongs to the chat that asked. It's judged like a wake recording, against the room's level from before the last "Hey Jarvis" and with nothing ignored at the start, and it's dropped without going to Whisper if no speech comes within that time. It's refused with 409 while any chat holds the wake word, or before ears has heard the room. `docker compose logs ears` adds a line when the microphone opens or closes (and why), for each detection (with the room's level; openWakeWord sends no score), for one that came while it wasn't listening or too late to trust, and when the wake word stops or starts working. After a wake, follow-up or talk-button recording that had speech in it, a line says how long after it began speech was first heard, how much speech there was, and the longest pause between words, from the tenths of a second it already judges for the end of the recording (never the words). `bash host/ears.sh wake-report` counts those lines into a short report: how many times it heard "Hey Jarvis", how many it ignored as late or as coming after it stopped listening, how many wake recordings started, failed to start, were taken by a chat or by none in time, and how each ended: no speech in time (a false wake, or nothing said after it), cancelled, muted or failed, turned into text, or not turned into text after all. Then the same for follow-ups, for talk-button recordings, and for other recordings (`/talk`, or `ask.js start`). It reads the whole of ears's log, which Docker keeps from when ears's container was last made (it's made again when its image or settings change, which includes the microphone's card number changing after the server restarts), dropping the oldest lines past about 100 MB (Docker's `local` log driver, set in `host/daemon.json`, keeps five files of 20 MB). `bash host/ears.sh wake-report 6` reads only the last 6 hours (1 to 720). It ends with a line each for wake recordings, follow-up windows and talk-button recordings, leaving out recordings that were cancelled, muted, failed or taken by no chat: the median time until speech was first heard (with the shortest and longest), the median amount of speech, and the median and longest pause between words. The pause that ends a recording isn't a pause between words, so the longest can only reach `EARS_WAKE_PAUSE` less a tenth of a second; if your longest often come close to that, some of your pauses are probably as long as the setting, and it may have cut you off. A wake recording's first speech can't show before 0.9 seconds, since it ignores its first 0.8. A follow-up start later than `JARVIS_FOLLOW_UP` counts as no speech in time instead, so the follow-up times can show the window is longer than you need, not that it's too short. It prints only counts and timings, never what was said.
  - The talk button (record 0045). `bash host/ears.sh talk` starts a recording as if you'd said "Hey Jarvis", for a button to run: on the server, or from another computer over SSH, like `ssh home-server "bash ~/docker/host/ears.sh talk"` from PowerShell (the script finds its own folder, so it runs from anywhere). It runs ears's own helper inside ears (`docker compose exec ears node dist/ask.js talk`), which asks ears's `POST /wake/talk` from inside ears itself, so nothing new can reach ears. A chat with `JARVIS_EARS=wake` takes the recording, chimes and shows a note, and it's judged like a wake recording: the first 0.8 seconds ignored (the chime), against the room's level from up to the last 3 seconds ears heard, as for the wake word (or the level it last measured, if it has heard less than a second since it last started listening), ending after `EARS_WAKE_PAUSE` of quiet or `EARS_WAKE_END`'s speech detector, or dropped without going to Whisper if no speech comes within 5 seconds. None of the sound from before the press is kept. It needs `EARS_WAKE=on` and a chat waiting on ears, but not openWakeWord itself, once ears has heard the room. Pressing again while its recording goes on sends it at once, like Enter on an empty line, once a chat has taken it and it has heard speech; before that, a press just says it's listening. A press is refused, with why, while ears is muted, failed or still sending the last recording, when no chat has waited on ears for 5 seconds, while Jarvis is speaking (rule R11), before ears has heard the room, during `/talk`'s own recording, or while ears is already listening after "Hey Jarvis" or for a follow-up, when you can just speak. It waits until a chat has taken the recording (up to 3 seconds) and prints one line, never what was said: that a chat has taken it and it's listening, that it's already listening, that it sent the recording (or stopped it but there was no text, and why), or why not, and exits 1 when nothing is listening or nothing was sent. When no chat takes it, ears drops it after 2 seconds and the command says so: a Jarvis chat started before this was added doesn't know the button, so start open chats again after updating. A press that got past those checks but that ears couldn't record after is logged with why. A question asked with it is logged with `button: true`, opens a follow-up like a wake question, and `npm run compare` counts it. `wake-report` counts the talk-button recordings, any that failed to start, and their speech timings; presses ears refused before starting one leave nothing in its log. Over SSH, the press reaches ears a second or two later than typing it on the server (Claude's guess; not measured), so wait for the chime.
  - Code words (records 0046, 0049, 0052, 0058, 0062 and 0063). Jarvis checks what Whisper heard against a short fixed list before Claude sees it, in his own code, so they're instant, cost nothing and give the AI no new powers. Only spoken questions count, never typed ones, and only when the code word is all you said or the last sentence of it, give or take an optional "Hey Jarvis" (or the clipped end of it Whisper sometimes writes) and a few filler words: please, oh, no, actually, thanks, okay or Jarvis before, and please, now, Jarvis, thanks, cheers, then, OK, "for now", "for a bit" or "for a while" after.   - openWakeWord is `rhasspy/wyoming-openwakeword` 2.1.0, pinned by digest, in the `wake` profile, with its "hey jarvis" model inside the image.   - Silero's speech detector (record 0042). A wake recording ends once it's been quiet for 1.5 seconds (or `EARS_WAKE_PAUSE`) after you speak, and by default "quiet" means quieter than three times the room. A fan, music or the kettle can be loud enough to keep it going, and a quiet voice can drop under the line. With `EARS_WAKE_END=silero` in `ears/.env` (the default is `loudness`), quiet means Silero's speech detector heard no speech instead. It judges each tenth of a second in pieces of 32 ms and counts a tenth as speech when any piece has a chance of 0.5 or more. It's speech it hears, not you: people talking on the TV still count. Everything else about the ending (the first 0.8 seconds ignored, the 1.5 seconds or `EARS_WAKE_PAUSE`, 5 seconds, 30 seconds) stays the same. Ears loads the detector when it starts, only with `EARS_WAKE=on` and `EARS_WAKE_END=silero`, and won't start if it can't; then set it back to `loudness`. If it fails during a recording, or falls more than a second behind, ears logs it once and that recording ends on loudness, with loudness's wording for why. Stop and start ears to change it. It runs inside ears, on one CPU thread, at about a millisecond per tenth of a second of sound in tests on the machine this was built on (the server's CPU wasn't measured), and about 25 MB more of ears's memory while it's loaded (59 MiB against 36 MiB in a rehearsal). Ears's image is now built on `node:26-trixie-slim` (Debian), because onnxruntime's ready-made Linux files need the C library Debian has and Alpine doesn't. `alsa-utils` comes from Debian. The image has `onnxruntime-node` (Microsoft, MIT licence; its install step's fetch of NVIDIA CUDA files is switched off in `ears/.npmrc`, and the image keeps only this machine's files). Microsoft's builds of it send usage telemetry over HTTPS unless `ORT_DISABLE_TELEMETRY=1` is set before it loads (its own privacy notice says so), so ears sets that in its image and in its code, and ears's network has no internet anyway. It also has Silero's model, `silero_vad.onnx` (v6.2.3, MIT licence, 2.3 MB), which the build downloads from a fixed commit on GitHub and checks by size and SHA-256, so building ears needs GitHub and npm. The model is never in this repo. Check it on the server with `docker compose run --rm --no-deps ears node dist/silero-check-run.js`: it plays it a second each of silence, noise and a steady tone, prints each one's highest chance of being speech, and fails if any reaches 0.5. `bash host/ears.sh mic-test` also shows what the detector heard when `EARS_WAKE_END=silero`, beside the loudness check, half a second to a mark. The first `npm ci` in `ears/` downloads onnxruntime-node, about 115 MB, and unpacks about 300 MB, all platforms' files; the tests don't load it, so they still run in `node:26-alpine`.
  - Judging the end by your words (record 0054). With `EARS_TURN_WORDS=on` in `ears/.env` (the default is `off`, and it needs `EARS_WAKE=on`), ears reads what you've said so far each time you pause and ends the recording sooner or later than the usual pause (1.5 seconds, or `EARS_WAKE_PAUSE`). 0.4 seconds after you stop speaking it sends the recording so far to Whisper, once per pause; speaking again calls that off and forgets what it found. Fixed rules in `ears/src/turn.ts` then judge the words. More to come: they end in a comma, a dash, a colon, a semicolon or "...", or the last word leads on ("and", "or", "but", "because", "if", "while", "than", "the", "a", "an", "my", "your", "our", "their", "of", "into", "plus", "very", "um", "uh", "er", "erm", "hmm"), or there's only a greeting or "Jarvis"; the recording then waits for 3.5 seconds of quiet, or the usual pause if that's longer. Finished: they end in a full stop, a question mark or an exclamation mark, and the last word isn't one that rarely ends a thought ("for", "in", "at", "to", "with", "from", "then", "you", "can", "could", "would", "is", "are", "was", "I", "we", "about"), since Whisper puts those marks on cut-off words too; the recording ends after 0.7 seconds of quiet, or the usual pause if that's shorter. Anything else is unsure and keeps the usual pause, unless a chat with `JARVIS_TURN_CHECK=on` is waiting: then ears shows the words so far in its view (`asking`, to anything holding `EARS_TOKEN`) and takes one answer on `POST /wake/turn`, `done` or `more`, for up to 1.5 seconds. When a look's text covers everything you said, ears uses it as the recording's text and doesn't ask Whisper again, and the log says `Turned into text in 0 seconds: the text made while you paused was used.` Each recording with speech in it also logs how it was judged, by what, and in how many looks, like `Judged by your words: finished, by the rules (1 look).`, never the words. Follow-ups and the talk button are judged the same way; `/talk` recordings aren't, since Enter ends those. Each look is a whole Whisper run, so it costs CPU at every pause, and Whisper's punctuation is what the rules rest on: it sometimes puts a full stop or question mark on words that weren't finished, and then the recording ends early. `bash host/ears.sh wake-report` shows whether recordings got shorter. Stop and start ears to change it.
  - Interrupting him (record 0055). `EARS_INTERRUPT` in `ears/.env` is `off` (default), `wake` or `speech`, and needs `EARS_WAKE=on`. With `off`, ears hears nothing while any chat holds the wake word, as before. With `wake`, the wake word is still listened for during a hold, so "Hey Jarvis" works while he's thinking or speaking. The recording it starts keeps nothing from before the wake word and hears silence until half a second after the last chat lets go, so neither his voice nor its last echo in the room is recorded or sent to Whisper; what you say before then is lost with it. A wake word heard in that half second gets the same. The chat that's speaking takes the recording at once, even though it's busy, and his code stops his speech straight away, without waiting for the chat to get to it: the rest of the answer he was giving still finishes writing on the screen, silently, and only then is your new question asked, because a question can't be called off part-way. A line says he stopped talking, and there's no chime, since his going quiet is the sign. If another chat takes the recording, the speaking chat still stops, and says why. The talk button works while he speaks too. Follow-ups are unchanged: ears still refuses one while a chat is speaking. The room's level, which decides what counts as speech, isn't measured while he speaks, so his voice never raises it. The wake word is listened for again straight after a hold, with no half-second gap. With `speech`, a recording started during a hold hears the real sound, not silence, and besides the wake word, 0.3 seconds of sound louder than speech in the room (three times the room's level, measured before he spoke) during a hold starts a recording as if you'd said "Hey Jarvis", keeping the sound from just before it (about half a second). That only works with a microphone that doesn't hear him, like a speakerphone that cancels its own speaker's sound with him playing through it: with the laptop's own microphone and speakers his voice is the loudest thing it hears, and he'd interrupt himself at once. Anything loud enough counts, not just you: the TV, music or someone else talking while he speaks is recorded and asked. A recording started this way is logged and counted as a wake-word recording, with `Heard speech while Jarvis was speaking.` on the line before it; a wake word in a hold logs `It came while Jarvis was speaking, so it cuts in.` after its usual line. Ears's view says which mode is on (`wake.interrupt`), which is how the chat knows. If his own answer has "Hey Jarvis" in it, he can interrupt himself. Stop and start ears to change it.
  - Voice ID (record 0056). Ears can compare a voice with a voiceprint of yours, to tell you from the TV, other people and Jarvis's own voice, and with `EARS_VOICE_ID` it does so for each recording before Whisper hears it. A small model, WeSpeaker's CAM++ for English (from sherpa-onnx's speaker recognition release on GitHub, 28 MB, Creative Commons Attribution 4.0, as its training data VoxCeleb is), turns a second or more of speech into 512 numbers, and the score is how alike two of those are, from -1 to 1. The build downloads the model into ears's image, from a fixed address, checked by size and SHA-256; it's never in this repo, and building ears needs GitHub's release downloads. `ears/src/fbank.ts` works out the sound features it needs, as Kaldi does, with no new package.
    - `bash host/ears.sh voice-enrol` shows five short sentences one at a time and records each for 6 seconds, 2 seconds after showing it. Sit where you talk to Jarvis, with nobody else talking and the TV off. A sentence with less than a second and a half of speech is asked again, up to three times. The voiceprint is the average of the five, and if any one sounds unlike the others (under the threshold) nothing is saved. Nothing you say is kept: only the voiceprint, in `ears/voice/voiceprint.json` (the model's name, how many clips, when, and the 512 numbers), in a folder and file only you can read. It's biometric data about you: it's never in git, never logged and never printed. Running it again replaces it; delete the file to remove it.
    - `bash host/ears.sh voice-check`, or `voice-check 10` to wait 10 seconds first (up to 60), records 5 seconds and prints the score against your voiceprint and what it counts as at the threshold. Try yourself, the TV and other people, from where you'd talk.
    - Both run like `mic-test`: only from a terminal, never while ears is listening, in a throwaway container from ears's image with only the microphone and its mixer, no network and no log. The enrolment's voiceprint comes back through a pipe and the script writes it; the check runs as you, with `ears/voice` read-only, so it can read your file.
    - `EARS_VOICE_ID` in `ears/.env`: `off` (default), `observe` or `require`. `EARS_VOICE_ID_THRESHOLD`: above 0 and below 1, to two places, default `0.5`; enrolment and `voice-check` use it too. With `observe`, each recording with speech in it is scored before it's turned into text, and the log says the score and what it counts as, like `Voice: Score against the voiceprint: 0.84. At the threshold of 0.5, that counts as the voiceprint's voice.`; nothing is blocked. With `require`, a recording started by the wake word (or by speech over him, record 0055) or as a follow-up whose voice counts as a different one isn't sent to Whisper: the log adds `Not turned into text: the voice in it didn't match the voiceprint.`, and the chat says nothing was sent and why. A recording with under a second of speech can't be judged, so it goes through: blocking it would lose "yes", "no" and "stop". One where the check finds no speech loud enough to judge is blocked as too quiet to check (that can only happen with `EARS_WAKE_END=silero`, which hears quieter speech than the check does). Recordings started by the talk button or `/talk` are scored but never blocked, since someone started them by hand. The voice is checked once a recording has ended, so with `EARS_INTERRUPT` on a cut-in still stops him even when its recording is then dropped: `require` keeps the TV's words from being asked, not from interrupting him. With `EARS_TURN_WORDS=on` as well (record 0054), `require` reads the words at a pause only when the voice so far counts as yours, whoever started the recording; otherwise that pause isn't looked at and the usual pause applies, so an answer under a second ends on the usual pause. Words read at a pause can still belong to a recording that's blocked at the end, if another voice came in after yours. `bash host/ears.sh start` checks the setting, refuses if there's no voiceprint yet, and adds `docker-compose.voice.yaml`, the only place ears gets `ears/voice` (read-only, at `/voice`) and the memory for the model (384 MiB, not 256).     - Several people (record 0072). Besides yours (`ears/voice/voiceprint.json`, or the one `EARS_VOICE_OWNER` names, 1 to 20 of a to z, 0 to 9 and -), anyone can have a voiceprint of their own: `bash host/ears.sh voice-enrol <name>` makes `ears/voice/<name>.json` the same way, and `voice-enrol` with no name makes or remakes the owner's. `bash host/ears.sh voice-list` lists them, each with when it was made and from how many clips, the owner marked, never the numbers, and says when the owner's is missing. `bash host/ears.sh voice-forget <name>` deletes one file after asking y/N in a terminal (it refuses without one, and refuses anything but a plain name); restart ears with `bash host/ears.sh start` so it stops using it.
