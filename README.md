# Home Hub

Home Hub is my server, to do what I want with, and to have futuristic things built on it that can help me do what I want: a cool program that knows stuff and can help me out.

## Why I built it
I built it to learn, to help me do more coding stuff, and because it was cool as shit.

## How I built it
I built it using my own ideas, with AI helping me plan and learn what I needed to do to make it. I made all the decisions and made each commit myself.

## How the parts fit
- Everything runs on one Ubuntu server, from one compose file: `docker-compose.yaml`.
- Caddy is the front door. Each service has a `.home` name, and AdGuard Home answers DNS on the home network, which is how those names reach Caddy.
- `hub.home` and `api.home` also answer over HTTPS, using Caddy's own certificate authority. Only devices that have installed Caddy's root certificate trust it, so plain HTTP still works everywhere.
- Nothing is open to the internet. Away from home, everything goes through Tailscale.
- The API (`api/`) is the centre: one module per capability, and every route except logging in needs a token. It reads from qBittorrent and Jellyfin, watches the server's Wi-Fi reconnect log, can count and add notes in the brain's inbox, and with catch-up on, reads recent commits from GitHub.
- Every 5 minutes the API checks for problems (low disk or memory, Wi-Fi reconnects, a failed backup) and sends any change to my phone through ntfy. It also pings Healthchecks.io, which tells me if the server goes quiet, and sends a daily summary at 08:00.
- The phone page (`hub/`, at `hub.home`) is plain JavaScript served by Caddy, which passes `/api/*` on to the API.
- Claude Code reaches the API through an MCP server (`mcp/`), a throwaway container started for each session. Its tools read from the API; the five that change things (start a library scan, stop or start a download, add or cancel a watcher) always ask first.
- The brain is a separate private repo of notes, `hub-memory`. Its `inbox/` folder is mounted into the API.
- Anything that runs outside Docker lives in `host/`. The main ones are the Wi-Fi watchdog, a systemd timer that reconnects the Wi-Fi when the router stops answering, and the backup.
- Backups use restic. `host/backup.sh` backs up this folder, the brain and Claude Code's settings, stopping the apps that keep databases while it copies them. A systemd timer runs it every night at 03:30, but it stays off until there's a backup drive. Each run's result shows on the phone page, in the daily summary and at `GET /system/backup`, and can ping its own Healthchecks.io check. `docs/restore.md` explains how to get files back.

## Switches
New features are built switched off. Each switch is a line in `api/.env` set to exactly `on` or `off`. Anything else, or a missing switch, stops the API starting, so a typo can't quietly change what's on. `GET /system/features`, the phone page and the daily summary all show what's off. The MCP server has one switch of its own, `MCP_ACTIONS`, which `bash host/hub-mcp.sh read-only` turns off. Jobs that run on the server itself, like the nightly backup, are switched on and off by enabling or disabling their systemd timer.

### The deal watcher's settings
`DEALS` switches it on. While it's on, `api/.env` also needs `DEALS_SEEN` (`memory` or `disk`), `EBAY_ENVIRONMENT` (`production` or `sandbox`), `EBAY_CLIENT_ID`, `EBAY_CLIENT_SECRET` and `DEALS_AI` (`on` or `off`: whether Claude's tools may read the listings). Each search has its own `switch` in `deals/searches.json`. `docs/deals.md` has the rest.

### Finding your phone
`FIND_PHONE` switches on `POST /phone/find`, which sends your phone ntfy's top priority, "Here's your phone", to `NTFY_TOPIC`, so `api/.env` needs that topic while it's on. ntfy's docs describe that priority as really long vibration bursts and the default sound, with a pop-over; whether it sounds through Do Not Disturb or silent mode is down to the phone and its ntfy settings (not checked). It's sent at most once every 10 seconds. Jarvis asks it when you say "find my phone" (record 0046).

### Train times
`TRAINS` switches on `GET /trains`, the next five trains from one station to another (or, with a change station, the next three journeys: see "Journeys with a change" below), from National Rail's live departure boards (Darwin) through the Rail Data Marketplace (record 0047). While it's on, `api/.env` also needs:
- `RAIL_DATA_KEY`: the consumer key from your free Rail Data Marketplace account, on the "Live Departure Board" product's Specification tab. It's a secret, like the other keys in `api/.env`.
- `TRAINS_FROM` and `TRAINS_TO`: the two stations' three-letter codes, in capitals (National Rail's station pages show them).
- `TRAINS_BOARD_URL`: the departure board's address on that Specification tab, up to but not including the station code. In community copies of that tab it looks like `https://api1.raildata.org.uk/1010-live-departure-board-dep1_2/LDBWS/api/20220120/GetDepartureBoard`, but copy yours. It must be https on `raildata.org.uk`, with no `?`, `#` or `{` part.

The hub asks `TRAINS_BOARD_URL/TRAINS_FROM?numRows=5&filterCrs=TRAINS_TO&filterType=to`, sending the key in an `x-apikey` header. That's how community examples of the board's JSON version ask it; the official specification is behind the marketplace's login and wasn't checked, so `bash host/hub-get.sh /trains` is the first test. One copy of the specification describes `filterType=to` as trains starting or ending at `TRAINS_TO`; it's believed to mean trains that call there, which that first test should show with a train known to run on past it. It gives each train's booked and expected time, platform, whether it's cancelled (or cancelled at `TRAINS_TO`) and why, how many buses the board lists, and up to three of the board's own messages, which on a day with no trains may be all there is. The board covers about the next two hours, as far as community clients show (not checked), so "no trains" means none in that time. It says why when the board can't be reached, refuses the key, can't find the address (a 404 usually means `TRAINS_BOARD_URL` includes the station code), redirects or sends something that isn't a board, never with the key, and gives up after 8 seconds. Jarvis says the next three when you say "train times" (record 0046).

### Journeys with a change
`TRAINS_CHANGE_AT` makes train times follow a journey with one change (record 0053). With it set, `TRAINS_TO` is where you end up, not where you change, and while `TRAINS` is on `api/.env` also needs:
- `TRAINS_CHANGE_AT`: the change station's three-letter code, in capitals, different from both ends.
- `TRAINS_CHANGE_MINUTES`: how long the change takes you, door to door, in whole minutes from 1 to 30. The boards give whole minutes, so every gap is a whole number of minutes: with 3, a 3-minute gap is enough and a 2-minute one is tight.
- `RAIL_ARRIVALS_KEY`: the consumer key of the free "Live Arrival Board" product, a second subscription on the Rail Data Marketplace with its own key. It's a secret, like `RAIL_DATA_KEY`.
- `TRAINS_ARRIVALS_URL`: that product's address from its Specification tab, ending in `GetArrBoardWithDetails`, without the station code.
- `TRAINS_BOARD_URL` must then end in `GetDepartureBoard` or `GetDepBoardWithDetails`: the hub uses the detailed board, `GetDepBoardWithDetails`, which sits next to the plain one and comes with the same Live Departure Board subscription and key.

The hub asks two boards at the change station at once:
- the arrival board, for trains and buses due in from `TRAINS_FROM` (`TRAINS_ARRIVALS_URL/TRAINS_CHANGE_AT?numRows=5&filterCrs=TRAINS_FROM&filterType=from`, with `RAIL_ARRIVALS_KEY`). Its detailed reply lists each one's earlier stops, so it gives the time at `TRAINS_FROM` too, and it keeps a train listed after it has left `TRAINS_FROM` until it gets in, which is what lets the hub follow it while you're on it. A departure board drops a train soon after it leaves.
- the detailed departure board, for trains and buses on to `TRAINS_TO` (the detailed address next to `TRAINS_BOARD_URL`, then `/TRAINS_CHANGE_AT?numRows=10&filterCrs=TRAINS_TO&filterType=to`, with `RAIL_DATA_KEY`), with when each is due in at `TRAINS_TO`.

`GET /trains` then gives `from`, `via`, `to`, `walk`, up to three messages from the two boards (each once), and the next three journeys by when they leave `TRAINS_FROM`, counting one that has left but isn't in yet. Each journey has its first train's time and expected time, whether it's cancelled or a bus, why it's late, when it's due and expected in at the change, and its platform there, then:
- `best`: the connection that gets you in soonest among those leaving you at least your walk. That's not always the first to leave: a slower train a few minutes earlier isn't best.
- `fallback`: the soonest in of the others leaving no earlier than the best, for if you miss it.
- `tight`: a connection that would get you in sooner than the best but leaves you less than your walk (a minute at least), so you know there's one worth running for.

Each connection has its time, expected time, platform, destination, when it's due and expected in, whether it's a bus, why it's late, and `change`, the minutes you'd have. A cancelled connection, one cancelled at `TRAINS_TO`, or one leaving before you're in isn't offered. A connection delayed with no time yet counts from when it was due, and one with no expected time in is taken to be as late in as it is leaving. A first train with no expected time in has no connections until it has one. Times work across midnight. The boards sometimes write "Ontime" without the space; it's read as "On time", here and on the direct board. Errors say which board failed and which setting to check, never a key. Jarvis says the next three journeys when you say "train times": each first train, the minutes you'd have at the change for its best connection and when that gets in, any tight one, and the fallback.

### Morning train alerts
`TRAIN_ALERTS` switches on a morning check of the trains between the same two stations, sent to your phone through `NTFY_TOPIC` (record 0048). It needs `TRAINS=on` too, and while it's on, `api/.env` also needs:
- `TRAIN_ALERT_DAYS`: the days to check, from `mon`, `tue`, `wed`, `thu`, `fri`, `sat` and `sun`, with commas between, like `mon,wed`.
- `TRAIN_ALERT_WINDOW`: the trains to watch, by the time they're due to leave, as two 24-hour times with a dash between, like `07:00-08:30`. Both ends count, and it must end by 22:59, so the hour after it is still the same day.
- `TRAIN_ALERT_REMINDER`: when to send the reminder, a 24-hour time like `06:45`. It must be before the window ends, and no more than 2 hours before it ends, since the board only looks about that far ahead.

London time throughout. On those days, at the reminder's time, the hub sends "Morning trains": each train in the window with whether it's on time, how late or cancelled and why, and its platform once the board has one, then any buses the board lists and its own messages. If the board's furthest train is due before the window ends, it says how far the board reaches, since it asks for only 10 trains. From then on it asks the board every 2 minutes and sends "Train change" when a train in the window:
- is cancelled, at high priority;
- becomes 5 minutes late or more, and again whenever that moves by 5 minutes or more;
- is shown as delayed with no expected time, when it wasn't already 5 minutes late;
- after one of those, is back to 2 minutes late or less, or is 5 minutes or more less late than last sent;
- runs again after being cancelled;
- moves from one platform to another (a platform appearing for the first time isn't sent);
- leaves the board more than a minute before it's due, while the board lists later trains and has fewer than 10 on it, which may mean it was cancelled or replaced by a bus.

With `TRAINS_CHANGE_AT` set, the window is the trains leaving `TRAINS_FROM`, the reminder gives each journey in it as `GET /trains` would (first train, its time in, the connection, any tight one, the fallback), and both boards are asked for 10 rows. On top of the first trains' own changes above, it sends "Train change" when a journey:
- loses its connection, because the gap has dropped under your walk, the first train now gets in after it leaves, or it's cancelled or gone from the board: at high priority, saying which, with the next best;
- gets a better connection back, once the gap is a minute more than your walk, so a gap hovering at your walk doesn't flip back and forth;
- has no connection on the board at all, at high priority, or finds one;
- has its connection move platform;
- has a sooner connection become possible but tight, said once for each connection.

A journey first seen after the reminder only sends its own first train's problems, and its connection is noted quietly. A first train with no expected time in keeps its last connection until it has one.

So a train hovering around 5 minutes late, or flipping between a time and no time, doesn't send each flip. A train is known by the time it's due, so a change of destination (a train ending its journey early, say) doesn't make it a new train; only two trains due at the same time are told apart by destination. A train first seen after the reminder, as the board reaches further, is only sent if something's already wrong with it. It stops once the window has ended and none of its trains is still on the board, or an hour after the window ends, whichever comes first, and starts again the next set day.

If the board fails for 5 minutes or more, whether it can't be reached, refuses the key or sends something that isn't a board, it says so with when it started failing (about 6 minutes after the first failure, since it asks every 2 minutes), and keeps trying every 2 minutes. When the board answers again it says so, unless the reminder follows straight away, and if it's still failing an hour after the window ends, it says it has stopped checking for the day. Each outage is sent once. The API's log says when it couldn't reach the board and when it can again, never with the key. A notification ntfy didn't take is sent with the next check, 2 minutes later. It keeps nothing on disk: if the API restarts before the window ends, the reminder comes again with the trains as they are then, and if it restarts after the window ends, it only sends what's wrong with the window's trains still on the board. The notifications pass through ntfy.sh like the other alerts. The hub adds no station or destination names to them, with a change station too, but the board's own reasons and messages go as they are, and those can name stations.

While `TRAIN_ALERTS` is on, `GET /trains/changes` gives today's change lines too (record 0051), for Jarvis to say aloud: each check that found changes is one entry, numbered from 1, with when it was found and its lines, only the newest 50 kept and none of the reminder's or the outage notices. `?after=<number>&run=<run>` gives only the entries after that number; the `run` changes each time the API starts, and since the numbers start again then, asking with an old run gives all of today's entries. Entries are found as each check runs, whether or not ntfy takes them, and kept in memory only, so a restart empties them. After a restart past the window's end, the first check's lines go to your phone as before but aren't added, since they're what was already wrong. It's behind the API's token like every route, and since Jarvis asks every 30 seconds, asking isn't logged, refusals and wrong tokens included, unless the API itself fails.

### Expiry alerts
`EXPIRY_ALERTS` switches on reminders for things that run out on a date, like the server's Tailscale key, a GitHub token or a yearly subscription, sent to your phone through `NTFY_TOPIC`, so `api/.env` needs that topic while it's on (record 0057).

The list is `expiry/items.json`, which git ignores: copy `api/src/modules/expiry/items.example.json` there and edit it in VS Code. Each item has a `name`, a `date` written `YYYY-MM-DD`, and an optional `note`. It's read again at every check, so a change needs no restart. It holds names and dates only, never a key, token or password: a name (up to 40 characters) or note (up to 100) is refused if it has anything but letters, digits, spaces and `' - . , ( ) & / + : _`, a word over 20 characters, or a word of 12 or more mixing letters and digits, since that could be a key pasted in by mistake. Two items with the same name, in any case, and more than 50 items are refused too. One refused entry stops the whole list, as with the deal watcher's: the error names the file and the entry by its number, never what was refused, and goes to the API's log, to `GET /system/alerts` (so the alerts send it to your phone while `ALERTS` is on) and to `GET /expiry`. With the switch off the list isn't read, so a missing or broken one never stops the API starting.

Every 5 minutes, from 08:00 London time, the API checks the list and sends one notification for everything due: an item is warned about at 30, 14, 7, 3 and 1 days before, on the day, and once when it's overdue. ntfy turns a message over 4,096 bytes into a file attachment, so a warning that long lists what fits in 3,500 bytes, soonest first, and ends by saying how many more there are. One first seen part way through, or after a day the check couldn't run, is warned about once for where it is then, with its real days left. A notification ntfy doesn't take is tried again at the next check. It's high priority when something is a day away or less, due today or overdue. What was sent is kept in `expiry/sent.json`, written by the API beside the list, so a restart sends nothing again; a new date for an item, as after renewing it, starts its warnings again. If that file can't be saved, the alerts say so, and a warning may be sent again after a restart. Deleting it while the API is stopped is safe: each item within 30 days, or overdue, gets one warning for where it is now.

The names, dates and notes go through ntfy.sh in the notifications and the daily summary, so keep them general. `GET /expiry` gives today's London date and each item with its date, note, days left (below 0 once passed) and whether it's overdue, soonest first, and says when expiry alerts are switched off or the list has a problem. The daily summary adds an "Expiring:" line when something is within 30 days or overdue, the phone page lists them under "Expiring", and Claude Code reads them with `get_expiries`.

### The server doctor
`GET /system/doctor` answers "is everything OK?" in one go, from what the hub can already see (record 0058). It has no switch of its own: it only reads, and adds nothing the other routes couldn't already reach. It's behind the API's token like every route. It gives an overall `state` (`ok`, `warn` or `problem`), a `summary` in plain words such as "1 problem: Heartbeat. 1 thing to look at: Disk.", the time it checked, and thirteen `checks`, each with a `name`, a `state` (`ok`, `warn`, `problem`, or `off` when its feature is switched off, which never counts as a problem), a `detail` in plain words and `next`, what to try, or null when it's ok or off:
- Disk: a problem under a tenth free (the alerts' rule), something to look at under a fifth.
- Memory: a problem under a tenth available (the alerts' rule).
- Wi-Fi: something to look at after any reconnect in the last 24 hours (the alerts' rule).
- Backups: off until one has run, a problem when the last run failed (the alerts' rule), something to look at when the last good one is more than a week old or the status can't be read.
- Heartbeat (`HEARTBEAT`) and Phone alerts (`ALERTS`): the API remembers, in memory only, whether its last ping to Healthchecks.io, and its last 5-minute alert check (reading the problems and sending any change to ntfy), worked, and when. A failure is a problem. Before the first one has finished after a start, it's something to look at. A restart forgets both.
- qBittorrent and Jellyfin: asked as `/media/downloads` and `/media/library` ask them, with their keys; no answer within 6 seconds, or an error, is a problem.
- Brain inbox (`MEMORY_INBOX`): a problem when it can't be counted.
- Deal watcher (`DEALS`): its own problems from the alerts; a day's calls used up on its own is something to look at.
- Train times (`TRAINS`): asks the departure board once, as `GET /trains` does (three boards with `TRAINS_CHANGE_AT`), so each check is one more call on your Rail Data Marketplace key; no answer is a problem.
- Expiry list (`EXPIRY_ALERTS`): anything overdue, a list it can't read, or warnings it couldn't save are problems; anything due within 7 days is something to look at. It names the items.
- Watchers (`WATCHERS`): how many things are being watched; a watcher whose last check couldn't read its source, or whose notification is waiting to be sent again, is something to look at. It asks nothing new: it only reads the watchers' own list.

The checks are asked at the same time, so one that doesn't answer holds the rest up by 6 seconds at most, which keeps the answer inside the 10 seconds Claude Code's hub tools wait and the 12 seconds Jarvis's code words wait. What qBittorrent, Jellyfin and the departure board answered is kept for 10 seconds, so the phone page asking for the doctor and for catch-up together makes one call to each of them, not two. Only an answer is kept: after a call that failed or didn't answer within the 6 seconds, the next ask tries again. It never reaches Docker, and never shows a key, a token or the Healthchecks address. The phone page shows it under "Is everything OK?", Claude Code reads it with `get_doctor`, the `server-doctor` skill (`.claude/skills/server-doctor/`) looks into anything that isn't fine with the hub's other read tools and suggests what to run, and Jarvis reads its summary out when you say "server check" (below).

### Watchers
`WATCHERS` switches on "tell me when": you ask Claude Code or Jarvis to tell you when something happens, and the hub sends your phone one notification through `NTFY_TOPIC` when it does, so `api/.env` needs that topic while it's on (record 0059). The kinds of thing it can watch are fixed in the hub's code (`api/src/modules/watchers/kinds.ts`); Claude only picks a kind and fills in its numbers, and nothing is saved until you've said yes. There are three kinds:
- `download-finished`, with `name`, a few words of the download's name (2 to 40 characters of letters, digits, spaces and `' - . , ( ) & / + : _`, refused if a word could be a pasted key, as on the expiry list): fires when a torrent whose name holds those words, in any case, finishes in qBittorrent after the watcher was made. It asks qBittorrent for its completed torrents and reads when each one finished, so a download that finished before you asked never counts.
- `disk-free-below`, with `percent`, a whole number from 1 to 99: fires when the server's free disk space, as `GET /system/status` reads it in whole GB, is below that percentage. If it's already below, it fires at the next check.
- `service-answering`, with `service`, `qbittorrent` or `jellyfin`: fires when that service answers the hub, asked as `/media/downloads` and `/media/library` ask it. If it's already answering, it fires at the next check.

Each also has `hours`, how long to watch before giving up: a whole number from 1 to 168 (a week), 24 if left out. `POST /watchers` with a JSON body like `{"kind": "disk-free-below", "percent": 15}` adds one, `GET /watchers` lists them, and `DELETE /watchers/<id>` cancels one by the 8-character id the list gives. A body with anything else in it (another kind's field, an unknown field, a number out of range, text that isn't plain) is a 400 saying what's allowed, never repeating what was sent, and a body over 1 KB is refused. The same watch twice, or an 11th, is a 409. All three routes are behind the API's token like every route, and say watchers are switched off with a 404 while `WATCHERS` is off.

While any watcher exists, the API checks once a minute, asking only the sources the watchers need, each once, with 8 seconds at most to answer. When one happens, it sends one notification naming only what you asked about (never a torrent's full name) and the watcher is gone. Two edges: a watcher cancelled in the moment its notification is being sent still notifies, and if ntfy takes the message but answers after the 10 seconds the hub waits, the hub counts it as not sent and sends it again at the next check, so it can arrive twice. If ntfy doesn't take it, it's tried again at the next check without asking the source again. A source that can't be read (qBittorrent down, say) never fires or removes a watcher: its last check says it couldn't read it, `GET /watchers` and the server doctor show that, and it keeps trying. For `service-answering`, not answering is what's being watched, so it's never a failed read. A watcher that reaches its time without happening sends one low-priority note saying it stopped watching and that it didn't happen (and if the last check couldn't read its source, that too), once, and goes. One that happened but still couldn't be sent by its time is dropped without that note, and the API's log says so. Watchers are kept in memory only, so restarting or rebuilding the API forgets them, without a notification. What you asked about (the kind, a download's words, the percentage) goes through ntfy.sh in the notification, so keep it general.

The phone page lists them under "Watching for", each with a Cancel button; it can't add one. Claude Code reads them with `get_watchers` and adds or cancels them with `add_watcher` and `cancel_watcher`, which always ask first, like the other actions. With `JARVIS_HUB_ACTIONS=on`, Jarvis can use the same two actions, and his own code asks you yes or no in the chat first, saying exactly what would be watched and for how long. Jarvis never says a fired watcher out loud: it's a phone notification only.

### Catch-up
`CATCH_UP` switches on "where was I?" for coming back to my projects after time away (record 0060): `GET /catch-up` gathers recent commits in the GitHub repos I list and what's waiting on the hub, in one answer. It only reads. It's behind the API's token like every route, and says catch-up is switched off with a 404 while `CATCH_UP` is off.

- `CATCH_UP_REPOS` (optional): up to 10 GitHub repos, each written `owner/repo`, with commas and no spaces between, like `alpha/one,beta/two`. Owners and names are checked against GitHub's own naming rules, and a repo listed twice is refused; a refusal names the setting, never its value. Left out, GitHub is never asked and the answer has only the hub's part.
- `CATCH_UP_GITHUB_TOKEN` (optional, a secret): a fine-grained GitHub token, starting `github_pat_`, for private repos. It needs read-only access to the repos' Contents and nothing else. Public repos need no token, so start without one. Classic tokens (`ghp_`) are refused, because they can't be limited to some repos and to reading.

`GET /catch-up?days=7` looks back that many days, 1 to 30, 7 if left out; anything else is a 400. For each listed repo it asks GitHub's REST API (`https://api.github.com/repos/<owner>/<repo>/commits`, with `since` and `per_page=30`, API version `2026-03-10`) for one page of commits, all repos at once, each with 4 seconds to answer, never following a redirect (GitHub answers a renamed repo with one, so that repo then says to check its name). The token, when there is one, goes only in that request's `Authorization` header, never in a reply, an error or a log. Each repo gives its commits per London day, newest first, with the short sha, the time and the message's first line, cut to 120 characters with control and hidden characters taken out, at most 30 (`more` is true when GitHub has more); a repo that can't be read says why in plain words (not found or private, the token refused, the hourly limit used up and until when, no answer, a redirect, an empty repo), never with GitHub's own reply, and the others still answer. Each repo's answer is kept for 10 minutes for the same number of days, or 1 minute if that repo failed, so the phone page and Claude asking again don't use up GitHub's limit: 60 calls an hour without a token, shared by everything behind the same public IP address, or 5,000 with one. Each different number of days is its own ask of every repo, so 10 repos asked for 6 different numbers of days in an hour would use all 60. When GitHub says the limit is used up, or says how long to wait, no repo is asked again before the time it gave (a minute at least, an hour at most, as [GitHub's rate limit rules](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api) ask): answers already kept are still given, and the other repos say they weren't asked and until when. `commitsAskedAt` is the oldest time any repo in the reply was asked, or `null` if none was.

The hub's part reuses what its modules already read, each with 5 seconds at most: notes waiting in the brain inbox (a count only, as `GET /memory/inbox` gives it; the hub can't read the notes), things on the expiry list due within 7 days or overdue, watchers still waiting, the alerts' problems, the last backup, and the server doctor's overall state and summary (asking qBittorrent, Jellyfin and, while `TRAINS` is on, the departure board, each with 4 seconds). A part whose feature is switched off says `off` with its setting, and one that can't be read says `failed` with why; neither fails the answer. A `summary` says it all in plain words. Commit messages are other people's text, so the tool's description tells Claude to treat them as untrusted.

The phone page shows it under "Where was I?" while it's on: the summary and each repo's latest commit. Claude Code reads it with `get_catch_up` (allowed without asking, like the other read tools), and the `catch-up` skill (`.claude/skills/catch-up/`) turns it into a plain "where was I?", suggesting read-only git commands for the repo it runs in. Jarvis doesn't have it. Nothing here reaches a work system: adding work tickets would need its own decision, and recent ideas from the brain would too.

### Jarvis's settings
Lines in `jarvis/.env`. Jarvis prints the `JARVIS_` ones in one line when he starts.
- `ANTHROPIC_API_KEY`: required.
- `JARVIS_LOG`: `on` or `off`, required, like the API's switches. Logs each answer's numbers, never its words, for `npm run compare`.
- `JARVIS_ENGINE`: `sdk` (default) or `api`.
- `JARVIS_THINKING_HISTORY`: `keep` (default) or `drop`. Only the plain API engine uses it.
- `JARVIS_LENGTH_HINTS`: `note` (default) prints the chat-length note below; `jarvis` gives Jarvis the chat's size with each question once it's long, and leaves the suggestion to him. The log records which, so `npm run compare` can show how big chats got before you typed `new`. The size lines stay in a saved chat, so type `new` before switching this setting on a saved chat, or its answers mix the two.
- `JARVIS_LENGTH_WARN`: the chat size, in tokens, where the length warning starts. Default `80000`, 80% of Haiku 5.5's long-prompt line. Set it lower to hear sooner, or to suit another model.
- `JARVIS_LENGTH_CAP`: `off` (default), or a number of tokens above the warning. Once a chat's last request passes it, Jarvis says so, won't send more questions in that chat, and says to type `new`. A guard against long chats quietly costing more. A saved chat's size is kept with it, so the cap still holds after a restart: in the chat file on the plain API engine, and on the Agent SDK in `jarvis/data/chats/agent-sdk-size.json`, which only counts while the transcript it names is still the newest.
- `JARVIS_HUB_TOOLS`: `off` (default) or `on`. On gives Jarvis the hub's read-only tools (status, alerts, switches, downloads, library, Wi-Fi reconnects, backup and what's being watched), through the MCP server in `mcp/`, which he starts inside his own container in read-only mode (unless `JARVIS_HUB_ACTIONS` is on), as one more Node process (about 60 MB) while he runs. Both engines use them. The log records whether he was given them, so `npm run compare` keeps answers with and without the tools apart; on the Agent SDK, a chat whose MCP server didn't start still counts as with. If the MCP server doesn't start or list its tools, Jarvis says so (the plain API engine as he starts, the Agent SDK with his first answer) and carries on with the brain only; the note doesn't say why, and running `npm test` for `mcp/` is the first thing to try. On needs two things, and he won't start without either:
  - Start Jarvis with `bash host/jarvis.sh`, which passes in only `API_TOKEN` from `api/.env`.
  - The MCP server built in `mcp/`, which Jarvis runs from `mcp/dist`: `npm ci`, then `npm test`, as under Tests below. After `mcp/` changes, run `npm ci` and `npm test` for it again, or Jarvis keeps using the old build. `host/hub-update.sh` does both when a pull changes `mcp/`. If the tests fail, `mcp/dist` already holds the new build, because `npm test` builds before it tests, so fix it before you next start Jarvis.
- `JARVIS_HUB_ACTIONS`: `off` (default) or `on`, and only with `JARVIS_HUB_TOOLS=on`. On lets Jarvis use the hub's five actions: scanning the library, stopping or starting a download, and adding or cancelling a watcher. Before each one, his own code (not his instructions) asks you in the chat what he wants to do, and waits for you to type `yes`, in any case. Anything else (even `exit`, which you'd then type again to leave) or no answer within 60 seconds means it isn't done, and he's told so. Ctrl+C closes Jarvis, so nothing runs. Only what you type after the question counts: in a terminal, anything half-typed before it is cleared. Two actions are asked one after the other. The log records whether this was on, so `npm run compare` keeps those answers apart.
  - The wait doesn't count towards the question's 2-minute limit, but it does show in that answer's time.
  - Jarvis takes only the hub tools he knows by name (the seven read tools, plus these three when this is on). A tool added to the MCP server later is left out on the plain engine until Jarvis is updated too; the Agent SDK still offers it to the model, but refuses it if he tries.
  - Before stopping or starting a download with a full hash, his code asks the API for it (`GET /media/downloads/<hash>`) and shows the start of its hash, how far it got and its name, so you're not relying on what Jarvis says. If the hub doesn't have that hash, the question says so. If the lookup fails or takes over 5 seconds, the question says the name couldn't be looked up. A hash that isn't 40 lower-case hex characters isn't looked up, and the question says so. Names come last, on one line, with hidden characters taken out, control characters shown as `�`, double quotes and look-alikes changed to `'`, and cut at 80 characters. Text he reads, such as a torrent name or, with `JARVIS_SESSION_NOTES` on, the sessions' notes, could still carry instructions aimed at him; records 0011 and 0012 have more.
- `JARVIS_SESSION_NOTES`: `off` (default) or `on`. On gives Jarvis the notes your two Claude Code sessions keep for themselves (the `MEMORY.md` in each one's auto memory, for `~/docker` and `~/hub-memory`), added to his instructions when he starts, so he can tell you what you've been working on. He keeps the first 200 lines or 25,000 characters of each, the limits in Claude Code's docs (which say 25KB), cut back to the end of a line, with hidden characters such as zero-width spaces taken out. If both are full, that's something like 12,000 to 17,000 tokens more in every request (Claude's estimate), which the cache makes cheaper while you keep asking within 5 minutes of the last question. He says at start-up how many lines he found for each session. The log records whether he had any.
  - Start him with `bash host/jarvis.sh`, which mounts each session's whole memory folder read-only at `/notes`, whatever this setting says. Only `MEMORY.md` is read, and none of his tools can read outside the brain. The script also needs `API_TOKEN` in `api/.env` and passes it in, though he doesn't use it unless the hub's tools are on.
  - The script finds the folders the way the bundled Claude Code named them in a test (the docs only say the folder comes from the git repo): the repo's full path with every character other than letters and digits turned into `-`, under `~/.claude/projects`, or under `$CLAUDE_CONFIG_DIR/projects` if that's set, which the memory docs don't mention. It doesn't know about Claude Code's `autoMemoryDirectory` setting, so if you set that, he finds none. `ls -d ~/.claude/projects/*/memory` shows what's there.
- `JARVIS_VOICE`: `off` (default), `kokoro` or `piper`, written plainly on a line of its own. With `kokoro`, Jarvis has a voice, made by [Kokoro](https://github.com/remsky/Kokoro-FastAPI), a speech engine that runs in its own container (the `kokoro` service). With `piper`, it's made by [Piper](https://github.com/OHF-Voice/wyoming-piper) instead, in the `piper` service, and everything below that says Kokoro applies to Piper too, apart from Kokoro's memory, voice, speed and logging, which `JARVIS_PIPER_VOICE` below covers for Piper (record 0034). He says one sentence out loud when he starts ("Jarvis is ready when you are."), then speaks his answers, a sentence at a time, while they're still being written. Start him with `bash host/jarvis.sh`, which then builds his image for sound, passes in the card named by `JARVIS_SOUND_CARD`, starts Kokoro and waits up to 2 minutes for it to be ready, and stops it again when the chat ends. If `JARVIS_SOUND_CARD` is missing or wrong, or the image won't build, the script stops there and says why. As he starts, he sets `JARVIS_VOLUME`, checks that Kokoro answers, says the sentence and prints a `Voice:` line. If any of that fails, or the sentence takes more than 45 seconds, the line says his voice is off and why, and the chat carries on in text. The one exception is a microphone device in his container, which stops him starting at all. The log records whether he had a voice, so `npm run compare` keeps those answers apart.
  - Kokoro used about 1.2 GiB of memory when it was measured on this server, and has a 2 GiB limit. It has no published port and sits on a Docker network of its own, `speech`, which has no route to the internet or the LAN and which only Jarvis joins. The server has no address on that network either, so Kokoro can't reach the server's own services, such as SSH (record 0024). If Kokoro is already running when the script starts, because you started it yourself (`docker compose up -d --wait kokoro`) or another chat did, the script says so, leaves that container exactly as it is, and doesn't stop it afterwards. Whoever started it stops it: the other chat's script when that chat ends, or you with `docker compose stop kokoro`.
  - Started with plain `docker compose run --rm jarvis`, he has no sound devices, so he says his voice is off.
  - What he speaks is the answer's own words, tidied for the ear: the marks for headings, lists, bold and code are left out, and code blocks, emoji and most file paths and web addresses are skipped. With `JARVIS_SPOKEN_STYLE=on`, anything in code marks is skipped too, found the way Markdown finds it within a line, so a stray backtick pairs with the next one; code marks left open, or code that runs over a line or past 400 characters, are still read out. A word counts as a path if it has a backslash in it, or a slash and one of these: it starts like a path (`/`, `~/`, `./`, `../`), ends in a slash or a file ending, starts with a site's name, has `://` in it, or is written whole in code marks. A table row is read as a list, and a list's number is read with a pause after it. The tool notes, the timing and cost lines and the yes-or-no question before a hub action aren't spoken, but what he said before one of them is spoken while it happens. If the engine starts an answer again, he starts speaking it again from the top. The screen shows exactly what it would without a voice, though `JARVIS_SPOKEN_STYLE` changes how he writes.
  - The prompt comes back as soon as the words are done, and he carries on speaking behind it. `new`, `exit` and Ctrl+C stop the sound at once. A new question, or Enter on an empty line, interrupts him the way `JARVIS_SPEECH_STOP` says, and a note says so: `(stopped talking)`, `(the last answer won't be spoken)` if he hadn't started, or `(stopping after this sentence)`. With `sentence`, if he's already on the last sentence nothing is cut, so there's no note; with `now`, the last sentence is cut short like any other, and noted. An empty line typed before the prompt is back is ignored, so an Enter pressed while you wait doesn't hush him before he's said anything; a question typed then is still asked once the prompt is back (record 0025). Until the prompt is back, which can be a while when he's using tools, only Ctrl+C stops the sound, and that ends the chat. At a hub action's yes-or-no question, an empty line still means no.
  - Each sentence is one request to Kokoro and is played by an `aplay` of its own. `aplay` and `amixer` get only `PATH` from Jarvis's environment, never his API key or tokens. Kokoro is asked for one sentence at a time and gets at most two ahead of what's playing. With `JARVIS_SPEECH_BUNDLE=on`, below, one request can hold several sentences, and what this paragraph says of a sentence's sound (skipped if it can't be made or played, two in a row, the time it gets to play) applies to that whole piece; the 40-sentence limit and the log still count sentences. Only the first 40 sentences of an answer are spoken. A sentence that can't be made or played is skipped. Two in a row that can't be made, or two in a row that can't be played, end the speech for that answer. Either way a note says so before the next answer, or when the chat ends (record 0023). The exception is a sentence he's finishing after being interrupted with `JARVIS_SPEECH_STOP=sentence`: if it can't be played, that's only counted in the log. A sentence gets twice its own length plus 10 seconds to play; a player still going after that is stopped, and the sentence counts as one that couldn't be played. A player that's stopped is asked to end first, and killed outright if it hasn't ended 2 seconds later, so a stuck one can't keep the chat from closing. Before the next sound, even in the next answer, he waits up to 3 seconds for that player to have ended, so a slow one has time to let go of the speakers before another starts. After 3 seconds the next one starts anyway. The wait doesn't count towards the next sound's time to play, and the log times a sound from when it reaches its player, after the wait. Only this chat's players are waited for, not another chat's.
  - With `JARVIS_LOG=on`, each answer given with his voice on gets a second line in the log when its speech is over: how long after the question the first sentence was sent to Kokoro, its sound came back and the first sound that played reached the player, the longest silence between two sentences (from one sentence's player finishing to the next sound reaching the player, so it leaves out `aplay` starting up and any quiet inside a sound, and it's empty when fewer than two sentences played; with `JARVIS_SPEECH_BUNDLE=on` it's between pieces, since sentences in one piece share one sound), how many sentences were spoken, failed (split into those that couldn't be made and those that couldn't be played) or left, how many requests the speech engine got and how many sentences went in them, including any made before an answer started again (record 0036), and whether the speech was stopped early, given up on or cut at 40 sentences. Never the words, and never the error a sentence failed with (record 0032). `npm run compare` shows the time to first sound and the longest silence, with the first question of each chat kept apart from later ones because Claude is slower on it. Kokoro is already warm by then, from the start-up sentence. A second table adds up, for each setting, the sentences played to the end, failed and not played in full, and the answers that made no sound, were stopped, were given up on or went over 40 sentences. Under it, each setting where sentences failed gets a line saying how many couldn't be made and how many couldn't be played. Log lines from before that split don't say which, so that setting's line counts them separately. Then a line for each setting says how many sentences the engine (Kokoro or Piper) was asked for in how many requests, and how many that is a request on average, which shows whether `JARVIS_SPEECH_BUNDLE` is really bundling; older log lines don't have it and are left out of it.
  - Kokoro is set to log errors only (`API_LOG_LEVEL` on the `kokoro` service). Left to itself it writes the first 50 characters of every piece of text it's asked to speak into its log, which Docker keeps; that's from its v0.10.0 code and docs, read and not yet seen on this server. A Kokoro that was already running when the setting changed keeps its old one. Stop it with `docker compose stop kokoro`, and the next `bash host/jarvis.sh` makes a new container with the new setting.
- `JARVIS_KOKORO_VOICE`: which of Kokoro's voices he speaks in, default `bm_george`. It takes any of Kokoro's voice names (`bm_fable`, `bm_lewis` and `bm_daniel` are other British male ones), or a blend like `bm_george(2)+bm_fable(1)`. Kokoro checks the name itself, so a wrong one shows in the `Voice:` line.
- `JARVIS_KOKORO_SPEED`: how fast Kokoro speaks, default `1`, its usual pace. Any number from `0.25` to `4`, like `0.9` for a little slower. It's sent with every piece of speech, the start-up sentence included. With Kokoro on, each answer's line in the log records it (`kokoroSpeed`), and `npm run compare` keeps different speeds apart; lines from before it was logged show as "speed not logged". The voice's name (`JARVIS_KOKORO_VOICE`) isn't logged.
- `JARVIS_PIPER_VOICE`: which of Piper's voices he speaks in with `JARVIS_VOICE=piper`, default `en_GB-alan-medium`, a British male voice. A name is the voice's language, speaker and quality, like `en_GB-northern_english_male-medium`; they're listed at https://huggingface.co/rhasspy/piper-voices/tree/main. It's checked every time he starts, voice or not.
  - Piper has no internet, so download the voice once before its first chat, after setting this: `bash host/jarvis.sh piper-voice`. It saves the voice named here in `piper/voices` (git-ignored, so a voice is never in this public repo), with its `MODEL_CARD`, which says where its recordings came from and their licence. Nothing is saved unless all three files arrive. Run it again to replace a voice. With the voice not downloaded, `bash host/jarvis.sh` stops before starting anything and says so.
  - Piper splits each piece of text into sentences itself and makes them one at a time, so with `JARVIS_SPEECH_BUNDLE=on` it gets fewer requests but no longer pieces to work on.
  - To start Piper by hand, as the Kokoro text above describes for Kokoro, use `PIPER_VOICE=<voice> docker compose up -d --wait piper`. Without `PIPER_VOICE` it's given `en_GB-alan-medium`, and Piper stops at once if the voice it's given isn't downloaded.
  - A `low` or `x_low` voice is played at 16,000 Hz and a `medium` or `high` one at 22,050 Hz. A voice whose settings give another rate isn't saved, and if Piper ever sends sound at another rate, that piece fails with a message saying so.
  - The alan voice's licence isn't clear: it's fine-tuned from a voice whose recordings are for research only, and its own recordings' licence reads "All Rights Reserved" (record 0034). It's used at home and never shared.
  - Piper has a 1 GiB memory limit, no published port, and the same network as Kokoro, `speech`, with no internet. It reads `piper/voices` read-only. It logs its start and its errors, never the words it speaks; it would only log them with `--debug`, which isn't set.
- `JARVIS_SPEECH_START`: `sentence` (default) or `clause`. With `sentence`, the first thing he says is the answer's whole first sentence. It's sent to Kokoro once the next sentence has begun, or a line ends, a tool starts or the answer ends. With `clause`, the first piece can end at the first comma, semicolon, colon or dash that has at least 20 spoken characters before it, so he starts sooner at the cost of a pause there. Only the first piece of an answer is cut that way, and the first piece after each tool he uses. The log records which, so `npm run compare` shows the time to first sound for each. It's checked every time he starts, voice or not.
- `JARVIS_SPEECH_STOP`: `now` (default) or `sentence`: what a new question or an empty line does while he's talking. With `now`, he stops at once, mid-word if need be. With `sentence`, he finishes the sentence he's on (with `JARVIS_SPEECH_BUNDLE=on`, the piece he's on, which can be several sentences) and says nothing after it; a new question is still sent straight away, and its answer's first sound waits until that sentence is over. Either way `new`, `exit` and Ctrl+C stop him at once. The log records which, so `npm run compare` shows each setting's times side by side. It's checked every time he starts, voice or not.
- `JARVIS_SPEECH_BUNDLE`: `off` (default) or `on`. With `on`, an answer's first piece (its first sentence, or its first clause with `JARVIS_SPEECH_START=clause`) still goes to Kokoro on its own, so its first sound comes as soon as before. After that, whenever Kokoro is free, the sentences already waiting go to it together. A sentence is only joined onto one that ends with a full stop, question or exclamation mark or ellipsis, so a line ending in a colon, or a list item without a full stop, isn't run into what follows. List items that end with a full stop are joined like any other sentences. A piece is no longer than twice the last piece Kokoro made, or 250 characters, whichever is smaller. Nothing is held back to wait for more. Kokoro's notes on its voices say they're weakest on very short pieces and suggest bundling them (https://huggingface.co/hexgrad/Kokoro-82M/blob/main/VOICES.md). Each piece is played by one `aplay`, so with `JARVIS_SPEECH_STOP=sentence` he finishes the whole piece he's on, which can be several sentences. The log records which, so `npm run compare` shows the times for each. It's checked every time he starts, voice or not (record 0033).
- `JARVIS_SPOKEN_STYLE`: `off` (default) or `on`. With `on` and his voice on, his instructions gain a paragraph asking him to write for the ear: lead with the answer, keep sentences short with the first one shortest, write numbers and units as they're said, leave out headings, tables and bold, use a list only when the order matters, and put file paths, commands, settings, web addresses and code in code marks without needing them to make sense of a sentence. What's in code marks is shown on screen but not spoken, with the exceptions above. It changes what's written too, since there's one answer for both. With his voice off, or if it can't start, his instructions are as they were. The log records which, so `npm run compare` shows the times for each. It's checked every time he starts, voice or not (record 0031).
- `JARVIS_PERSONA`: `off` (default) or the name of a file in `jarvis/persona/` without the `.md`, like `butler` (record 0050). He reads that file once when he starts and adds it to his instructions straight after his own, before the live facts, spoken style and session notes, under a line saying it shapes his manner only, never changes what he can do, and lasts the whole chat, tool use included. Only lowercase letters, numbers and dashes are allowed in the name, so it can't point outside that folder, and he won't start if the file is missing, empty or over 4,000 characters once tidied (blank space at either end trimmed, hidden characters taken out, as for session notes). Every character is sent with every question, so keep it short: `butler.md` with the line before it is about 1,400 characters, something like 350 tokens (Claude's estimate). His start-up line names it and counts its words, and the log records its name (never its words), so `npm run compare` shows each persona's numbers side by side. Edit the file and start him again to change it. `jarvis/persona/` is in this public repo, so keep personal details out of it; they belong in the brain.
- `JARVIS_LIVE_FACTS`: `off` (default) or `on` (record 0050). With `on`, his own code writes a short paragraph about what's switched on in this chat and adds it to his instructions: whether his voice is on and which engine is speaking, how you can talk to him (typing, `/talk`, the wake word, the talk button, and the follow-up window), whether he has the hub's tools and actions, and that he can't run commands, change files, browse the web or set reminders. With `JARVIS_EARS` on, it also lists the code words his own code answers before he sees them, and tells him that if you ask for one of those and it reaches him, his code didn't catch it: typed messages never count, but typed and spoken ones reach him the same way, so he should never say which it was, never claim he did it, and tell you to say the words out loud, on their own or as the last thing you say (record 0052); with no hub token, it adds that notes, the phone and train times won't work until hub tools are on. It's written from what actually started (a voice that fails to start counts as off), and it says to trust it over older notes about himself. With everything on it's about 1,700 characters, something like 400 tokens (Claude's estimate). The log records whether it was on, so `npm run compare` shows the numbers with and without it.
- `JARVIS_FILLER`: `off` (default) or `on` (record 0044). With `on` and his voice on, when a tool starts in the middle of an answer and he has then been quiet for 1.2 seconds (nothing playing, being made or waiting to play, and the last answer's speech over), he plays two short low notes, 230 ms in all, unlike the wake word's chime. It plays at most once per tool call, and not at all once the answer's words come back, a yes-or-no question or a note comes up, the answer ends or is stopped, or his speech has been given up after two failures. A hub action asks first, so it gets none. A stop cuts it off. His speech isn't over until it has played, so the chat holds the wake word through it and ears doesn't hear it. It isn't logged.
- `JARVIS_EARS`: `off` (default), `push` or `wake`. With `push` or `wake`, `bash host/jarvis.sh` puts him on ears's network with `docker-compose.talk.yaml` and passes in `EARS_TOKEN` from `ears/.env`, and he can take a spoken question (record 0038). Type `/talk`: he stops talking at once and ears records for up to 30 seconds. Press Enter on an empty line to send it: he waits for Whisper's text, shows it as `You said: ...`, and answers it like a typed question. Type anything else to drop the recording, which ears then ends without sending it to Whisper; if it had already ended at its 30-second limit and been turned into text, ears clears that text instead. If ears doesn't answer a start or a stop, he cancels the recording anyway, in case it went through. His start-up line says whether ears is ready, muted or out of reach; the script doesn't start ears, so start and unmute it first (below). The log keeps how long a spoken question was recorded and how long its text took after Enter, never the words, and `npm run compare` shows them. Once asked, a spoken question is like a typed one: it goes to Anthropic's API, and with `JARVIS_CHATS=resume` it's saved with the chat. With `off` he isn't on ears's network and has no token.
- With `JARVIS_EARS=wake`, "Hey Jarvis" works as well as `/talk`, when ears has `EARS_WAKE=on` (record 0039). The chat waits on ears the whole time it's open, even while he answers, and a line under the prompt says when the wake word is on, or why it's off and what to do. When ears hears "Hey Jarvis" and the chat takes the recording, he stops talking, shows that he's listening, and, with his voice on, plays two short notes. Ears ends the recording once you've stopped talking (by loudness, or with `EARS_WAKE_END=silero` by Silero's speech detector); press Enter on an empty line to send it sooner, or type anything else to drop it. Then he shows `You said: ...` and answers, as with `/talk`. While any recording runs, `/talk`'s included, ears doesn't pass the microphone to openWakeWord, so "Hey Jarvis" said then does nothing. A wake after a `/talk` recording has ended at its 30-second limit, but before you've pressed Enter, takes over, because ears only keeps the latest recording (record 0040). Only one open chat takes each wake: a chat waiting for you to type takes it at once, and one that's still busy, answering or asking you something, waits a second first, so an idle chat gets it if there is one (record 0040). A chat that ends while it has a wake recording it hasn't finished with cancels it, so its text isn't left in ears. A false wake from the TV asks Claude whatever Whisper heard, unless ears heard nothing it counted as speech, in which case it's dropped; mute ears when you don't want him listening. The log marks these questions with `wake`, and which way ears was set to end the recording with `ender` (`loudness` or `silero`, even when you sent it with Enter or it ran to 30 seconds), and the pause it was set to end on with `pauseMs` (from `EARS_WAKE_PAUSE`), and `npm run compare` counts them, splitting their recording times by `ender` once both appear, and by `pauseMs` once two pauses appear. If ears ignores a "Hey Jarvis" because openWakeWord reported it more than 2 seconds after the sound, the chat says so on a line of its own, with how far behind it was. If the chat stops watching ears for any reason but closing, its status line says so (`wake word off: this chat stopped watching ears (...)`), rather than carrying on without the wake word.
- `JARVIS_FOLLOW_UP`: `off` (default) or a whole number of seconds from 2 to 15, only with `JARVIS_EARS=wake` (record 0043). Once he has answered a question you asked with "Hey Jarvis" (not when the answer failed) and his last sound has played, he waits half a second and asks ears to listen again for that many seconds without the wake word. A line under the prompt says he's listening for a follow-up; there's no chime. Start speaking within that time and it's recorded and asked like a wake question, and then the next window opens. Say nothing and it's dropped without going to Whisper, with a line saying so. Typed and `/talk` questions open no window, and anything typed before it opens (Enter on an empty line included), or a wake word, calls it off. After 5 follow-ups in a row he says to use "Hey Jarvis" again, because anything said in a window, the TV included, is asked, and with `EARS_WAKE_END=silero` the TV's dialogue counts as speech. Ears refuses a window while any chat is speaking, and just after it starts, before it has heard the room; the chat shows why. If asking fails, as when ears doesn't answer in time, he cancels a follow-up ears may have started anyway. Ears needs rebuilding for it with `bash host/ears.sh start`: an older one answers 404, and the chat says so. The log marks these questions with `follow` (and `ender`), and `npm run compare` counts them.
- `JARVIS_TURN_CHECK`: `off` (default) or `on`, only with `JARVIS_EARS=wake` (record 0054). It's the second half of ears's `EARS_TURN_WORDS` (see ears below) and does nothing without it. With `on`, the chat tells ears it will judge, and when ears's own rules can't tell whether you'd finished, the chat that took the recording asks the model the chat uses one small question: a fixed instruction and what you've said so far (500 characters at most), answered with one word, `done` or `more`. It gives up after 1.2 seconds, and ears waits 1.5 seconds at most. `done` ends the recording after 0.7 seconds of quiet and `more` gives you 3.5; no answer leaves the usual pause. A line under the prompt says what was answered and how long it took, or that the answer came too late for ears to use. This is his code asking, not the AI deciding to: the answer can only be one of those two words, about the recording that's already running. Each check is a small API call that the chat's cost line doesn't count, and it sends what you've said so far to Anthropic about half a second into a pause, before the recording has ended and even if you then cancel it.
- `JARVIS_TRAIN_ALERTS`: `off` (default) or `on`, which needs `JARVIS_HUB_TOOLS=on` (record 0051). With `on`, the chat asks the hub's `GET /trains/changes` every 30 seconds while it's open, and when the hub's morning train alerts find a change, he says it (`Train change: The 07:14 is cancelled.`), or with his voice off shows it, as soon as the chat is quiet: not while he's answering or speaking, a recording is going on or waiting for you to press Enter, or a follow-up is on its way or open. He never cuts himself off for it; it waits, checking every 2 seconds, and anything you say or type next stops it like any of his speech. Only changes are said, never the reminder or the notices about the board failing, which still go to your phone like the changes. Changes found before the chat started aren't said. It's his own code that says them: they're never sent to Claude, logged, or followed by listening for a follow-up, and his speech holds the wake word as always, so ears doesn't hear him. With `TRAIN_ALERTS=off` in `api/.env`, the chat says so once and stops asking. An API from before this route says to rebuild it, and the chat stops asking. If the hub can't be asked, it says so once and keeps trying, and says when it answers again; changes the hub found while it couldn't be asked are said once it can, unless the hub restarted in between or the chat hadn't reached it yet. Only the newest 20 lines are kept waiting. With `JARVIS_LIVE_FACTS=on`, his live facts gain a sentence saying his code passes train changes on and that he doesn't see them, about 200 characters more.
- `JARVIS_BRAIN_QUESTIONS`: `off` (default) or `on`, which needs `JARVIS_HUB_TOOLS=on`, and `MEMORY_UPLOAD=on` in `api/.env` to file anything (record 0061). With `on`, typing `/questions`, or saying "brain questions" or "any questions for me" (the spoken list is with the code words below, and with it off they go to Claude as before), has Jarvis ask you a gap question or two about your brain. He never asks unprompted, and he never writes to the brain.
  - Finding them: his own code sends Claude a fixed instruction through the chat you're in, asking it to read the brain with its usual read-only tools and find up to two things worth asking: two files that contradict each other, a dated fact that looks out of date, or something mentioned but never explained. Claude must reply with a small block in a fixed form (`BEGIN QUESTIONS`, then `question:`, `files:`, `kind:` and `wrong:` lines for each, then `END QUESTIONS`). Words before the block are ignored. A reply that isn't in that form, has more than two, names a file that isn't a plain path in the brain or isn't there, or has a field over 300 characters, isn't guessed at: he says he couldn't read his list and stops. Any hub action Claude tries while looking is refused without asking you. The lines saying which files it reads are shown as usual; the block itself isn't.
  - It's part of the chat: the instruction and Claude's reply stay in the chat's history (and in a saved chat with `JARVIS_CHATS=resume`), so you can ask him about a question afterwards. Its cost is in the chat's cost line, it counts towards the chat's size, its length warnings and `JARVIS_LENGTH_CAP` like any question (past the cap he won't look), and it's not written to the answer log, so it can't be rated. Your answers aren't sent to Claude.
  - Asking: one question at a time, shown with which of how many it is, the files, and what looked wrong, and said aloud with his voice on. Your next line, typed or spoken (through `/talk`, Hey Jarvis or the talk button), is the answer. After a question he asks out loud in answer to something you said, he listens for a follow-up as usual with `JARVIS_FOLLOW_UP` set. `skip` passes a question over; for a suspected mistake he then asks whether to file it anyway, and only `yes` (or "yeah", "yep", "yes please", "file it") files it. `never mind` or `that's all` ends the questions. While they're open, everything you type is an answer except an empty line, `exit`, `quit`, `new`, `+`, `-` and `/` commands, and everything you say is an answer, code words included, except skip, never mind and a request to stop listening. A request to stop listening ends the questions like never mind, filing what you'd answered, and is never filed or asked: Jarvis says what he says outside them, and no follow-up listens again. So does ears muting itself because "stop listening" was all you said. An answer over 4,000 characters is refused and the question stays open.
  - Filing: when the questions end, by answering the last one, `never mind`, a request to stop listening, `new`, `exit` or the chat closing, his own code (not Claude, and not through any tool Claude has) sends one note to the hub's `POST /memory/inbox`, titled `brain questions`, so it's named like `2026-11-26-brain-questions.md`. For each question it holds `Jarvis asked:` with the question, the files, what looked wrong to him, and your answer marked `typed` (exactly as typed) or `spoken, as Whisper heard it`, with the date and time. It's written as questions and facts, never as instructions to change anything. Skipped gaps aren't filed, and if nothing was answered nothing is sent. If the hub refuses or can't be reached, he says why in plain words and prints the whole note in the chat so you can keep it.
  - With `JARVIS_LIVE_FACTS=on`, his live facts gain a sentence saying how you ask for them and that his own code asks and files, about 350 characters more.
- `JARVIS_CLOCK`: `off` (default) or `on` (record 0062). Jarvis has no clock of his own: Claude only knows what's in the chat. With `on`, his code gives him one, in two ways. Every question, typed or spoken, goes to Claude with one more line after it, like `[Time now: 13:52 on Thursday 26 November 2026, in London.]`, so he can answer anything where the time or the date matters. The line is never shown on screen, costs a few tokens a question and stays in a saved chat; it goes before the chat-size line when there is one. And asking the time or the date out loud, when that's all you say, becomes a code word (below) that his own code answers from the server's clock, with no call to Claude. Both give London's time, whatever time zone the server is set to. With `off`, nothing is added and those phrases go to Claude as before. It needs nothing from the hub, and the log doesn't record it.
- `JARVIS_WEB`: `off` (default) or `ask` (record 0063). Jarvis can't look anything up: Claude answers from what it already knows, the brain and the hub. With `ask`, you can have something looked up on the web by saying "look up" and a question (a code word, below) or typing `/lookup` and a question. Jarvis himself never touches the web. His code prints the question, says "Looking that up.", and hands only the question to a separate helper: the Claude Code program that comes with the Agent SDK, run once for that look-up and signed in to your Claude plan with `JARVIS_WEB_TOKEN`, not with his API key. The helper has two tools, web search and opening a page, and nothing else: no file reading, no commands, no hub tools, no brain and none of the chat. It starts in a new empty folder that's deleted afterwards, with an environment that holds the plan token and none of Jarvis's own settings. The answer is stripped of links and markup, cut to 1,200 characters, printed with the sites it came from and how long it took, and said aloud with his voice on. Claude never sees the question or the answer, so nothing from the brain can end up in a search and nothing a web page says can reach the Jarvis who reads your brain. With `off`, none of this exists: the phrases go to Claude and `/lookup` isn't a command.
  - The guard. Searches go through Anthropic, but pages are fetched from this server, so before the helper opens one, `jarvis/src/web-guard-run.ts` checks the address and refuses anything that isn't an ordinary public web page: an address that's a number, a name with no dot, a name ending in `.home`, `.local`, `.lan`, `.internal`, `.ts.net` and the like, an unusual port, a name or password in the address, and any name that leads to a private address when it's looked up. Claude Code follows a redirect between a name and the same name with `www.` in front without asking again, so the guard looks both up and refuses if either leads somewhere private. Opening a page isn't allowed by default: the helper may search, and a page opens only when the guard has run and said yes. So if the guard is missing, crashes, takes too long or can't tell, the page isn't opened. It checks where a name leads just before the page is fetched, so a name that changes in between could get past it.
  - While it runs. A look-up runs in the background, so the chat stays free. One that fails gets "I couldn't look that up." with the reason printed underneath. Typing anything but a rating, saying "Hey Jarvis", asking for another look-up or ending the chat stops it, and one that takes longer than 45 seconds is stopped. A question is cut to 300 characters. There's no limit on how many you make: he says he's looking it up every time, and you decide.
  - `JARVIS_WEB_BY`: `claude` (default) or `api` (record 0064). Who does the looking up. `claude` is the helper above. `api` asks Anthropic's API with its own web search tool switched on, in one request from Jarvis's code with his API key: no program is started and no page is fetched from this server, since the search results reach Claude with their text, so the guard has nothing to do. It makes at most three searches for a look-up and is sent the question and nothing else, like the other helper. It's here so the two can be compared: each look-up's line in the logs says which did it, and `npm run compare` shows them side by side. With `api`, `JARVIS_WEB_TOKEN` isn't needed.
  - What it costs. Look-ups by `claude` run on your Claude plan, so they come out of the same allowance as your chats and Claude Code, not out of API credits. Claude Code still reports what each would have cost at list prices, which `npm run compare` shows. Look-ups by `api` are paid for from API credits: a cent a search, plus the tokens.
  - `JARVIS_WEB_TOKEN`: needed when `JARVIS_WEB` isn't `off` and `JARVIS_WEB_BY` is `claude`. `claude setup-token`, run on the server, prints a token that lasts a year; put it in `jarvis/.env` on one line. It's a secret: never in the repo and never pasted into a chat. Jarvis reads it once as he starts and removes it from his own environment, so only the helper is ever given it. Its expiry date is worth a line in `expiry/items.json`.
  - `JARVIS_WEB_LOG`: `off` (default) or `on`. With `on`, each look-up adds a line to `jarvis/data/look-ups.jsonl`, which git ignores: its numbers, the question that was sent, the sites it found, opened and was refused, and for one that failed, what went wrong in the helper's own words. Never the answer. It's the one log that holds your words, because the question is the one thing that leaves the server; delete the file to clear it. With `JARVIS_LOG=on`, each look-up's numbers alone also go to the answer log, and `npm run compare` reports them: how many, how they ended, how long they took and how long Claude Code took to start, searches, pages opened and refused, tokens, the estimated cost, what kind of thing went wrong, and the sign-in each one reported, which shows whether Claude Code really ran on your plan.
- Not listening to himself: every chat with his voice on and `JARVIS_EARS=push` or `wake` holds the wake word from when he starts answering (and while he says his start-up sentence) until his last sound has played, renewing the hold every 5 seconds, so ears doesn't listen to him. A recording that's already running while any chat holds it, as when a second chat starts speaking during it, hears silence for that stretch instead of him (record 0040). Holds need `EARS_WAKE=on`: with the wake word off, ears takes none, so a `/talk` recording made while another chat is speaking hears him. Ears starts again half a second after the last chat lets go, and a hold runs out by itself after 15 seconds if a chat stops renewing it. A chat with `JARVIS_EARS=off` can't reach ears to hold it, so don't have one speaking while a wake chat is open. With `EARS_INTERRUPT` set in `ears/.env`, ears does listen for some things during a hold, so you can interrupt him: see ears below (record 0055).
- `JARVIS_SOUND_CARD`: the speakers' name under `/dev/snd/by-path`, like `pci-0000:04:00.6`. `ls -l /dev/snd/by-path` lists the names and the card each leads to, and `cat /proc/asound/cards` says which card is which. `bash host/jarvis.sh` reads it, for the sound test and for a chat with his voice on: it follows the name to the card's number for this boot, and passes in only that card's mixer and speakers. Names stay the same after a restart; card numbers might not, and both cards on this server are called `Generic`, so their `CARD=` names can swap too. Set it again on a new server. Only the script reads it, so it isn't on his start-up line; his `Voice:` line names the card it led to.
- `JARVIS_VOLUME`: `0` to `100`, default `80`. Before anything plays, Jarvis sets the card's `Master` control to this and unmutes it (`0` mutes it), because the server forgets the level when it restarts and comes back muted (record 0015). The sound test does this, and so does a chat with his voice on. It's checked every time he starts, voice or not.
- `JARVIS_CHATS`: `fresh` (default) saves nothing; `resume` saves the chat in `jarvis/data/chats/` and picks it up next time.
  - Saved chats hold everything said, brain text included. Only their owner can read them, and backups copy them.
  - Every question sends the whole saved chat. On Haiku 5.5, a request over 100,000 tokens costs five times as much. Jarvis doesn't trim saved chats yet. The Agent SDK only summarises a chat when it nears its context limit (about 990,000 tokens in a test), so it pays the higher rate long before that.
  - When a chat reaches `JARVIS_LENGTH_WARN` (80,000 tokens unless set), Jarvis says once that it's getting long (once per start of Jarvis). Past 100,000, where Haiku 5.5's long-prompt price starts, he says so after every answer, with how to start a new one (unless `JARVIS_LENGTH_WARN` is set higher, when he waits for that). It goes by each answer's last request, and works in fresh chats too. With `JARVIS_LENGTH_HINTS=jarvis`, Jarvis is told the size instead and suggests a new chat himself.
  - Type `new` to start a new chat without leaving Jarvis. In a saved chat, the old one is moved to `jarvis/data/chats/old/` (private, the newest 10 per engine kept), Jarvis says exactly where, and it isn't carried on. To get it back, move it back by hand. A plain API chat brings its size back with it (if it was saved since sizes were kept); an Agent SDK one usually has no size known until its first answer. A leftover `*.saving` file is a save that was cut off, and is safe to delete.
  - Lines shaped like a command (a `/` then one word, like `/clear`) aren't sent to Jarvis, on either engine. The Agent SDK would otherwise run them as its own commands; `new` does that job on both. Paths like `/etc/hosts` go through as normal.
  - Run one Jarvis at a time on a saved chat: with two, one of them's questions won't be carried on.
  - The engines save differently: the Agent SDK also keeps questions that failed or were stopped, and the plain API engine keeps only answered ones. On the plain API engine, thinking is left out of the saved chat for good with `JARVIS_THINKING_HISTORY=drop`, or after a thinking restart.

## Folders
- `api/`: the API. Fastify and TypeScript on Node 26, one module per folder in `src/modules/`, with each module's tests beside its code.
- `hub/`: the phone page.
- `mcp/`: the MCP server for Claude Code. Same setup as `api/`.
- `jarvis/`: Jarvis, a text chat that reads the brain, with two engines to compare: the Agent SDK and a plain API call. With `JARVIS_VOICE=kokoro` or `piper` he also has a voice: one sentence when he starts, then his answers, a sentence at a time. Its settings live in `jarvis/.env` (below), and `jarvis/data/` (git-ignored) holds the answer log and any saved chats. `jarvis/Dockerfile` is his image for sound.
- `jarvis/persona/`: how Jarvis comes across, one file per persona, for `JARVIS_PERSONA`. `butler.md` is Claude's draft, there to be edited. It's tracked, so keep personal details out.
- `host/`: files that run outside Docker (the Wi-Fi watchdog, and the backup script with its service and timer), plus helper scripts: `hub-update.sh` pulls and rebuilds only what changed, `hub-mcp.sh` starts the MCP server, `jarvis.sh` starts Jarvis with the API token for the hub's tools and the sessions' notes (and, with his voice on, with his speakers, starting and stopping Kokoro or Piper around the chat, and with `JARVIS_EARS=push` or `wake`, with ears's network and token), runs his sound test, or downloads Piper's voice, `ears.sh` mutes and unmutes ears and checks its microphone, and `hub-get.sh` and `hub-post.sh` try an API route, and `ebay-check.sh` tests the eBay keys without showing them.
- `deals/`: the deal watcher's search list and state file, both git-ignored. Only its `README.md` is tracked.
- `expiry/`: the list of things that expire and the record of warnings sent, both git-ignored. Only its `README.md` is tracked.
- `piper/voices/`: the voices Piper speaks in, downloaded by `bash host/jarvis.sh piper-voice` and git-ignored.
- `ears/`: "ears", the service that owns Jarvis's microphone. Node 26 and TypeScript with its own tests, built into its own image, which also holds Silero's speech detector (record 0042) and the voice model (record 0056). `ears/switch/` (git-ignored) holds its mute switch, and `ears/voice/` (git-ignored, readable only by you) your voiceprint.
- `whisper/`: `sitecustomize.py`, which keeps Whisper's transcripts out of its log, and `models/` (git-ignored), where `bash host/ears.sh whisper-model` puts Whisper's model.
- `openwakeword/`: `health.py`, the wake-word server's health check.
- `caddy/`: the Caddyfile.
- `homepage/config/`: Homepage's settings. Logins and keys come from `homepage/.env`.
- `docs/`: `restore.md` (getting files back from a backup), `going-private.md` (what to do if this repo goes private), `deals.md` (setting up and using the deal watcher) and `decisions/` (why things are the way they are, one record per decision).
- `.github/`: tests and safety checks on every push, and Dependabot.
- `CLAUDE.md`, `.mcp.json` and `.claude/settings.json`: how Claude Code works in this repo.

## Running it
Secrets live in `.env` files that git ignores (`api/.env`, `homepage/.env`, `beszel/.env`, `jarvis/.env` and `ears/.env`), so they're never in this repo. The API also expects the brain's inbox at `../hub-memory/inbox`, and won't start without it. The backup's settings and password live in `/etc/home-hub/`, outside this folder and readable only by root.
- Start everything: `docker compose up -d`
- Rebuild the API after a change: `docker compose up --build --wait api`
- Pull from GitHub and rebuild only what changed: `bash host/hub-update.sh`, or `bash host/hub-update.sh --dry-run` to see what it would do. When `mcp/` changes, it also rebuilds the copy Jarvis runs. When Jarvis's packages change (`jarvis/package-lock.json`), it reinstalls them and runs his engine check, since a new Agent SDK brings a new engine. A change to his code alone needs nothing, because he builds himself each time he starts. Close Jarvis before updating: reinstalling packages replaces folders a running chat is using.
- Talk to Jarvis: `docker compose run --rm jarvis`. He's in the `jarvis` profile, so `docker compose up` never starts him. Type `exit` or press Ctrl+C to stop, and `--rm` removes the container. He needs `jarvis/.env` and the brain at `../hub-memory` (mounted read-only), and won't start without them. With `JARVIS_HUB_TOOLS=on`, `JARVIS_SESSION_NOTES=on`, `JARVIS_EARS=push` or `wake`, or his voice on, start him with `bash host/jarvis.sh` instead. He's on his own Docker network, `jarvis`, which only the API shares, so the API is the one container he can reach directly (when `host/jarvis.sh` gives him sound, for a chat with his voice on or for the sound test, he's also on `speech`, where he reaches Kokoro and Piper; with `JARVIS_EARS=push` or `wake` he's also on `ears`, where he reaches ears, Whisper and openWakeWord). Services with a published port or a `.home` name can still be reached through the server's address, as from any device on the LAN, and he can reach the internet, which he needs for Anthropic's API (record 0013).
- Test Jarvis's speakers: `bash host/jarvis.sh sound-test`. It builds his image for sound, `home-hub-jarvis` (`jarvis/Dockerfile`: his usual `node:26-alpine` plus `alsa-utils`, from its cache after the first time), finds the card named by `JARVIS_SOUND_CARD`, sets `JARVIS_VOLUME`, and plays two short beeps, low then high. It adds `docker-compose.sound.yaml`, the only place Jarvis gets sound devices: his card's mixer and speakers, read and write, never a microphone, and the group that owns them (record 0014). The same file puts him on the `speech` network, where Kokoro is when it's running; the sound test doesn't use it. Without it, as with `docker compose run --rm jarvis`, he gets none and runs on the stock image. A newer `node:26-alpine` reaches his image only after `docker pull node:26-alpine`.
- Ears, the service that owns Jarvis's microphone, and Whisper, which turns what it records into text (records 0035 and 0037). Jarvis uses them with `JARVIS_EARS=push` (record 0038) or `wake` (record 0039). Both are in the `ears` profile, so `docker compose up` never starts them.
  - Set it up once. `ears/.env` holds `EARS_TOKEN`, at least 32 characters (`openssl rand -hex 32` makes one), and `EARS_MICROPHONE`:
    - `card`: a real microphone, on the sound card that `EARS_SOUND_CARD` names, by its name in `ls /dev/snd/by-path` (like `JARVIS_SOUND_CARD`). That can be the laptop's own card, `pci-0000:04:00.6`, for its built-in microphone (it works, seen on 20 Nov) or a headset's in its jack, or a USB microphone's own card. At start, ears sets the card's `EARS_MIC_CONTROL` (default `Capture`) to `EARS_MIC_LEVEL` (0 to 100, default 80) and switches capture on, because a card's levels go back to how the driver starts them after a reboot. `EARS_MIC_LEVEL=keep` leaves the card's levels alone. `EARS_MIC_BOOST` is left alone unless it's set: a whole number of steps from 0 to 10 sets the card's `EARS_MIC_BOOST_CONTROL` (default `Internal Mic Boost`) at start too, for a microphone that's still too quiet with `EARS_MIC_LEVEL=100` (record 0041). A card's boost only goes so high (3 on many laptops' chips, per `amixer`), and amixer stops at its top. A card that names its controls differently needs `EARS_MIC_CONTROL`; `docker run --rm --device /dev/snd/controlC1 node:26-alpine sh -c "apk add --no-cache -q alsa-utils && amixer -c 1 scontrols"` lists card 1's controls from a throwaway container. That gives the container card 1's mixer, so it could change the card's levels, and nothing else of the sound devices; never give a throwaway container all of `/dev/snd`, which includes every microphone.
    - `pretend`: a quiet tone, so the rules around recording can be tried with no microphone.
    - Left out: it records nothing.
  - Then run `bash host/ears.sh mute`, which makes `ears/switch/`; ears won't start without that folder. And download Whisper's model once with `bash host/ears.sh whisper-model`, about 82 MB into `whisper/models/base-int8`: the `base-int8` model from its pinned version on Hugging Face, checked by size and, for the model itself, by its SHA-256, plus the tokenizer that model leaves out, from `openai/whisper-tiny`, which faster-whisper would otherwise fetch every time it starts. Whisper's network has no internet, so it can't fetch anything itself. Both `whisper-model` and `start` check the four files are there at their right sizes, and won't go on with part of a model.
  - Check the microphone from where you'll talk to it with `bash host/ears.sh mic-test`, or `bash host/ears.sh mic-test 10` to wait 10 seconds first (up to 60) so you can get there (record 0041). Stay quiet for the first 2 seconds, which it measures the room from, then talk as you would to Jarvis. It records 10 seconds from `EARS_SOUND_CARD`'s microphone with ears's own `EARS_MIC_LEVEL`, `EARS_MIC_CONTROL`, `EARS_MIC_BOOST` and `EARS_MIC_BOOST_CONTROL`, so it hears what Whisper and the wake word would. Then it prints the room's level and what counts as speech, in the same words and on the same scale as ears's log line for the wake word, how long you were above that, your typical and loudest level, your longest pause (ears ends a wake-word recording after 1.5 seconds of quiet, or `EARS_WAKE_PAUSE`), whether anything clipped, and the one setting to change next if it's too quiet or too loud. Turning the microphone up raises your voice and the room together, so when your voice is under six times the room's level (or, with no speech, never above three times it), more gain can't help, and it says to get closer, quieten the room or try another microphone instead. Then it plays the recording back on `JARVIS_SOUND_CARD`'s speakers at `JARVIS_VOLUME`. Change one setting at a time and run it again; ears itself uses a changed setting after `bash host/ears.sh stop` and `start`. It records in a throwaway container from ears's image (built as `home-hub-ears`) that has only that card's microphone and mixer, and plays in one from Jarvis's image that has only the speakers and mixer. The sound goes from one to the other through a pipe on the server, never a file, and neither container has a network or keeps a Docker log. It's a command you run by hand, so it has no setting to switch it on, and it refuses to run anywhere but a terminal someone is typing in. Just before it records, if ears is running, it asks ears whether it's muted (`ask.js health`, which prints the status code and one word), because only one program can have the microphone open at a time, and ears comes back muted after a restart whatever the switch file says. If ears answers anything else, it stops and asks you to mute ears first; if ears doesn't answer clearly, it stops and says to wait or to stop ears. It never mutes or stops ears itself.
  - Start them with `bash host/ears.sh start`, and stop them with `bash host/ears.sh stop`, which stops openWakeWord too. Start builds ears's image from `ears/` (from its cache after the first time; `host/hub-update.sh` doesn't rebuild it), starts Whisper (and openWakeWord, with `EARS_WAKE=on`) and waits for it to be healthy, then starts ears. Stop ends them within a second or so. With `EARS_MICROPHONE=card` it adds `docker-compose.mic.yaml`, the only place ears gets a sound device: that one card's mixer and microphone, read and write, never its speakers, and the group that owns them. Started any other way, as with `docker compose up -d ears`, ears gets no device, and with `card` it then won't start, saying how to start it.
  - Mute or unmute it with `bash host/ears.sh mute` or `bash host/ears.sh unmute`. They write `ears/switch/mute`, which ears reads every 200 ms through a read-only mount, so no container can change it through its own mounts. Ears always starts muted, even if the file says unmuted: only an unmute it sees appear after it started counts, and each one counts once. If it can't read the file when it starts, what it first reads counts as old, so unmute again once it can. Muting ends a recording within about a second (one look at the file, plus a second if the recorder has to be killed), and so does a new unmute while recording, in case a mute came and went between two looks. If a mute can't be written, as on a full disk, the script removes the file instead, which also counts as muted.
  - Try it from inside its container: `docker compose exec ears node dist/ask.js state`, or `start`, or `stop`. It prints the status code and ears's answer, and exits with 1 if ears said no. `health` prints only the status code and the state's one word: it's what ears's health check runs, because Docker keeps what a health check prints, and the state can hold the text. Its API is `GET /state`, `POST /recording/start`, `POST /recording/stop` and `POST /recording/cancel` on port 8090, with `EARS_TOKEN` as a Bearer token. Every answer includes `lastId`, the number of the last recording that ended, and a start's answer includes `id`, the new recording's number. Numbers carry on from the time ears started, in milliseconds, so a restarted ears doesn't reuse one a chat may still hold, as long as the server's clock doesn't go back. Stop and cancel can name the recording with `?id=<number>`, and then act only on that one: one that has already ended while a newer one runs is refused with 409, and one ears has moved on from is refused with 410 (record 0040). Jarvis always names his; without `?id=`, as from `ask.js`, they act on whatever ears has. Cancel ends a recording without sending it to Whisper, drops the text if Whisper is already working on it, or clears the text if it's already made. It's on its own network, `ears`, which is internal and isolated. Its container runs with Docker's own init as its first process, so ears isn't process 1 (Linux ignores a stop sent to process 1 unless the program itself handles it), a read-only filesystem, every Linux capability dropped and `no-new-privileges`, so nothing in it can gain rights it wasn't started with. Whisper and openWakeWord share the network, and Jarvis joins it only through `docker-compose.talk.yaml`, with `JARVIS_EARS=push` or `wake`.
  - It reports one state: `muted`, `idle`, `recording`, `working` or `failed`. Failed means its recorder ended by itself or couldn't start, and it records nothing until it's unmuted again. A recording stops when asked, when ears is muted, after 30 seconds, or if more sound comes than 37.5 seconds' worth (a quarter extra, for sound arriving in bursts). Ending it ends the recorder and anything it started that's still in its process group; with the wake word on, recordings share one recorder, which ends when ears is muted or no wake chat is waiting. The recorder is `arecord` for a card, giving 16-bit mono at 16,000 Hz.
  - A recording that was asked to stop, or ended at its time or sound limit, is turned into text: ears is `working` while Whisper does it, records nothing new meanwhile, and gives Whisper a minute. The answer to `stop` waits for the text, and the state's `last` holds it (`text`), or why there's none (`textProblem`). A recording ended by a mute, by a new unmute or a cancel (even one that comes while a stop is still ending it) or by its recorder failing is never sent to Whisper, and a mute or a new unmute while Whisper is working drops its text even if it comes. The sound stays in ears's memory until Whisper has it, and Whisper writes each recording to a file in its `/tmp`, which is in memory, and removes it when it's done. Memory can be moved to swap, if the server uses swap. The text stays in ears's state until the next recording ends, ears is muted or asked to cancel, or ears stops; a mute or a cancel clears it and says so. Nothing writes it anywhere.
  - `docker compose logs ears` has a line for each start, stop (why, and how long), mute, unmute, text made (how long, never the words), text not made (why), text cleared by a mute, never the sound, and never the token unless a recorder prints it when it fails. Whisper would log every transcript at its normal level, and has no setting for that, so `whisper/sitecustomize.py`, which Python loads at start because `PYTHONPATH` points at it, lifts that one logger to warnings only. Its other lines, and any errors, still show in `docker compose logs whisper`; one says how long each recording was, never what was said.
  - The wake word (record 0039). Ears passes the sound to openWakeWord, and on "Hey Jarvis" it starts a recording. A detection that openWakeWord sends more than 2 seconds after the sound it's about, with no time, or with a time ahead of the sound ears has sent it (left over from before ears paused), is ignored and logged as too late to trust. Ears sends openWakeWord whole milliseconds of sound, up to a second at a time, and holds what's left for the next piece: openWakeWord times what it hears by adding up each piece's length rounded down to a millisecond (its 2.1.0 code, through the `wyoming` library), so pieces of any size made its clock fall about 2.5 ms a second behind ears's on this server, and after about 13 minutes of listening with no recording, hold or closed microphone to restart both clocks, every detection looked late and was ignored. While any chat holds it (when that Jarvis is speaking), ears passes nothing to openWakeWord and throws the sound away; each chat's hold is kept apart and runs out by itself after 15 seconds unless it's renewed, and ears starts again half a second after the last one is let go. Before opening the microphone again, ears waits for the last `arecord` to have ended, because a second one couldn't open it. `EARS_WAKE_THRESHOLD` (above 0 and below 1, default 0.5, openWakeWord's own) is how sure openWakeWord must be: raise it if the TV sets him off. `EARS_WAKE_PAUSE` (seconds, 1 to 5 to a tenth, default 1.5) is how long a pause after you've spoken ends a wake recording or a follow-up: raise it if you pause mid-question and get cut off, at the cost of every answer starting that much later. To turn the wake word off again, set `EARS_WAKE=off`, then stop and start ears, since `start` alone leaves a running openWakeWord as it is. If openWakeWord can't be reached, ears says why, tries again every 5 seconds, and `/talk` still works. Its API adds `GET /wait?after=<version>`, which answers with the whole state, its version and which run of ears it is, as soon as any of it changes, or after 20 seconds; `POST /wake/claim?id=<number>` to take a wake-word recording; and `POST /wake/hold?by=<id>` and `POST /wake/release?by=<id>`, where each chat names itself with its own id. The `wake` part of a `/wait` answer also has `late`: how many detections ears has ignored as too late since it started, and how far behind the last one was (`behindMs`, or null when openWakeWord gave no time, or a time ahead of the sound ears had sent it). And `POST /wake/follow?within=<milliseconds>` (1,000 to 20,000, record 0043), which starts a recording that already belongs to the chat that asked. It's judged like a wake recording, against the room's level from before the last "Hey Jarvis" and with nothing ignored at the start, and it's dropped without going to Whisper if no speech comes within that time. It's refused with 409 while any chat holds the wake word, or before ears has heard the room. `docker compose logs ears` adds a line when the microphone opens or closes (and why), for each detection (with the room's level; openWakeWord sends no score), for one that came while it wasn't listening or too late to trust, and when the wake word stops or starts working. After a wake, follow-up or talk-button recording that had speech in it, a line says how long after it began speech was first heard, how much speech there was, and the longest pause between words, from the tenths of a second it already judges for the end of the recording (never the words). `bash host/ears.sh wake-report` counts those lines into a short report: how many times it heard "Hey Jarvis", how many it ignored as late or as coming after it stopped listening, how many wake recordings started, failed to start, were taken by a chat or by none in time, and how each ended: no speech in time (a false wake, or nothing said after it), cancelled, muted or failed, turned into text, or not turned into text after all. Then the same for follow-ups, for talk-button recordings, and for other recordings (`/talk`, or `ask.js start`). It reads the whole of ears's log, which Docker keeps from when ears's container was last made (it's made again when its image or settings change, which includes the microphone's card number changing after the server restarts), dropping the oldest lines past about 100 MB (Docker's `local` log driver, set in `host/daemon.json`, keeps five files of 20 MB). `bash host/ears.sh wake-report 6` reads only the last 6 hours (1 to 720). It ends with a line each for wake recordings, follow-up windows and talk-button recordings, leaving out recordings that were cancelled, muted, failed or taken by no chat: the median time until speech was first heard (with the shortest and longest), the median amount of speech, and the median and longest pause between words. The pause that ends a recording isn't a pause between words, so the longest can only reach `EARS_WAKE_PAUSE` less a tenth of a second; if your longest often come close to that, some of your pauses are probably as long as the setting, and it may have cut you off. A wake recording's first speech can't show before 0.9 seconds, since it ignores its first 0.8. A follow-up start later than `JARVIS_FOLLOW_UP` counts as no speech in time instead, so the follow-up times can show the window is longer than you need, not that it's too short. It prints only counts and timings, never what was said.

  - Silero's speech detector (record 0042). A wake recording ends once it's been quiet for 1.5 seconds (or `EARS_WAKE_PAUSE`) after you speak, and by default "quiet" means quieter than three times the room. A fan, music or the kettle can be loud enough to keep it going, and a quiet voice can drop under the line. With `EARS_WAKE_END=silero` in `ears/.env` (the default is `loudness`), quiet means Silero's speech detector heard no speech instead. Everything else about the ending (the first 0.8 seconds ignored, the 1.5 seconds or `EARS_WAKE_PAUSE`, 5 seconds, 30 seconds) stays the same.   - Interrupting him (record 0055). `EARS_INTERRUPT` in `ears/.env` is `off` (default), `wake` or `speech`, and needs `EARS_WAKE=on`.   - Voice ID (record 0056).     - `bash host/ears.sh voice-enrol` shows five short sentences one at a time and records each for 6 seconds, 2 seconds after showing it. Sit where you talk to Jarvis, with nobody else talking and the TV off. A sentence with less than a second and a half of speech is asked again, up to three times. The voiceprint is the average of the five, and if any one sounds unlike the others (under the threshold) nothing is saved. Nothing you say is kept: only the voiceprint, in `ears/voice/voiceprint.json` (the model's name, how many clips, when, and the 512 numbers), in a folder and file only you can read. It's biometric data about you: it's never in git, never logged and never printed. Running it again replaces it; delete the file to remove it.
    - `bash host/ears.sh voice-check`, or `voice-check 10` to wait 10 seconds first (up to 60), records 5 seconds and prints the score against your voiceprint and what it counts as at the threshold. Try yourself, the TV and other people, from where you'd talk.
    - Both run like `mic-test`: only from a terminal, never while ears is listening, in a throwaway container from ears's image with only the microphone and its mixer, no network and no log. The enrolment's voiceprint comes back through a pipe and the script writes it; the check runs as you, with `ears/voice` read-only, so it can read your file.
    - `EARS_VOICE_ID` in `ears/.env`: `off` (default), `observe` or `require`. `EARS_VOICE_ID_THRESHOLD`: above 0 and below 1, to two places, default `0.5`; enrolment and `voice-check` use it too. With `observe`, each recording with speech in it is scored before it's turned into text, and the log says the score and what it counts as, like `Voice: Score against the voiceprint: 0.84. At the threshold of 0.5, that counts as the voiceprint's voice.`; nothing is blocked. With `require`, a recording started by the wake word (or by speech over him, record 0055) or as a follow-up whose voice counts as a different one isn't sent to Whisper: the log adds `Not turned into text: the voice in it didn't match the voiceprint.`, and the chat says nothing was sent and why. A recording with under a second of speech can't be judged, so it goes through: blocking it would lose "yes", "no" and "stop". One where the check finds no speech loud enough to judge is blocked as too quiet to check (that can only happen with `EARS_WAKE_END=silero`, which hears quieter speech than the check does). Recordings started by the talk button or `/talk` are scored but never blocked, since someone started them by hand. If the check itself fails, or takes more than 10 seconds, a wake-word or follow-up recording is blocked, and the log says it couldn't be checked. The voice is checked once a recording has ended, so with `EARS_INTERRUPT` on a cut-in still stops him even when its recording is then dropped: `require` keeps the TV's words from being asked, not from interrupting him. With `EARS_TURN_WORDS=on` as well (record 0054), `require` reads the words at a pause only when the voice so far counts as yours, whoever started the recording; otherwise that pause isn't looked at and the usual pause applies, so an answer under a second ends on the usual pause. Words read at a pause can still belong to a recording that's blocked at the end, if another voice came in after yours. `bash host/ears.sh start` checks the setting, refuses if there's no voiceprint yet, and adds `docker-compose.voice.yaml`, the only place ears gets `ears/voice` (read-only, at `/voice`) and the memory for the model (384 MiB, not 256). Ears reads the voiceprint and loads the model when it starts, and won't start if it can't: then make a voiceprint, or set `EARS_VOICE_ID=off`. Ears runs as user 1000 in its container and the voiceprint is readable only by its owner, so this needs your user on the server to be 1000 (`id -u` prints it). `bash host/ears.sh wake-report` gains a line with how many recordings counted as your voice and as a different one, with the range of scores each way, which is how to pick a threshold. Stop and start ears to change either setting.
    - What counts: speech is from the first tenth of a second above ears's floor (300) to the last. Under a second of it is "too short" and has no score; at most 10 seconds of it are used. In tests on synthetic and recorded voices, the same voice scored 0.70 or more and different real people 0.55 or less, but noise lowers scores (to 0.40 with loud noise), so check your own numbers with `voice-check`. A recording of your voice would pass: it's a filter, not a lock.
    - The model adds about 50 MB to ears's memory when loaded, and about 60 MB more while it scores; one score took about 0.2 seconds for 10 seconds of speech on the machine this was built on (the server's CPU wasn't measured). The check runs before Whisper, so that time is added to every recording while `EARS_VOICE_ID` isn't `off`.
  - Whisper is `rhasspy/wyoming-whisper` 3.8.1, pinned by digest, with the `base-int8` model in English. It runs as user 10300, which has no account on the server, so it isn't root and owns none of my files, with its model folder and that one file mounted read-only, no port and no device, and `HF_HUB_OFFLINE=1` so Hugging Face's library never tries the network. Docker's own init (`init: true`) is its first process, because its image starts it from a bash script that wouldn't pass a stop on, so it would be killed after 10 seconds. Its memory limit is 1 GiB: it used 456 MiB after one recording on 20 Nov, and 479 MiB after a longer one on 21 Nov. If it ever needs more, Docker stops it, and ears says it can't reach Whisper until it's started again with `bash host/ears.sh start`; then raise the limit.

## Tests
Node isn't installed on the server, so npm runs in a throwaway container. From this folder:
```
docker run --rm -u node -v "$PWD/api:/app" -w /app node:26-alpine npm ci
docker run --rm -u node -v "$PWD/api:/app" -w /app node:26-alpine npm test
```
For the MCP server, use `$PWD/mcp` instead, for Jarvis `$PWD/jarvis`, and for ears `$PWD/ears`. An `.npmrc` in each of `api/`, `mcp/`, `jarvis/` and `ears/` turns off npm's notice that a newer npm exists, which each throwaway container would otherwise print after the results. Their npm is the one in the `node:26-alpine` image, so a newer one comes with a newer image. GitHub runs all four test suites, and Jarvis's engine check, on every push, alongside a secret scan of the whole history. The update script has its own tests, which use a pretend `docker` and throwaway git repos, so they change nothing. GitHub doesn't run them, so run them by hand after changing the script: `bash host/hub-update.test.sh`. Likewise `bash host/jarvis.test.sh` for `host/jarvis.sh`, with a pretend `docker` and pretend sound devices, `bash host/ears.test.sh` for `host/ears.sh` and the ears service's compose settings, and `bash host/ebay-check.test.sh` for `host/ebay-check.sh`, with a pretend `curl`, so it never contacts eBay.
