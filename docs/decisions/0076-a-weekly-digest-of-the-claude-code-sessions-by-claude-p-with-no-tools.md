# 0076. A weekly digest of the Claude Code sessions, written by claude -p with no tools

- Date: 2026-11-27
- Status: accepted

## Context
Jarvis knows the brain and, with `JARVIS_SESSION_NOTES`, the notes the two Claude Code sessions keep for themselves, but not what I actually did in those sessions this week. The transcripts are on the server in `~/.claude/projects/`, far too long to give him whole, and full of things that shouldn't travel: tokens pasted by mistake, tool output, other people's text from the web and GitHub. A summary written every few days by Claude on my plan, kept small, would let him answer "what have I been doing?", and the same summary could go to the brain's inbox so it gets filed.

## Options considered
Chosen 27 Nov (Phil): a weekly digest that goes to the brain's inbox, with a range and a buffer: it knows the past week and is refreshed every 3 or 4 days, so it's never empty after a reset.

Claude's picks, not discussed:
- Who writes it: the host's own Claude Code, `claude -p` on my plan's login, as the batch plan said. Not the API (costs credits per run) and not the Agent SDK inside Jarvis's container (it would need the transcripts mounted into the container that reads my brain).
- No tools at all: `--tools ""` for the built-in tools, `--disallowedTools "mcp__*"` for any MCP tool (the CLI reference says `--tools` doesn't affect those), `--strict-mcp-config` with no servers, `ENABLE_CLAUDEAI_MCP_SERVERS=false` so the claude.ai connectors aren't fetched ([environment variables](https://code.claude.com/docs/en/env-vars)), `--setting-sources ""`, `--disable-slash-commands`, `--permission-mode dontAsk`, `--no-session-persistence`, in a new empty folder, with an environment of only `HOME`, `PATH`, `LANG` and the switches that turn off telemetry, error reports, the auto-updater and the connectors ([CLI reference](https://code.claude.com/docs/en/cli-reference)). Never `--bare`: [it never reads the plan's login](https://code.claude.com/docs/en/headless#start-faster-with-bare-mode). Not `--safe-mode` either, which would also skip CLAUDE.md and plugins, because the docs don't say which version added it and an unknown flag stops the run; with no tools and no servers there's nothing for a customisation to run.
- The transcripts go on its input between tags, never on its command line, with any tag inside them changed; the instructions say they're untrusted data to summarise. The answer only replaces the digest when the run succeeded and said something.
- What's read: only what I typed and Claude's text answers, from the top-level transcript of each session in the folders I list (`DIGEST_REPOS`, up to 4, in `host/digest.env`, found the way `host/jarvis.sh` finds the sessions' notes). Not tool calls or results, thinking, subagents, slash commands or compact summaries: they're most of the size and most of the risk. Claude Code's docs say the transcript format is internal and changes between versions ([where transcripts are stored](https://code.claude.com/docs/en/sessions#where-transcripts-are-stored)); there's no other way to read a session's history in bulk, so this is a known weak point, and a `no-messages` result says when it breaks.
- Parsing in bash, awk and sed, which the server has, rather than `jq` (not installed by default) or Node (not on the host) or a throwaway container (more moving parts for a nightly job).
- The size: 2,000 characters a message, 300,000 in all, cut alike when over, then every second or third left out; about a sixth of the context window, so one run never fails on size.
- Redaction: the expiry list's rule for what could be a key, applied to each run of letters and digits; known token prefixes; UUIDs; values of anything named like a secret; `Bearer`, `ntfy.sh/` and spoken passwords; credentials in addresses; private key blocks. Before Claude and again after. It over-redacts on purpose.
- When it runs: a daily system timer (`home-hub-digest@<user>.timer`, a template so my user name isn't in the repo, at 04:40 London time), and the script decides if `DIGEST_EVERY` days have passed, with 2 hours' slack. Not a timer every 3 days, so changing `DIGEST_EVERY` needs no unit change. `--force` and `--dry-run` for trying it by hand. The script runs from `/usr/local/bin/home-hub-digest`, installed with sudo, so a Claude Code session in `~/docker` can't change what the timer runs; `host/hub-update.sh` now offers that install, and restarts every instance of a template timer it installs.
- Defaults: `DIGEST_DAYS=7` (1 to 30, as transcripts are kept 30 days), `DIGEST_EVERY=3` (no more than `DIGEST_DAYS`, so the file always covers the range), `DIGEST_INBOX=off`.
- The inbox note: plain markdown in the brain note's headings, Source, Date and Covers lines and a line saying the digest job wrote it, covering only the time since the last note (kept in `~/.local/state/home-hub/digest-state`), never overwriting a note, and not counted if it fails, so nothing is filed twice or missed.
- The log: one JSON line per run in `~/.local/state/home-hub/digest.jsonl`, numbers only.
- The lock, the log and the state live in `~/.local/state/home-hub/`, not `jarvis/data`, because Jarvis's container can write to `jarvis/data` and the job runs on the host as my user: a link planted there would make the job write through it to any of my files. The job refuses to run if `jarvis/data` or `jarvis/data/digest.md` is a link, and replaces `digest.md` with `mv -T`, which never follows a link to a folder.
- In Jarvis: `JARVIS_DIGEST=on|off`, default off. `digestFor({ guest })` reads the file at the start of each chat and returns nothing for a guest without reading it; `withDigest` adds it after the rest of his instructions, framed as information and never instructions, in tags, double quotes made single, at most 12,000 characters. A guest's chat passes `guest: true`, so it never gets the digest.

## Decision
A daily timer runs `host/digest.sh` as my user; every `DIGEST_EVERY` days it has `claude -p`, with no tools, summarise the redacted text of the last `DIGEST_DAYS` days of the listed Claude Code sessions into `jarvis/data/digest.md`, and with `DIGEST_INBOX=on` writes an inbox note covering only what's new. Jarvis reads the digest at the start of each chat with `JARVIS_DIGEST=on`, never in a guest's chat.

## Confidence and the case against
Medium for the script, lower for the parts that couldn't be run here. Every rule is tested with a pretend `claude` and made-up transcripts, and each was broken on purpose to check a test caught it. Not checked: that `claude -p` with these flags reads my plan's login on the server (the docs only say `--bare` doesn't), the real transcript lines of today's Claude Code (the test lines follow the shape Claude believes the files have, `"role":"user","content":"` for what I typed and `{"type":"text","text":"` for text blocks; no real transcript was available where this was built), and how good the summaries are. The case against: the digest is AI-written text about my week that goes into Jarvis's instructions every chat, so a transcript that carried someone else's words (a page Claude quoted back, a commit message) is a way into Jarvis that persists for days; it's framed as information, but that's a soft barrier. The redaction is pattern-matching and will miss a secret that looks like a word. It uses my plan's allowance every three days for something I may rarely ask about, and session notes already give Jarvis some of this for free. And parsing an internal format with awk will break silently on some update.

## Consequences
- New host files to install: `/usr/local/bin/home-hub-digest`, `home-hub-digest@.service` and `home-hub-digest@.timer`, and a git-ignored `host/digest.env`.
- The job reads my Claude Code transcripts and sends redacted excerpts to Anthropic through my plan, as the sessions themselves already did.
- With `DIGEST_INBOX=on`, notes appear in `~/hub-memory/inbox/` that no one typed.
- With `JARVIS_DIGEST=on`, every chat's instructions grow by up to 12,000 characters (roughly 3,000 tokens, Claude's estimate).
