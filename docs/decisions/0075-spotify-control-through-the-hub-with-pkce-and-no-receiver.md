# 0075. Spotify control through the hub, signed in with PKCE, with no receiver on the server

- Date: 2026-11-27
- Status: accepted

## Context
I have Spotify Premium and wanted to control it from the hub and Jarvis: music on any device I ask, with Spotify's full capabilities. I'll make the developer app and sign in myself. Replacing Spotify is ruled out, so this works with it.

Spotify changed what Development Mode apps can use in February 2026 ([update](https://developer.spotify.com/blog/2026-02-06-update-on-developer-access-and-platform-security), [migration guide](https://developer.spotify.com/documentation/web-api/tutorials/february-2026-migration-guide), [changelog](https://developer.spotify.com/documentation/web-api/references/changes/february-2026)): the app's owner needs Premium, new apps get 5 users, batch and browse endpoints went, the library and playlist-item endpoints were renamed (`PUT /me/library`, `/playlists/{id}/items`) and search returns at most 10 of each kind. The changelog lists every player endpoint as still available. The March, May and July 2026 changelogs restored a field, added one and changed the quota counting, and removed nothing else. Extended Quota Mode is only for organisations with 250,000 monthly users ([quota modes](https://developer.spotify.com/documentation/web-api/concepts/quota-modes)), so this stays in Development Mode.

## Options considered
Chosen 27 Nov (Phil): he has Premium; music on any device he asks; full Spotify capabilities; he does the developer app setup and the sign-in himself.

Claude's picks, not discussed:
- How it signs in: Authorization Code with PKCE ([Spotify's PKCE guide](https://developer.spotify.com/documentation/web-api/tutorials/code-pkce-flow)), so no client secret exists anywhere. Not the plain Authorization Code flow, which needs a secret in `api/.env`, and not the Implicit Grant, which Spotify has deprecated and which can't renew itself.
- Where the code lands: a page of the hub's own, `hub/spotify.html`, posts Spotify's code and state to `POST /spotify/callback`, behind the API's token. Not a route Spotify's redirect lands on directly: the login cookie is `SameSite=Strict`, so the browser wouldn't send it on a redirect from Spotify, and that route would have to skip the token, the first route besides logging in to do so. A paste box on the same page handles a loopback redirect address.
- `SPOTIFY_REDIRECT_URI` as its own setting, checked against Spotify's rules ([redirect URIs](https://developer.spotify.com/documentation/web-api/concepts/redirect_uri)): https, or http on `127.0.0.1` or `[::1]` with a port, never `localhost`. Suggested value `https://hub.home/spotify.html`; whether Spotify's dashboard accepts a `.home` address isn't documented and wasn't checked, so `http://127.0.0.1:8888/callback` with the paste box is the fallback.
- One sign-in waits at a time, for 10 minutes, in memory; its state is compared in constant time and used once.
- The refresh token in `spotify/tokens.json`, a git-ignored folder mounted like `deals/` and `expiry/`, written with mode 600 through a temporary file, and denied to Claude Code in `.claude/settings.json`. The access token stays in memory. The batch spec said "the API's data folder"; there isn't one shared folder yet, so this follows the per-module folders.
- Renewal a minute early, two asks sharing one renewal, the newest refresh token kept, and the file removed when Spotify answers `invalid_grant`, so a revoked sign-in says so instead of failing on every call.
- Ten scopes, listed in the README. `user-follow-modify` because Spotify's page for saving to the library lists it, `user-read-private` because `GET /me` lists it, and no email scope.
- The routes and limits: the endpoints listed as still available only, search limited to 10 as Spotify now is, 100 items to a playlist and 40 to the library as their pages say, the queue cut to 20. Saving sends the addresses in the query, as the page's example is written; the page doesn't say which, and it wasn't checked against Spotify. Removing from the library, creating playlists, following artists and recently played weren't built: they weren't asked for.
- Adding to a playlist checks first that it's mine or collaborative, so the AI can't add to someone else's even if Spotify would let it.
- Errors in plain words, never Spotify's message, with a 403 that has no reason explained as the Development Mode user list, since that's what Spotify's docs say it means.
- Its log lines: what each call was, status, time, reason code and counts, never a token, code, verifier, state, Client ID, id, address or search words.
- MCP: five read tools named `get_spotify_*` (Jarvis's tests want reads to start `get_`) and twelve actions named `spotify_*`, in their own file, `mcp/src/spotify-tools.ts`. Claude Code always asks before an action.
- Jarvis: playback controls (play, pause, next, previous, seek, volume, shuffle, repeat, queue, transfer) run without his yes, because they're harmless and undone with another command; adding to a playlist or saving to the library always asks. `JARVIS_MUSIC_YES=changes|all`, default `changes`, makes every Spotify action ask. The rule is `needsHubYes` in `jarvis/src/hub-tools.ts`, used by the Agent SDK's hook in `agent.ts` and the plain engine in `hub-client.ts`, and the setting reaches it through `hubServerFor` in `jarvis.ts`: three one-line changes outside `hub-tools.ts`, because that's where the two engines decide.
- No receiver on the server for now, so the hub plays only on devices where Spotify is already open; the list below is for Phil to decide later. The maintained Spotify Connect receivers, for a later decision (versions from their changelogs and package pages on 27 Nov 2026; memory use is Claude's guess, not measured or documented): [librespot](https://github.com/librespot-org/librespot) (MIT, Rust library and player, 0.8.0 of 2025-11-10 with unreleased work since), [raspotify](https://github.com/dtcooper/raspotify) (MIT, a Debian package of librespot with an amd64 build, 0.48.4 of 2026-10-22), [Spotifyd](https://github.com/Spotifyd/spotifyd) (GPL-3.0, a daemon built on librespot, 0.4.2, dated 19 Nov on its releases page with no year; its files looked like 2025, not confirmed), [go-librespot](https://github.com/devgianlu/go-librespot) (GPL-3.0, Go, with a published Docker image and an API, [0.10.7 of 2026-11-18](https://pkg.go.dev/github.com/devgianlu/go-librespot)). All need Premium, and each would need the laptop's speakers (as Jarvis has them) and, for discovery, mDNS on the LAN, which in a container means host networking or a published port.

## Decision
With `SPOTIFY=on`, the hub controls my Spotify through its Web API, signed in with PKCE from a hub page, keeping the refresh token in a git-ignored file only the API can read, with read tools and actions for Claude Code and Jarvis. Jarvis's playback controls need no yes unless `JARVIS_MUSIC_YES=all`; playlist and library changes always do.

## Confidence and the case against
Medium. The flow, token handling, refusals and every route are tested against a stand-in Spotify, but nothing here has talked to the real Spotify: the reply shapes come from its reference pages, and two things are open (whether the dashboard takes a `.home` redirect, and whether saving wants the addresses in the query). The case against: Spotify has cut Development Mode twice in two years and could cut player endpoints next, and a 5-user, owner-needs-Premium app is fragile. Phil's phone already has Spotify Connect for "music on any device", so the hub adds Jarvis's voice and little else. A refresh token on the server is a long-lived secret that controls the account until it's revoked in Spotify's settings. And letting Jarvis change playback without a yes means a misheard question can start music, which is the price of not answering yes to every pause.

## Consequences
- `SPOTIFY` is a new switch in `api/.env`, so the API won't start without it; with it on, `SPOTIFY_CLIENT_ID` and `SPOTIFY_REDIRECT_URI` are needed.
- The API mounts `./spotify` and reaches `accounts.spotify.com` and `api.spotify.com`, and may hold a new secret, the refresh token.
- `.claude/settings.json` allows the five read tools, asks before the twelve actions and denies reading `spotify/`.
- Jarvis's hub actions now include Spotify's, and his live facts' line that each action needs a yes is no longer true for playback controls with `JARVIS_MUSIC_YES=changes`.
- Playing through the server's speakers needs its own decision about a receiver.
